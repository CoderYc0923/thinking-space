### 1、为什么 Redis 单线程模型还这么快？（高频必问）

**标准答案：**

Redis 核心命令执行是单线程，但速度极快，原因四点：

1）**纯内存操作**：所有数据在内存，读写速度远超磁盘数据库；

2）**IO 多路复用**：单线程监听海量客户端连接，不阻塞、不浪费线程资源；

3）**避免线程开销**：无需线程切换、无需锁竞争，执行效率极高；

4）**数据结构高度优化**：底层 **SDS、跳跃表、压缩列表**都是为高速读写设计。

**补充**：Redis6+ 是 **IO 多线程，命令执行依然单线程**。

### 2、Redis 适合做什么？不适合做什么？

**标准答案：**

✅ 适合场景：

热点缓存、分布式锁、计数器、限流、排行榜、UV统计、签到、简单消息队列、Session共享。

❌ 不适合场景：

海量冷数据持久存储（内存成本高）、强事务场景、超大文本存储、数据不能丢的核心业务主库。

### 3、Redis 过期 key 是怎么删除的？

**标准答案：三种删除策略结合**

1）**惰性删除**：用户访问 key 时才判断过期，过期直接删，节省CPU；缺点是冷门过期key占内存。

2）**定期删除**：每隔一段时间随机抽取部分过期key删除，平衡CPU与内存。

3）**内存淘汰策略**：内存满了主动淘汰数据。

### 4、Redis 8种内存淘汰策略，生产用哪个？

**标准答案：**

volatile 系列：只淘汰带过期时间的 key

\- volatile-lru、volatile-lfu、volatile-random、volatile-ttl

allkeys 系列：淘汰所有key

\- allkeys-lru、allkeys-lfu、allkeys-random

\- noeviction：默认，内存满直接报错

**生产最优：allkeys-lru（优先淘汰最少使用）**

### 5、什么是缓存穿透？场景+解决方案

**场景**：请求数据库不存在的数据（如 id=-1、虚假手机号），缓存永远不命中，压力全部打库。

**标准答案解决方案：**

1）接口参数校验，拦截非法参数；

2）**空值缓存**：查询为空也缓存，过期时间短一点；

3）**布隆过滤器**：提前拦截不存在的key。

### 6、什么是缓存击穿？场景+解决方案

**场景**：**热点Key** 过期瞬间，海量并发请求全部打数据库。比如（秒杀商品、首页热门）

**标准答案解决方案：**

1）**热点Key永不过期**（业务最常用、最简单）；

2）**分布式互斥锁**：只放一个请求查库，其他请求等缓存；

3）逻辑过期（异步更新缓存）。

### 7、什么是缓存雪崩？场景+解决方案

**场景**：大量key同时过期 / Redis宕机，大量请求瞬间压垮数据库。

**标准答案解决方案：**

1）过期时间加**随机偏移量**，避免集体过期；

2）Redis 高可用（主从+哨兵/集群）防止宕机；

3）服务层**限流、降级、熔断**；

4）多级缓存（本地缓存+Redis）。

### 8、RDB 和 AOF 区别？生产怎么搭配？

**标准答案：**

**RDB（快照）**

原理：定时全量内存快照二进制落盘。

优点：文件小、恢复快、适合冷备。

缺点：会丢失最后一次快照后的数据。

**AOF（日志追加）**

原理：记录每一条写命令，重启回放恢复数据。

优点：数据极安全，最多丢1秒数据。

缺点：文件大、恢复慢、需要重写压缩。

**生产标准配置：RDB+AOF 同时开启，优先AOF恢复数据**

### 9、AOF 重写是干嘛的？

**标准答案**：AOF 日志会越来越大，Redis后台会合并冗余命令（多次set同一个key只保留最后一条），压缩文件体积，不影响主程序运行。

### 10、主从复制原理 & 问题

**标准答案**：

主节点写，从节点同步数据、只读分担读压力。

流程：建立连接 -> 全量同步（RDB传输） -> 增量同步（回放缓冲区命令）。

**致命缺点**：主节点宕机，**无法自动切换**，只能人工操作。

### 11、哨兵机制核心作用

**标准答案**：

基于主从，增加自动运维能力：

1）监控：实时监听主从节点状态；

2）主观下线+客观下线：多哨兵投票判定真宕机；

3）**自动故障转移**：主挂了自动选新主、改从节点指向；

4）通知客户端新master地址。

**适用场景**：数据量不大、不需要分片，只需要高可用。

### 12、Redis Cluster 集群原理、为什么16384个槽？

**标准答案**：

集群把数据分成 **16384 个hash槽**，不同主节点负责不同槽，实现**数据分片、水平扩容**。

16384 原因：

1）槽位太少分片不均匀，太多浪费内存；

2）16384 刚好满足集群通信、心跳、分片均衡需求；

3）Redis 作者官方最优取值。

**集群限制**：不支持跨槽多key操作（mget/mset 跨槽报错）。

### 13、Redis 分布式锁正确写法？为什么不用单纯 setnx？

**标准答案**：

错误：setnx + expire 两条命令，非原子，中间宕机会死锁。

**正确命令：SET key value NX EX 过期时间**

NX：不存在才创建（加锁）

EX：自动过期，防止死锁

### 14、锁超时导致业务没执行完，怎么解决？

**标准答案**：

使用 **Redisson 看门狗机制**：

加锁成功后，后台定时续期锁过期时间，业务没执行完锁不释放，业务结束停止续期。

### 15、释放锁为什么必须用 Lua 脚本？

**标准答案**：

防止误删别人的锁：

1）判断锁是自己的（匹配唯一value）；

2）删除锁；

两条操作必须原子，Lua 保证整体原子执行。

### 16、Redis 集群分布式锁存在什么问题？怎么解决？

**标准答案**：

主从异步复制，主节点加锁成功、没同步到从就宕机，新主节点允许重复加锁，**锁失效**。

解决：**Redlock 红锁机制**（多节点过半加锁成功才算加锁成功）。

### 17、大Key问题、危害、解决方案

**场景**：几十K的String、百万元素List/Hash

**危害**：

1）读写耗时变长，阻塞单线程；

2）网络传输卡顿、集群迁移卡顿、CPU飙升。

**解决方案**：

拆分大key、禁止存储超大对象、异步删除、合理控制数据粒度。

### 18、缓存更新策略（双写一致）

**标准答案最优方案：先更新数据库，再删除缓存**

原因：

1）数据库更新成功率高；

2）删除缓存让下次请求自动预热，数据一致性更高；

3）避免先更缓存导致的频繁无效更新。

**终极兜底**：定时任务兜底刷新缓存、过期时间兜底。

### 19、Redis 为什么不适合强一致性场景？

**标准答案**：

1）主从复制是异步复制，存在数据延迟；

2）集群槽位迁移、故障切换会短暂数据不一致；

3）只能保证最终一致性，无法保证强一致。

### 20、本地缓存 + Redis 二级缓存优势？

**标准答案**：

1）减少Redis请求量，降低网络开销；

2）Redis宕机不影响核心服务；

3）抗并发能力更强，有效防止雪崩。

示例

```java
// 顺序：本地 Caffeine → Redis → DB

// 查询
public String getGoods (Long id) {
    // 本地缓存命中直接返回
    String val = localCache.getIfPresent(id);
    if (val != null) return val;
    
    // 查redis
    val = redisTemplate.get("goods:"+id);
    if (val != null) {
        localCache.put(id, val); //写进本地
        return val;
    }
    
    // 查数据库
    val = db.query(id);
    // 写回两级缓存
    redisTemplate.set("goods:"+id, val, 5, TimeUtil.MINUTES);
    localcache.put(id, val);
    return val;
}

// 更新：更新DB，再删除缓存
public void update(Long id) {
    db.update(id);
    redisTemplate.delete("goods:"+id);
    // 无法清除其他机器的本地缓存，靠本地短TTL过期
    localcache.invalidate(id);
}
```
