Redis（Remote Dictiomary Server）远程字典服务，基于**内存的键值对NoSQL数据库**，C语言开发，单线程模型（IO多路复用），高性能，常用来做**缓存、分布式锁、计数器、消息队列**

> 核心特点：内存为主，可持久化；多数据结构；单线程；高性能；支持集群



## 一、核心特性

1. **内存数据库**：绝大部分数据放内存，读写极快，QPS 可达 10w+
2. **丰富数据结构**：不只是简单 key‑value，支持多种数据类型
3. **持久化**：内存数据落磁盘，重启不丢数据（RDB、AOF）
4. **单线程模型**：命令执行是单线程，避免多线程竞争；IO 多路复用处理网络 IO
   - ⚠️：Redis6 以后有多线程 IO，但**命令执行依旧单线程**。
5. **高可用**：主从复制、哨兵 Sentinel、Redis‑Cluster 集群
6. **原子操作**：单条命令原子；多条可以用 Lua 脚本保证原子
7. **过期时间**：key 可以设置 TTL，自动过期删除



## 二、常用数据结构与场景

| 类型          | 说明                       | 典型业务场景                   |
| ------------- | -------------------------- | ------------------------------ |
| String 字符串 | 可以存字符串、数字、二进制 | 缓存、计数器、分布式 ID、token |
| Hash 哈希     | key‑field‑value，类似 map  | 用户信息、对象存储             |
| List 列表     | 双向链表，两头读写         | 简单消息队列、排行榜、日志列表 |
| Set 集合      | 无序、去重                 | 标签、交集并集、去重统计       |
| ZSet 有序集合 | 带 score 权重排序          | 排行榜、延时队列               |
| BitMap 位图   | 按位操作                   | 签到、统计在线人数             |
| HyperLogLog   | 基数统计                   | UV 统计，允许误差              |
| Geo 地理位置  | 经纬度                     | 附近的人                       |

简单示例命令

```js
# String
set name zhangsan
get name
incr count

# Hash
hset user:100 name lisi age 20
hgetall user:100

# ZSet
zadd rank 100 user1 90 user2
zrange rank 0 -1 withscores
```





## 三、三大删除策略

设置了过期时间的 key，不会到期立刻删除：

1. **惰性删除**：访问 key 的时候才判断是否过期，过期直接删。优点省 CPU；缺点大量过期 key 不访问会占内存
2. **定期删除**：Redis 每隔一段时间随机抽取一批过期 key 删除。平衡 CPU 和内存
3. **内存淘汰策略**：内存满了，执行淘汰策略释放内存（maxmemory 配置）
   - 8 种内存淘汰策略
     - `noeviction`：默认，内存满直接报错，拒绝写入
     - `allkeys‑lru`：所有 key，淘汰最近最少使用
     - `volatile‑lru`：只对带过期时间 key，淘汰 LRU
     - `allkeys‑lfu`：所有 key，淘汰访问频次最低
     - `volatile‑lfu`：过期 key 中淘汰 LFU
     - `allkeys‑random`：全部 key 随机删
     - `volatile‑random`：过期 key 随机删
     - `volatile‑ttl`：过期 key 优先删剩余时间最短
   - 生产最常用：`allkeys‑lru`





## 四、持久化 RDB vs AOF

Redis 内存断电丢失，靠持久化落盘。

1. RDB 快照
   - **把某一刻全量内存数据二进制写入磁盘`.rdb`文件**
   - 触发：**手动`save`、`bgsave`**；**配置定时触发**；**主从同步**；**shutdown**
   - bgsave：**fork 子进程做快照，主进程继续服务**
     - ✅优点：**文件小，恢复速度快；适合备份**
     - ❌缺点：**两次快照之间的数据会丢失**；**fork 会消耗内存**
2. AOF 追加日志
   - 把每一条写命令追加到 aof 日志文件
   - 三种刷盘策略 `appendfsync`
     - **always：每写就刷盘，最安全性能差**
     - **everysec：每秒刷盘，默认，最多丢 1 秒数据**
     - **no：交给操作系统控制，不可控**
   - AOF 重写：**aof 文件膨胀**，后台**重写压缩日志**
   - ✅优点：数据丢失极少；安全性高。
   - ❌缺点：文件体积大，恢复比 RDB 慢
3. 生产建议：**RDB+AOF 同时开启，AOF 优先恢复**





## 五、高可用方案

1. **主从复制 Master‑Slave**

   - **主节点写**，从节点**复制数据**，**从节点只读**

   - 作用：读写分离、数据备份

   - 问题：主节点挂掉，不能自动切换，需要人工干预

   - 案例

     - ```js
       // 环境：3 台机器示例
       // 192.168.1.10 master
       // 192.168.1.11 slave‑1
       // 192.168.1.12 slave‑2
       
       // 主从复制：数据备份、读写分离；没有自动故障转移，主挂了需要人工切换
       // master 192.168.1.10 redis.conf
       bind 0.0.0.0
       port 6379
       # 主不需要配置从，从节点配置指向主
       
       
       // slave‑1 / slave‑2 redis.conf
       bind 0.0.0.0
       port 6379
       replicaof 192.168.1.10 6379   # 指定主节点地址
       replica‑read‑only yes          # 从节点只读，禁止写
       
       
       // 操作
       # 分别启动3个redis
       redis‑server redis.conf
       
       # 在从节点查看复制状态
       redis‑cli
       info replication
       
       
       // master 角色：role:master
       // slave 角色：role:slave
       ✅测试：master 执行 set name test，slave 执行 get name 拿到数据。
       ❗master 宕机，从不会自动升级为主，需要手动执行 slaveof no one 把从提升为主
       ```

     - 

2. **哨兵 Sentinel**

   - **监控主从节点**，**主宕机后自动选新主，自动故障转移**

   - 至少 **3 个**哨兵实例

   - 客户端**连接哨兵**获取主节点地址

   - 案例

     - ```js
       // 架构：1 主 2 从 + 至少 3 个 sentinel 哨兵进程，哨兵独立于 redis 实例
       // 作用：监控，主宕机自动选新 master，通知客户端
       
       // 示例：3 个 sentinel，端口 26379 / 26380 /26381
       // sentinel‑26379.conf
       port 26379
       bind 0.0.0.0
       # 监控主节点，mymaster自定义主名字，2代表至少2个哨兵同意才判定主下线
       sentinel monitor mymaster 192.168.1.10 6379 2
       sentinel down‑after‑milliseconds mymaster 5000    # 5000ms没响应判定主观下线
       sentinel failover‑timeout mymaster 10000
       
       // 另外两个哨兵配置只是 port 改 26380、26381，其余配置一样
       
       
       //启动
       # 先启动好1主2从redis实例
       # 启动3个哨兵
       redis‑sentinel sentinel‑26379.conf
       redis‑sentinel sentinel‑26380.conf
       redis‑sentinel sentinel‑26381.conf
       
       
       // 测试故障转移
       
       # 杀掉master节点redis
       kill -9 <master‑pid>
       
       # 哨兵日志会看到：投票选举，把其中一个slave升级为新master，剩余从节点自动追随新主
       
       
       
       // Java/SpringBoot 客户端使用哨兵
       spring.redis.sentinel.master=mymaster
       spring.redis.sentinel.nodes=192.168.1.10:26379,192.168.1.11:26380,192.168.1.12:26381
       // 客户端连接哨兵，哨兵返回当前真正 master 地址，不需要硬编码 masterIP
       ```

     - 

3. **Redis‑Cluster 集群（分片）**

   - 解决**单节点内存上限**，**水平分片**

   - **16384** 个 **hash 槽**，key 做 hash 映射到槽

   - 至少 **3 主 3 从**

   - 支持数据分片 + 故障转移

   - 注意：cluster 不支持多 key 跨槽操作（mset、mget 跨槽报错）

   - 案例

     - ```js
       // （分片集群，3 主 3 从）
       // 目标：分片存储，突破单节点内存上限；同时自带故障转移。
       // 规则：一共 16384 个 hash 槽，key 哈希分配到槽；至少 3 主，每个主配一个从，标准 3 主 3 从共 6 实例
       // 6 个节点端口：
       // 主 1：7001；从 1：7002
       // 主 2：7003；从 2：7004
       // 主 3：7005；从 3：7006
       
       // 每个节点 redis‑700x.conf（示例 7001）
       port 7001
       bind 0.0.0.0
       cluster‑enabled yes                  # 开启集群模式
       cluster‑config‑file nodes‑7001.conf  # 集群元数据文件
       cluster‑node‑timeout 15000
       appendonly yes
       // 6 份配置文件，只改 port、cluster‑config‑file。
       
       // 启动全部 6 个 redis 实例
       redis‑server redis‑7001.conf
       redis‑server redis‑7002.conf
       redis‑server redis‑7003.conf
       redis‑server redis‑7004.conf
       redis‑server redis‑7005.conf
       redis‑server redis‑7006.conf
       
       
       // 创建集群（redis‑cli 一键创建）
       redis‑cli --cluster create \
       127.0.0.1:7001 127.0.0.1:7002 \
       127.0.0.1:7003 127.0.0.1:7004 \
       127.0.0.1:7005 127.0.0.1:7006 \
       --cluster‑replicas 1
       // --cluster‑replicas 1：每个主分配 1 个从节点。输入 yes 确认分配槽
       
       
       // 集群客户端连接
       # -c 开启集群模式，自动跳转槽
       redis‑cli -c -p 7001
       > set k1 v1
       > get k1
       
       
       // SpringBoot 配置集群：
       spring.redis.cluster.nodes=127.0.0.1:7001,127.0.0.1:7002,127.0.0.1:7003,127.0.0.1:7004,127.0.0.1:7005,127.0.0.1:7006
       ⚠️限制：跨槽多 key 命令 mget/mset 会报错，除非 key 用 hash tag 强制落到同一个槽
       ```

   

4. | 方案          | 核心能力            | 故障自动转移 | 适用场景                     |
   | ------------- | ------------------- | ------------ | ---------------------------- |
   | 主从复制      | 读写分离、备份      | ❌人工切换    | 简单备份，测试环境           |
   | Sentinel 哨兵 | 主从 + 自动故障转移 | ✅            | **不做分片，只做高可用缓存** |
   | Redis‑Cluster | 分片 + 高可用       | ✅            | 数据量大，需要水平扩容       |

   **主从：只备份；哨兵：主从自动续命；cluster：分片 + 续命**

   





## 六、适合 & 不适合场景

1. ✅适合：
   - 热点数据缓存
   - 计数器、限流
   - 排行榜、延时队列
   - 分布式锁、会话存储
   - UV 统计、签到
2. ❌不适合：
   - 海量持久化存储（Redis 是内存库，成本高）
   - 需要强事务支持





## 七、分布式锁要点

用 Redis 做分布式锁，`SET key value NX EX`

- **NX**：key 不存在才设置
- **EX**：过期时间，防止死锁
- **注意**：
  - 锁释放必须**判断是自己加的锁**，不能直接 del；推荐 **Lua 脚本释放锁**
  - 注意**锁续期**（**Redisson 看门狗**）
  - Redis **集群环境会有锁失效风险**，**红锁 Redlock**
