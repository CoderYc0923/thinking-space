## Redis 常见锁详解

Redis 实现分布式锁核心解决：**多进程 / 多服务实例并发争抢共享资源**，分为：**基于 SETNX 的基础锁、Redlock 红锁、Redisson 可重入锁、读写锁、信号量、联锁**，同时区分**悲观锁 / 乐观锁（Redis 事务 + Watch）**。

> 注意：Redis 锁是**分布式锁**，和 JVM 本地锁 (synchronized、Lock) 不一样，本地锁只在单个 JVM 内生效，集群环境失效。



## 基础分布式锁（SETNX + expire，原生命令）

```js
# 原子加锁：key锁名称，value唯一标识(UUID)，NX不存在才设置，EX过期时间(秒)
SET lock:goods UUID-123 NX EX 30

# 释放锁：Lua脚本保证原子，判断value匹配才删除，防止误删别人的锁
if redis.call('get',KEYS[1]) == ARGV[1] then
    return redis.call('del',KEYS[1])
else
    return 0
end
```

- 问题:
  - 不可重入：同一个线程再次获取锁直接失败；
  - 没有锁等待，抢不到直接失败，需要业务自己做重试；
  - 主从切换风险：主节点加锁成功，锁还没同步到从节点，主宕机，从升级为主，其他客户端可以再次拿到锁，出现锁失效
- 适用：简单业务，自己封装，不推荐生产直接裸写。



## Redisson 可重入锁 RLock（生产最常用）

底层就是封装上面 Lua 脚本，**可重入锁（Reentrant Lock）**，类似 Java `ReentrantLock`

- **可重入**：同一个客户端线程，多次加锁，计数器 + 1；释放锁计数器 - 1，计数器为 0 真正删除 key

- **自动续锁（看门狗 WatchDog）**：如果业务执行超过锁过期时间，后台线程自动延长锁过期时间，避免业务没跑完锁过期释放

- 支持阻塞等待、超时获取锁

- 仍然存在主从切换锁丢失问题

- ```JAVA
  RLock lock = redissonClient.getLock("lock:goods");
  // 尝试获取锁，等待10s，锁30s
  boolean ok = lock.tryLock(10,30, TimeUnit.SECONDS);
  try{
      //执行业务
  }finally {
      if(lock.isHeldByCurrentThread()){
          lock.unlock();
      }
  }
  ```

- 看门狗：如果你不指定 leaseTime（锁过期时间），redisson 默认 30s，每 10s 续期；指定 leaseTime 看门狗失效





## Redlock 红锁（解决主从锁丢失问题）

业界争议很大，Redis 官方文档提醒谨慎使用

原理：**N 个独立 Redis 主节点（无主从，完全独立）**，客户端向全部节点申请锁，超过半数节点加锁成功，才算拿到锁

- 优点：规避主从异步同步导致锁丢失
- 缺点：
  - 需要部署多套独立 Redis，成本高；
  - 时钟漂移风险
  - 性能差，需要和多个 Redis 交互
  - 大部分场景不推荐，优先用 Zookeeper 做强一致性锁，如果业务可以容忍极小概率锁失效，普通 Redisson 锁足够
- Redisson 也提供`RedissonRedLock`实现红锁





## Redisson 读写锁 RReadWriteLock

读写分离锁：**读锁共享，写锁互斥**

- 多个线程可以同时拿到读锁

- 写锁排他，有读锁存在时写锁阻塞；有写锁时读锁阻塞

- ```JAVA
  RReadWriteLock rwLock = redissonClient.getReadWriteLock("rw:lock");
  RLock readLock = rwLock.readLock(); //读锁
  RLock writeLock = rwLock.writeLock();//写锁
  ```

- 适用场景：读多写少，比如缓存更新，大量读，少量修改





## 联锁 MultiLock

把**多个不同 key 的锁捆绑成一把大锁**，必须所有 key 全部加锁成功，才算获取锁；释放的时候全部释放

场景：需要同时锁定多个资源，比如同时操作订单、账户两个资源 key

```JAVA
RLock lock1 = redissonClient.getLock("key1");
RLock lock2 = redissonClient.getLock("key2");
RLock multiLock = new RedissonMultiLock(lock1,lock2);
multiLock.lock();
```





## 信号量 RSemaphore & 可过期信号量

信号量（限流、池化）

相当于分布式`Semaphore`，设置许可数，acquire 获取许可，release 归还

```JAVA
// 例：设置许可 5，最多 5 个线程同时执行业务。
RSemaphore semaphore = redissonClient.getSemaphore("sem");
semaphore.tryAcquire();
semaphore.release();
```

**可过期信号量（PermitExpirableSemaphore）**

许可可以设置过期时间，许可超时自动归还



## 公平锁 FairLock

普通锁是非公平锁：多个客户端抢锁，谁先抢到谁执行，会出现饥饿

公平锁：按照请求的顺序排队，先来先获取锁

性能比非公平锁差

```java
RLock fairLock = redissonClient.getFairLock("fair:lock");
```





## Redis 乐观锁（WATCH + MULTI 事务）

不是真正分布式锁，属于乐观并发控制，不加锁，基于版本校验

```js
WATCH stock:num #监听key，如果key被别人修改，事务直接失败
MULTI
DECR stock:num
EXEC
```

- 特点：无阻塞，不加锁；冲突直接失败，需要业务重试
- 局限：只支持单机 Redis，集群环境 WATCH 失效；不能做跨节点分布式锁





| 锁类型                  | 是否可重入 | 特点                     | 适用场景             | 风险点                    |
| ----------------------- | ---------- | ------------------------ | -------------------- | ------------------------- |
| SETNX 原生锁            | ❌          | 自己写 Lua，轻量         | 简单临时锁           | 不可重入、主从切换锁丢失  |
| Redisson 可重入锁 RLock | ✅          | 看门狗自动续期，阻塞等待 | 绝大多数业务分布式锁 | 主从切换极小概率锁失效    |
| 公平锁 FairLock         | ✅          | 排队先来先得             | 对顺序有要求         | 性能低                    |
| 读写锁 RReadWriteLock   | ✅          | 读共享写互斥             | 读多写少场景         | 写饥饿，大量读会阻塞写    |
| 联锁 MultiLock          | ✅          | 同时锁定多个 key         | 多资源同时锁定       | 任意 key 加锁失败全部失败 |
| RedLock 红锁            | ✅          | 多独立节点过半成功       | 追求锁强一致性       | 部署重、时钟漂移，不推荐  |
| 信号量 Semaphore        | —          | 控制并发许可数量         | 分布式限流、资源池   | 许可泄露问题              |
| Watch 乐观锁            | —          | 无锁，版本校验           | 单机短事务并发       | 集群无效，冲突需要重试    |





## 生产实践面试高频考点

**为什么不能 SETNX + EXPIRE 分两条命令？**

两条命令不是原子，如果 setnx 成功，expire 还没执行，服务宕机 → 锁永不过期，死锁。必须用`SET key value NX EX`一条原子命令。

**为什么释放锁不能直接 DEL？**

业务超时锁过期，其他线程拿到锁，当前线程执行 del 会删掉别人的锁。**必须 Lua 脚本判断 value（客户端唯一标识）匹配才删除**。

**看门狗原理？什么时候失效？**

没有手动指定 leaseTime 时开启，默认锁 30s，每 10s 续期；设置 leaseTime 看门狗关闭。

**Redis 分布式锁最大缺陷？**

主从异步复制，主节点加锁成功，未同步到从节点，主宕机，从升主，锁失效。追求绝对安全用 Zookeeper。

**可重入锁怎么实现？**

value 存储`线程ID + 重入计数`，Lua 脚本做计数加减。

**Redlock 实际要不要用？**

绝大多数业务不用，能接受极小概率锁失效就普通 RLock；强一致性选 zookeeper。
