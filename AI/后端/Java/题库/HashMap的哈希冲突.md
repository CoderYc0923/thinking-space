## 什么是哈希冲突？HashMap 是怎么处理哈希冲突的？

```js
哈希冲突指的是不同的key，经过hash计算之后得到了相同的数组下标
HashMap无法彻底杜绝哈希冲突，分为 降低冲突发生概率 和 冲突产生之后的解决策略 两部分

put 时判断 key 是否相同：先对比 hash 值，再==，再equals()；hash 相同但 equals 不同就是哈希冲突

1. 降低冲突概率（预防）
	1.1 扰动函数h ^ (h >>>16),让hash值高16位参与下标运算，优化hash值离散度，减少碰撞
	1.2 底层数组容量强制为2的n次幂，通过(n-1)&hash位运算获取桶下标，保证散列分布均匀
	1.3 设置负载因子0.75，达到阈值触发扩容；数组扩容，桶数量变多，分散元素，减少单个桶元素数量
2. 冲突发生之后的解决方案（链地址法）
	2.1 JDK18 采用数组 + 链表 + 红黑树
	2.2 桶位置已有元素，则把冲突元素挂载到桶后面
	2.3 链表长度大于8，且数组容量≥64，链表转为红黑树，查询复杂度由O(n)优化为O(logn)
	2.4 当树节点减少到≤6，，红黑树退化成链表，降低树维护开销
    2.5 JDK1.7 是数组 + 单向链表，头插法，并发扩容会产生环形链表死循环；JDK1.8 改为尾插法解决该问题。
    
```



## 为什么会产生 hash 冲突？

```js
1. hash 值是 int 类型，取值范围有限，但对象 key 是无限的，鸽巢原理，必然存在不同对象 hashCode 相同
2. HashMap 的桶下标是(n‑1)&hash，是对 hash 做压缩映射；不同 hash 值也可能算出同一个下标
3. 业务自定义对象hashCode()实现质量差，大量对象返回相同 hash 值，人为制造大量冲突

契约：equals()相等的对象，hashCode 必须相等；hashCode 相等，对象不一定 equals，这就是冲突根源
```





## HashMap 做了哪些手段来减少 / 解决 hash 冲突？

```js
1. 预防手段（减少冲突概率，不能完全避免）
	1.1 扰动函数，高低位混合运算，改善 hash 分布
	1.2 容量强制 2 的幂，位运算计算下标，散列更均匀
    1.3 负载因子 0.75，达到阈值自动扩容，增加桶数量分散元素
2. 冲突已经发生，链地址法解决冲突
	2.1 JDK8：数组 + 链表 + 红黑树；冲突元素挂在同一个桶下；长链表转红黑树提升查询效率；节点变少退化为链表
	2.2 JDK7：数组 + 单向链表头插法，存在并发死循环问题
```





## 扰动函数 `h ^ h>>>16` 原理，为什么要右移 16 位？

```js
1. 计算桶下标是(n‑1)&hash，n 是 2 的幂，一般数组不会特别大，只有 hash 的低位 bit 生效，高位会被丢弃。
2. 如果直接使用原始 hashCode，高位信息完全浪费，冲突概率变大。
3. 将 hash 右移 16 位，把高 16 位移到低 16 位，和原 hash 做异或，把高低位信息混合到低位，让低位也携带原始 hash 的高位特征，提升 hash 离散性，降低冲突。
```





## 为什么容量必须是 2 的幂？不是 2 的幂会怎么样？

```js
1. 桶下标公式 index = (n‑1) & hash。
2. 当 n 为 2 的 n 次幂，n‑1二进制全部为 1，&运算等价于取模hash % n，运算速度远高于取模。
3. 如果不是 2 的幂，n‑1二进制会出现 0 位，hash 对应的 bit 位会被直接置 0，大量 key 映射到同一个下标，冲突急剧上升。
4. 扩容、初始化时，HashMap 会自动调整容量到最近的 2 的幂。
```





## 负载因子为什么默认 0.75，调大 / 调小有什么影响？

```js
1. 阈值 = 容量 * 负载因子，达到阈值触发扩容。
2. 0.75 是时间和空间的权衡。
3. 调小：扩容变频繁，占用更多内存；冲突少，查询性能好；
4. 调大：减少扩容，节省内存；桶内元素变多，冲突概率上升，链表 / 树查询变慢
```





## 链表转红黑树阈值为什么是 8，退化阈值为什么是 6，为什么不是 7？

```js
1. 根据泊松分布，hash 足够随机情况下，同一个桶链表达到 8 个元素概率极低。
2. 大于 8，转为红黑树，把 O (n) 查询转为 O (logn)；同时要求数组容量≥64，否则优先扩容，不转树。
3. 退化阈值设置 6，和转换阈值 8 中间留缓冲区间 7，避免频繁链表↔红黑树来回切换，防止震荡消耗性能
```





## JDK1.7 头插法为什么会环形链表？JDK1.8 尾插法解决了什么，HashMap 线程安全吗？

```js
1. JDK7 头插法，扩容迁移链表时，会把新元素插链表头部；多线程同时 resize，链表节点引用会形成环形链表，get 操作死循环 CPU100%。
2. JDK8 改为尾插法，保留原有节点顺序，解决环形链表问题
3. HashMap 依然线程不安全，会出现数据丢失、覆盖等其他并发问题，并发场景推荐 ConcurrentHashMap

为什么推荐ConcurrentHashMap？
1. JDK1.7 ConcurrentHashMap 采用 Segment 分段锁，Segment 继承 ReentrantLock，锁住一段数组，提升并发；开销大，已废弃。
2. JDK1.8 去掉 Segment，底层和 HashMap 一样数组链表红黑树；使用 CAS + synchronized 锁桶头节点，锁粒度细化到单个桶；支持多线程协助扩容 transfer。
```





## resize 扩容的时候，元素是怎么迁移的？需要重新计算 hash 吗？

```js
1. 不需要重新调用 hash ()。
2. 原容量 oldCap 为 2 的幂，扩容后 newCap=2*oldCap
3. 旧桶中元素，新下标只有两种情况：
	3.1 hash & oldCap == 0 → 下标不变，留在原 index
    3.2 hash & oldCap !=0 → 下标 = index + oldCap 直接位运算拆分高低两条链表，提升扩容性能
```





## 如果重写 equals 但是不重写 hashCode，HashMap 会发生什么？

```js
1. 两个逻辑相等对象 equals 返回 true，但 hashCode 不同，会散列到不同桶，put 会存两份，get 无法取出，造成 bug
```





## 除了链地址法，还有哪些哈希冲突解决方案？HashMap 为什么不用？

```js
1. 开放寻址法：冲突向后找下一个空位；ThreadLocalMap 使用；删除需要标记，容易聚集冲突，数据量大性能差，不适合 HashMap
2. 再哈希法：冲突换另一个 hash 函数；实现复杂
3. 链地址法：冲突挂链表；适合数据量大，冲突不均匀场景，就是 HashMap 方案
```
