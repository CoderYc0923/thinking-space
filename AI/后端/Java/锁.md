## Java 各类锁完整梳理（原理 + 别名 + 实现 + 厕所场景举例）

统一场景模型：

公共厕所 = 共享资源；多个排队的人 = 多个线程；蹲位 = 临界区；上锁 = 占用蹲位；释放锁 = 离开蹲位。



## 一、锁分类总览（先理清维度，避免混淆）

锁可以从多个维度划分，不是互斥分类，一把锁可以同时归属多个类别：

1. 悲观锁 / 乐观锁：并发冲突预判策略
2. 排他锁 / 共享锁：能不能多人同时占用资源
3. 可重入锁 / 非可重入锁：持有者能不能再次获得同一把锁
4. 公平锁 / 非公平锁：排队是否严格按照先来后到
5. 自旋锁 / 阻塞锁：拿不到锁是循环尝试还是休眠等待
6. 偏向锁、轻量级锁、重量级锁：synchronized内置锁的三种状态（对象头Mark Word实现）



## 二、详解

1. 悲观锁
   - 原理：默认认为**一定会发生线程竞争冲突**，访问共享资源前先上锁，锁住资源，别人无法访问
   - 实现：synchronized、ReentrantLock（默认悲观）、ReentrantReadWriteLock
   - 举例：
     - 预判厕所资源会争抢，想要使用必须先向管理员申领准入钥匙（上锁）；
     - 持有钥匙期间，按照锁规则限制其他人访问资源
2. 乐观锁
   - 原理：默认认为**冲突很少发生**，不上锁；操作完成时校验资源有没有被别人修改。校验失败则重试。**无阻塞，不锁定资源**
   - 实现：CAS（Compare And Swap）、`AtomicXXX`原子类、数据库版本号机制
     - ⚠️ CAS 是乐观锁底层核心原语，硬件层面指令，无内核上下文切换。
   - 举例：
     - 无需申请钥匙，直接进入区域使用；
     - 全部操作完成后检查，这段时间有没有其他人修改资源。如果发生冲突，放弃本次操作重新尝试。
3. 排他锁（写锁）
   - 原理：同一时刻**只能一个线程持有锁**，其他线程全部阻塞。
   - 实现：synchronized`、`ReentrantLock、ReentrantReadWriteLock.WriteLock
   - 举例：
     - 独立单间厕所，想要使用必须先上锁；
     - 同一时间仅允许一人使用。有人占用时，其他人只能在外等候
4. 共享锁（读锁）
   - 原理：多个线程可以同时持有锁；**读和读不互斥，读和写互斥，写和写互斥**。
   - 实现：ReentrantReadWriteLock.ReadLock
   - 举例：
     - 多人开放式洗手区。**想要洗手必须先申领洗手准入凭证（读锁）**，凭证可同时发放给多人，大家能够同时洗手；
     - 一旦有人申请打扫权限（获取写锁），不再发放新的洗手凭证，并且等待所有拿到凭证的人离开
     - 打扫进行期间，任何人不能洗手。
5. 可重入锁（递归锁）
   - 原理：**同一个线程已经持有锁，能够再次获取同一把锁，不会死锁**；内部记录持有次数，释放必须对应次数。
   - 实现：`synchronized`（隐式可重入）、`ReentrantLock`（显式可重入）
   - 举例：
     - 你拿到单间钥匙进入厕所，隔间内储物间也需要同一把钥匙。你不需要出门归还钥匙，可以再次开锁
     - 离开时需要依次归还两次钥匙，锁才算完全释放。
6. 不可重入锁
   - 原理：持有锁时再次获取直接阻塞 / 死锁。
   - 实现：Java 没有内置实现，需要自己手写。
   - 举例：你持钥匙进入厕所隔间，隔间内储物门需要同一钥匙，但你无法再次开锁，只能先出门归还钥匙，否则卡死。
7. 公平锁
   - 原理：线程按请求锁的先后顺序排队，先到先得，严格 FIFO。
   - 实现：new ReentrantLock(true)
   - 举例：所有人排成一条直线，谁先向管理员申请钥匙，谁优先使用资源，禁止插队。
   - 缺点：频繁切换线程，性能较低。
8. 非公平锁（默认）
   - 原理：线程抢锁不遵守排队顺序；刚释放锁时，新来线程可以直接抢占，允许插队。
   - 实现：`synchronized`、`new ReentrantLock()`（无参构造）
   - 举例：单间厕所门打开，管理员发放钥匙时不严格排队，所有人一起争抢，后来的人有可能抢先拿到钥匙。
   - 优点：减少线程切换，吞吐量更高；
   - 缺点：可能出现线程长时间抢不到（饥饿）。
9. 自旋锁
   - 原理：拿不到锁**不进入阻塞休眠**，循环不断尝试获取锁（空循环）；避免内核态 / 用户态切换开销。适合：锁持有时间很短的场景。
   - 实现：JUC 底层 CAS 手写自旋锁；`synchronized`轻量级锁底层就是自旋；`LockSupport`可自定义
   - 举例：厕所有人占用，你不去休息区等候，持续向管理员反复询问、尝试申领钥匙，不断轮询。
   - 缺点：长时间自旋消耗 CPU。
10. 阻塞锁
    - 原理：获取锁失败，线程进入阻塞队列，放弃 CPU，被操作系统挂起；锁释放后由操作系统唤醒。存在上下文切换开销。
    - 实现：`synchronized`重量级锁、ReentrantLock 阻塞逻辑
    - 举例：厕所有人占用，申领钥匙失败后，到一旁休息区等待；有人归还钥匙后，管理员主动通知你
11. 偏向锁、轻量级锁、重量级锁
    - 重点：这是**内置监视器锁（Monitor）内部优化分层**，只属于 synchronized
    - ✅ **锁升级规则：偏向锁 → 轻量级锁 → 重量级锁，只能升级，不能降级**
    - 偏向锁：
      - 原理：多数场景：**锁长期被同一个线程占用**。第一次线程获取锁，标记线程 ID；后续再次获取不用 CAS，直接放行。没有竞争。
      - 触发条件：无竞争场景
      - 举例：
        - 这个厕所长期只有你一个人使用，管理员记住你的身份，你每次来不用重复申请钥匙；
        - 一旦出现其他人争抢，偏向锁触发升级。
    - 轻量级锁（自旋锁）：
      - 原理：多个线程交替竞争锁，不存在同一时刻并发争抢；依靠**自旋 CAS**获取锁，不向操作系统申请阻塞
      - 触发条件：多个线程交替竞争锁
      - 举例：两个人轮流使用厕所，几乎不会同时到达。有人占用时，另一个人短暂轮询尝试申领钥匙，不会直接进入休息区休眠等待。
    - 重量级锁（监视器锁 Monitor Lock）：
      - 原理：底层依赖 OS 操作系统 Monitor（互斥量）。竞争失败线程直接阻塞，进入内核等待队列。开销最大。
      - 触发条件：当自旋多次抢不到 → 升级重量级锁（synchronized 竞争激烈时自动升级）
      - 举例：大量人群同时争抢厕所，反复轮询没有意义，申领失败的人全部前往休息区休眠等待，依靠操作系统调度唤醒



## 三、AQS（AbstractQueuedSynchronizer）（所有JUC锁底层基础）

1. 原理：双向阻塞队列 + state 状态变量 + CAS；
2. 所有`ReentrantLock`、读写锁、CountDownLatch 底层都是 AQS。
3. 举例：厕所门口维护一条排队队伍（双向链表队列），state 变量标记「蹲位是否被占用」。
