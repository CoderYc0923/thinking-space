- 其实问题归根结底，有几个大类，可能互相影响：
  - 数据库层面的问题
  - 中间件层面的问题
  - 应用层面的问题
  - 特殊场景下的问题
- 表象一般有这几个：
  - 系统进不去、打不开、服务异常
  - 接口卡死、大面积响应超时
  - 接口很慢
  - 大量失败、报错
  - 偶尔卡，比如整点



- 系统进不去、打不开、服务异常，先去看进程状态看看是不是进程没了、反复启动。然后再看报错日志原文写的是什么，比如JVM相关的（OOM、Connection not available、StackOverflow），比如依赖异常（DB、Redis等中间件报错），或者再看看配置（比如是否发版的问题、扩缩容等），按照错误分类对应去解决。
- 接口卡死、大面积响应超时，首先反应是不是哪边被拖死了。先去看CPU状态（高还是低），然后看线程栈特征，有什么问题（在等什么），再看日志中依赖的异常（DB\Redis等中间件）。一般如果：
  - CPU低+jstack线程栈中打印getConnection：倾向于数据库的问题，请求连接慢了。
  - CPU低+jstack线程栈中打印HttpClient：倾向于中间件的问题，网络请求慢了。
  - jstack打印deadlock/死循环：倾向于应用的问题，应该去排查代码或者哪个类有问题。
  - 若是日志直接线程池拒绝/连接打满（OOM、Rejected、Connection not available、StackOverrflow等）可能是数据库等下游拖满了，导致应用层面的报错。
- 接口很慢，先看RT（总 RT ≈ 应用自身 + DB + Redis + HTTP 下游 + 锁等待 + GC 停顿），看是哪部分RT比较慢，对应去看。然后看看GC异常（GC日志+jstat连续看 GC/堆趋势），若FGC狂涨、长停顿、GC清理低效，应该是应用层面问题（内存泄漏/堆小/分配）
- 大量失败报错，看日志原文（OOM、Rejected、Connection not available、Stackflow）、依赖异常（DB\Redis、中间件）。若是依赖超时/连不上，倾向于数据库/中间件，NPE/业务码错误+刚发版：应用问题，RejectedExecution：倾向于应用线程池
- 偶尔卡，比如整点，排查时间规律周期，比如整点任务、大促、发版等，具体问题具体分析。



```bash
# jstack如何手动看

# 1，先看应用PID
jps -l
# 或
ps -ef | grep java

# 2，打印线程栈
jstack <pid>
# 或保存下来看
jstack <pid> > /tmp/jstack_${date + %H%M%S}.txt


# 更现代的写法
jcmd <pid> Thread.print > /trmp/thread.txt

```





- 若是数据库问题：
  - 先从应用侧分析，看应用侧是否正常连接（比如jstack是在getConnection，还是已经连接成功在等DB）
    - 应用日志中`Hikari`的`pool status`的状态（`total active idle waiting`）
    - `jstack`看`jstack <pid> | grep -nE 'HikariPool|getConnection'`是否有大量线程`WAITING`
  - 然后再去数据库侧看
    - 一般先看所有的会话列表`SHOW FULL PROCESSLIST`，看每一列的`Command/Time`，`State/Info`，看执行了多久、执行哪条SQL等，慢的原因是什么，可能是MDL元数据锁、行锁、需要排序、大量扫描数据等
    - 慢SQL分析，看慢SQL日志（用`mysqldumpslow`或`py-query-digest`）和分析执行计划EXPLAIN
      - 关键看这几个字段`type`，`key`，`key_len`，`rows`,`Extra`
        - `type`看类型，`system`系统表最快，`const`主键或唯一键等值匹配，`eq_ref`关联查询主键匹配，`ref`普通索引等值匹配，`range`范围查询，`index`扫索引树，`all`扫全表，最少到`range/ref`
        - `key`看使用到的索引
        - `key_len`看索引使用的长度
        - `rows`看扫描预估行数
        - `extra`中看
          - `Using index`用到了索引，理想
          - `Using filesort`使用文件排序，慢
          - `Using where`服务器层过滤数据
    - 行锁/表锁等待，可能是长事务、热点行问题，长事务可以尝试拆分，热点行读多可以读缓存，写多可以用`redis`串行或原子操作
    - DB死锁，`InnoDB deadlock`，看`SHOW ENGINE INNODB STATUS\G`或`RDS`死锁分析，具体分析
    - 大结果集，比如无分页读取大结果集，打爆应用内存。同时可能会看到`OOM\GC`，最好就是处理下比如分页、流式
    - 库不可用，可能会看到连接不可用，`rejected`，连接上限等，可能是磁盘满了，或者连接数超标等等
- 若是中间件问题：
  - 主要是看日志和线程栈
    - 看日志是否有`grep -E 'timeout|timed out|Redis|Jedis|RocketMQ|Kafka|Feign|OkHttp|UnkonwHost|Connection refused' app.log \ | tail -80`
    - 看`jstack`，先看状态`grep 'java.lang.Thread.State' /tmp/jstack.txt | sort | uniq -c | sort -rn`，再抽几段等待中的栈看看`grep -A 20 'TIMED_WAITING\|WAITING' /tmp/jstack.txt | head -80`
    - 然后看看具体是什么中间件出问题了，再去对应中间件排查
- 若是应用侧问题：
  - `JVM`
    - 先看日志异常（`OOM`，`Rejected`、`StackOverflow`）和`CPU`状态
      - 若是`OOM`，
        - `Java heap space`那就看`hprof+MAT`分析哪个对象或者类的问题，或者本地无界缓存
        - `Metasapce`那就看`jstat -gcmetacapacity`
      - 频繁GC且还是`OOM`，且`CPU`升高，看GC日志和jstat
      - 大对象，RT尖刺后可回落，看看`hprof+MAT`分析哪个对象或者类的问题，顺便看慢SQL
      - 无限等待，`CPU`低，在等锁或者`join`，看`jstack`
      - 死循环，`CPU`高，看`jstack`+被占用的线程分析代码
      - 日志阻塞，`CPU`低，看`jstack`的`BLOCKED`，日志`appender阻塞`
      - 死锁卡死，`CPU`低，看`jstack`的`deadlock`
      - 堆外直接内存（JVM 里 NIO 堆外直接内存（`ByteBuffer.allocateDirect`、Netty 等）占用的那一块），一般看`OOM:Direct buffer memory`，然后一般先调大上限`-XX:MaxDirectMemorySize`，然后排查根因，用 Netty 泄漏检测 / 代码与连接配置 定位
      - RSS问题，一般会出现应用进程因`OOM`被杀掉，如果有监控，可以先分析监控（容器/进程 内存、RSS涨跌）、Direct / 堆外（有的话）情况，分析。
      - 栈溢出，`StackOverflow`
      - 等连接卡死，`jstack`大量线程`WAITING`
      - 线程池打满/拒绝，`jstack`信息+线程池状态
- 偶发和特殊场景：
  - 比如定点任务
    - 整点定时任务，把`CPU/DB`打满
    - GC规律性停顿
  - 秒杀等大促
    - 大量并发把线程连接打满，或者直接打库触发行锁、表锁
    - 看是否提前预热，限流降级策略
  - 缓存雪崩等
    - 缓存雪崩：大批量缓存一起失效，可以通过TTL加随机值打散过期时间分布，或者多级缓存、`Redis`高可用方案等
    - 缓存击穿：某个热点`key`过期瞬间大量并发，可以让热点`key`永不过期的方案
    - 缓存穿透：访问没有缓存的数据，导致直接打库，可以通过缓存空值TTL、布隆过滤器拦截非法`key`、参数校验
  - 发版问题
    - 配置问题，比如地址、超时等
    - 扩缩容等
