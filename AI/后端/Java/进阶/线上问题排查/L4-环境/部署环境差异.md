# L4：部署环境差异（同一结论，不同入口）

> 工具思想相同（栈 / GC / SQL / 依赖），**怎么拿到证据**不同。  
> 先完成 **L1 用户表象（U\*）→ L2 信号（S-\*）→ L3 模块**，再来本节换命令。

---

## 1. 总对照

| 能力 | 单机 VM | 多机集群 | K8s / ACK | 阿里云常用 |
|------|---------|----------|-----------|------------|
| 找坏实例 | 本机即是 | 网关/注册中心按实例错误率 | 按 Pod 错误率、Restart | SLB + ARMS 按实例 |
| 日志 | 文件 / journal | 集中日志 or 逐台 | `kubectl logs` / SLS | SLS |
| 线程栈 | SSH + jstack | SSH 坏机 | exec / 诊断容器 / ARMS | ARMS 线程 + exec |
| GC | gc.log / jstat | 同左 | 日志卷 + 监控 | ARMS JVM + gc.log |
| dump | 本地盘 | 注意磁盘 | **必须落到 volume** | 同 K8s/ECS |
| DB | 自建 CLI | 同左 | 应用与 RDS 分离 | RDS 控制台 |
| 内存被杀 | dmesg | 同左 | OOMKilled + limit | 事件 + 云监控 |
| 第一现场 | SSH | 监控定位实例 | 监控 + kubectl | **ARMS/云监控优先** |

## 2. 单机 / 传统 VM

```bash
PID=$(pgrep -f 'application.jar' | head -1)
ps -eo pid,etime,pcpu,pmem,rss,cmd | grep "$PID"

jstat -gcutil "$PID" 1000
jstack "$PID" > /tmp/jstack-1.txt
sleep 15
jstack "$PID" > /tmp/jstack-2.txt

# dump 前确认磁盘；高峰慎用
# jcmd "$PID" GC.heap_dump /data/dump/heap.hprof

dmesg -T | grep -iE 'oom|killed' | tail
df -h
```

## 3. 多机集群（非 K8s）

1. **先定位坏实例**（错误率、RT、连接数按 IP 拆）  
2. 只登坏机做 jstack/jstat  
3. 若**所有实例一起坏** → 优先全局依赖（DB/Redis/下游），不要先怀疑单机代码

## 4. Kubernetes / ACK

### 4.1 编排层（先做）

```bash
kubectl get pod -n <ns> -o wide
kubectl describe pod <pod> -n <ns>
# 重点：Restart Count、Last State=OOMKilled、Events（FailedScheduling、Evicted…）

kubectl logs <pod> -n <ns> --tail=200
kubectl logs <pod> -n <ns> --previous   # 上次崩溃日志

kubectl top pod -n <ns>                 # 需 metrics-server
```

### 4.2 进程内诊断

```bash
# 镜像里有 JDK 工具时（PID 在容器内常为 1）
kubectl exec -it <pod> -n <ns> -- jstack 1
kubectl exec -it <pod> -n <ns> -- jstat -gcutil 1 1000

# 没有 jstack：看业务/GC 日志；或用公司规范的 debug/ephemeral 容器
# attach 失败时的兜底：向 JVM 发 SIGQUIT，线程栈打到标准输出 → kubectl logs 可见
kubectl exec -it <pod> -n <ns> -- kill -3 1
```

### 4.3 内存：两套账

| 现象 | 含义 |
|------|------|
| 日志 `OutOfMemoryError: Java heap space` | 堆上限到了 |
| Pod `OOMKilled`、Exit 137，无 Java OOM | **cgroup limit** 到了（含堆外、元空间、线程栈等） |

```text
容器 memory limit
  ≥ -Xmx + MaxMetaspaceSize + MaxDirectMemorySize + 线程栈余量 + JVM/直接开销
```

Heap dump 必须写到 **volume**（写容器可写层会加重内存并随 Pod 消失）。

### 4.4 建议常备 JVM 参数（容器）

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump/java.hprof
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=50M
-XX:MaxMetaspaceSize=256m
-XX:MaxDirectMemorySize=512m
# 视 JDK：-XX:+UseContainerSupport（现代 JDK 默认更好识别 cgroup）
```

## 5. 阿里云常见组合（建议顺序）

```text
① 云监控 / ARMS：哪台实例、哪个接口、依赖谁慢
② SLS：OutOfMemoryError / timed out / Connection is not available
③ 坏 ECS/Pod：jstack 或 ARMS 线程剖析
④ RDS：慢日志、会话、锁分析
⑤ Redis / MQ：慢日志、大 key、堆积
⑥ 需要时再 dump（低峰或抽一台）
```

| 产品 | 排查入口 |
|------|----------|
| ECS | 云监控；SSH 同单机 |
| ACK | 容器监控 + kubectl + SLS |
| RDS MySQL | 慢日志、会话管理、锁/死锁分析、自治 |
| Redis | 监控、慢日志、大 key |
| RocketMQ 等 | 堆积、死信、实例监控 |
| ARMS | 应用 RT、JVM、线程、链路（很多公司第一现场） |
| SLS | 关键字与时间线 |

## 6. 本机练习 ↔ 线上

| 本机（jvm排查） | 线上 |
|-----------------|------|
| `.\run-usecase.ps1 Case` | 真实进程 / 预发复现 |
| `& "$jdk\jstat.exe" …` | `jstat -gcutil …` |
| `& "$jdk\jstack.exe" …` | `jstack` / `jcmd Thread.print` / ARMS |
| 任务管理器句柄 | `lsof`、`/proc/pid/fd` |

练习练的是**工具肌肉**；线上第一现场往往是 **ARMS/Grafana + 日志**。

---

## 7. 安全与规范

- dump 含业务数据：按公司规范存储与脱敏  
- 高峰优先：日志、指标、jstack；全量 heap dump 要评估停顿  
- 不要对所有实例同时打 dump  
- 变更（扩池、加 -Xmx、回滚）走变更/审批，留时间线

## 8. 一张「换环境」速查

| 你判断的结论 | 单机 | K8s | 阿里云 |
|--------------|------|-----|--------|
| 等 DB 连接 | jstack + SHOW PROCESSLIST | Pod jstack + RDS 会话 | ARMS + RDS 控制台 |
| GC thrashing | gc.log + jstat | 日志卷 gc.log + 监控 | ARMS JVM + SLS |
| OOMKilled | dmesg | describe pod | 事件 + 容器监控 |
| 下游拖死 | jstack 搜 HttpClient | 同左 + 下游 ARMS | 链路追踪 |
| 发版导致 | 发版记录 | ReplicaSet/镜像 tag | 发布单 + 按实例错误率 |
