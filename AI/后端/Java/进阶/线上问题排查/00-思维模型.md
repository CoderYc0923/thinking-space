# 思维模型：层级怎么分、脑子怎么走

## 1. 四层定义（必须分清）

| 层 | 问题 | 谁在说话 | 例子 |
|----|------|----------|------|
| **L1 用户表象** | 业务/用户先感知到什么？ | 用户、客服、业务方、（监控上的）可用性/错误率告警 | 「打不开」「一直转圈」「整体变慢」「大量失败」「只有整点卡」 |
| **L2 初查信号** | 我们打开监控/登机器后看到什么？ | 你自己 / Oncall | CPU 高、OOMKilled、磁盘满、FGC、栈堵在 getConnection、刚发版 |
| **L3 模块** | 根因更可能落在哪一类？ | 结论层 | 应用 JVM / 数据库 / 中间件 / 偶发触发器 |
| **L4 环境** | 在这种部署里命令从哪进？ | 平台差异 | 单机 SSH / K8s / 阿里云 ARMS |

**常见错误**：把 L2 信号（CPU 打满、写不了日志）当成 L1 表象——那是排查中途看到的，不是用户第一句话。

补充：监控先报「错误率飙升 / 探活失败」，业务还没投诉——仍算 **L1**（服务对外已经坏了），不是 L2。

---

## 2. 四步不许跳

```text
① L1 用用户话术归类（U1～U5）
② L2 采信号、填表（S-*），得到倾向模块
③ L3 进模块查子问题与命令
④ L4 按单机/K8s/云换入口
```

---

## 3. 五条铁律

1. **表象 ≠ 根因**；信号 ≠ 根因。  
2. **先箱子与依赖，再 JVM 细节**（Box → 依赖 → Threads → GC → Heap）。  
3. **卡住看栈，变慢拆 RT，内存分清谁涨**（堆 / Metaspace / Direct / 容器杀）。  
4. **同表象可以是一条链**，只修最后一环会复发。  
5. **先收证据再解释**。

---

## 4. 高频因果链

```text
慢 SQL / 行锁 → 连接占满 → getConnection 等待 → 线程池打满 → 用户侧「大面积超时」
无界缓存 / 大结果集 → 堆涨 → Full GC → 用户侧「周期性变慢/超时」
下游无超时 → 线程占满 → CPU 低 → 用户侧「卡死」，根因在下游
```
