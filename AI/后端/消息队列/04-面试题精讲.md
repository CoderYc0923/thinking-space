> 下列按频次分组，可直接当口述提纲。

## A. 基础与场景

### A1. 为什么用消息队列？有什么缺点？

**答**：解耦、异步、削峰；缺点是架构变复杂、最终一致、重复/乱序要业务处理、运维与排查成本上升。  
不是所有地方都上 MQ——主链路强一致、极简系统可以不上。

- 为了上下游解耦，异步处理，也可以流量削峰
- 缺点是架构变复杂、结果最终一致，可能有延迟。同时还要处理消息重重复/乱序问题，运维和排查成本上升。

### A2. 如何保证消息不丢失？

分三段讲：

1. **生产**：同步发送并判断结果；失败重试/落库补发  
2. **Broker**：持久化 + 合理刷盘；多副本；磁盘监控  
3. **消费**：处理成功再 ACK；失败重试；防先 ACK 后处理  

结合项目说你用的是同步发送还是事务消息/本地消息表。

- 生产者同步发送并判断结果；失败重试/落库补发
- Broker做持久化+合理刷盘（同步/异步）；磁盘监控预警；Broker多实例拷贝副本（主从同步、`Raft/DLedger`等）
  - `Raft`是一种分布式共识算法，也就是多台机器要对【日志/数据】达成一致时用的算法，用来解决谁当`Leader`、日志怎么复制到多数节点才算提交、主挂了怎么自动选新主
  - `DLedger`是`RocketMQ`把`Raft`用在`Broker`提交日志上的实现（`CommitLog`多副本），将一组`Broker`用`Raft`选主、多数派落盘，切换更自动

- 消费者处理成功之后再`ACK`，防止先`ACK`后处理；失败重试

### A3. 如何保证消息不被重复消费？

MQ 多为 **至少一次** → 必然可能重复。  
手段：业务唯一键、去重表、Redis SETNX、状态机、天然幂等写入。  
强调：**去重键用业务主键，不要只靠 MQ 的 MsgId（重发可能变）。**

- MQ多为**至少一次**，它虽然可以保证消息不丢，但是可能会消息重复。所以一般用**幂等**来保证消息的不重复。
  - 比如**业务唯一键**、**去重表**、**`Redis SETNX`**、**状态机**、**天然幂等（覆盖写）**


### A4. 如何保证顺序？

**口述版：**

严格说，消息队列很难廉价地做到「整个 Topic 全局有序」，因为全局有序往往意味着只剩一个队列、吞吐上不去，一般不这么用。

业务上真正要的大多是**局部有序**：比如同一个订单号的创建、支付、取消必须按顺序。做法是三件事一起做——生产时用订单号这类业务 key 做哈希，保证同一 key 始终进同一个队列/分区；Broker 上单分区本身是先进先出；消费端开顺序消费、单线程处理这个分区，不能用并发消费，否则同一分区里多条消息并行处理还是会乱序。

代价是：单分区单线程，一条消息卡住会堵住后面；热点 key 打到同一分区也会成为瓶颈，所以不是所有场景都上顺序消息，能接受乱序的就用并发消费更划算。

**要点备忘：**

- 全局有序代价大（单队列）→ 少用  
- 局部有序：同一 key → 同一分区 + 顺序消费  
- 并发消费会破坏顺序；注意热点 key 与慢消息堵塞 



- 消息队列一般不是全局有序，因为全局有序的代价比较大，因为意味着只剩一个队列，吞吐上不去
- 业务上往往是局部有序，比如同一个订单号的创建、支付、取消必须按顺序。一般是生产者用订单号这类业务key做哈希，保证同一key始终进同一队列/分区；Broker上单分区内本身就是先进先出；消费者开顺序消费、单线程处理这个分区，不能用并发消费，不然还是有可能会乱序。不过代价是单分区内单线程，如果有慢消息或者热点key，后面会堵住。
  - 比如同一订单里【支付】那条调外部接口卡了，后面的操作也会被堵住
  - 如果大促时大量消息按同一个热门店铺ID进同一分区，这个分区就会很长。

### A5. 消息积压怎么处理？

先讲清：**积压靠扩容/提速/止血，不是靠「补偿」**；补偿是业务不一致时的补单/对账。

再看是预期削峰还是故障：

1. 扩容消费者（到分区数上限）  
2. 优化消费/下游  
3. 修复毒消息/死信，避免重试风暴  
4. 紧急：临时 Topic 分流、丢弃非关键、修复后追赶  

细节见 [03-实操与生产经验 · 堆积](./03-实操与生产经验.md#五堆积怎么判断怎么处置)。



- 消息积压一般先看是消息太多，消费者来不及处理还是消费者异常卡死。
- 如果是消息太多，消费者来不及处理，那就先将消费者增加到分区上限，必要时再加分区
- 如果是消费者异常卡死，先看日志定性，对应处理。可能是慢SQL、下游超时、线程打满、坏消息疯狂重试占位。
- 后续需要对应做异常监控告警，比如消息堆积量、消费延迟持续超阈值等、重试次数设置等措施。或者大促前压测、预扩容等。
- 如果积压期间业务已经错乱，要再做补偿、对账、死信重放等善后措施。

## B. 投递语义与事务

### B1. 三种投递语义？

At most once / At least once / Exactly once。  
生产常见：至少一次 + 幂等 ≈ 业务上的恰好一次。

- 最多一次：会丢、会重复
- 至少一次：不丢，会重复
- 刚好一次：不丢、不重复
- 生产一般是至少一次+幂等

### B2. 发消息和写库怎么保证一致？

**口述版：**

这个问题本质是两个操作不在同一个事务里：写库和发 MQ。你如果先写库再发消息，库成功了消息却失败，下游就收不到；如果先发消息再写库，消息出去了库却回滚，下游又会拿到脏数据。所以不能靠「谁先谁后碰运气」。

常见有几条路。一是本地消息表：和业务写库放在同一个本地事务里，多插一条「待发送」记录，事务提交后再异步把消息投出去，投成功就改状态，失败就重试扫表，这样至少保证「库有了就最终能发出去」。二是用 RocketMQ 事务消息：先发一条半消息，下游暂时看不见，再执行本地事务，成功就提交半消息、失败就回滚，如果迟迟没结果 Broker 还会回查生产者，问本地事务到底成没成。三是 Outbox 加 CDC：业务只写库和 Outbox 表，由 Canal 之类去扫 binlog 再转成 MQ，应用自己不用双写。支付这类也可以最大努力通知，多次回调，最后靠对账兜底。

落地时我们一般按场景选：强一致、用 RocketMQ 就上事务消息；不想绑死某一款 MQ 就用本地消息表或 Outbox。不管哪种，消费侧还是要幂等，因为消息仍可能重复。

**要点备忘：**

- 两难：先写后发可能丢消息；先发后写可能脏消息  
- 方案：本地消息表 / 事务消息 / Outbox+CDC / 最大努力通知+对账  
- 能画半消息时序加分；消费侧仍要幂等



- 写库和发MQ不在同一个事务里会出现不一致的问题：先写库再发消息，库成功了消息可能失败，下游收不到；先发消息再写库，消息出去了库却回滚了，下游拿到脏数据。
- 可以做本地消息表，和业务写库同一个本地事务，多插一条待发送记录，提交后再异步投递，失败就扫表重试，保证库有了最终一定发的出去
- 另外，RocketMQ原生事务消息，先发半消息，再跑本地事务，成功就提交、失败就回滚；没结果时Broker还会回查生产者
- Outbox+CDC：业务只写库，用Canal扫binlog再转成MQ。
- 支付业务的话也可以通过最大努力通知，多次回调，最后对账兜底

### B3. RocketMQ 事务消息原理？（深挖向）

**口述版：**

RocketMQ 事务消息要解决的就是「本地写库」和「消息对下游可见」尽量绑定在一起。流程可以想成四步。

第一步，生产者先发一条半消息到 Broker。半消息已经落在 Broker 上了，但对消费者不可见，所以这时候下游还不会去消费。第二步，生产者执行本地事务，比如写入订单。第三步，本地事务成功，就向 Broker 提交这条半消息，消息变成可投递，消费者才能收到；本地事务失败，就回滚半消息，等于这条消息作废，下游永远看不到。

还有一种情况：提交或回滚的结果没能及时告诉 Broker，比如进程重启了。这时 Broker 会主动回查生产者，问你：这条半消息对应的本地事务到底成功了没有？所以生产者必须实现回查接口，根据订单号之类去查库，再回答提交或回滚。没有回查，半消息可能一直挂着。

要注意，事务消息比普通消息多了半消息和回查，网络交互更多，吞吐会低一截，不适合超高 TPS 的打点类场景；适合下单、支付这种必须和本地事务对齐的链路。消费侧仍然要做幂等，因为提交之后还是至少一次投递。

**要点备忘：**

1. 发半消息（下游不可见）  
2. 执行本地事务  
3. 成功提交 / 失败回滚  
4. 无最终结果 → Broker 回查生产者（必须实现）  
5. 吞吐低于普通消息；消费侧仍要幂等



- 先发一条半消息到Broker，消息已经存了但是消费者看不到。然后执行本地事务，比如写订单。本地成功就提交半消息，下游才能消费；本地失败就回滚半消息，下游收不到。
- 如果提交/回滚的结果没有及时告诉Broker，比如进程重启了，Broker会回查生产者：这条半消息对应的本地事务成功了吗？所以必须实现回查，按订单号查库再回答提交或回滚，不然半消息可能会一直挂着
- 事务消息比普通消息多半消息和回查，吞吐更低，适合下单支付这类要对齐的场景。不适合超高TPS类场景。

## C. 对比选型

### C1. Kafka vs RocketMQ vs RabbitMQ？

| 问法 | 抓手 |
|------|------|
| 吞吐/日志 | Kafka |
| 事务/延时/业务重试 | RocketMQ |
| 路由灵活/多语言/中等流量 | RabbitMQ |

补一句：可并存（数据面 Kafka，业务面 RocketMQ）。

### C2. Kafka 为什么快？

**口述版：**

Kafka 快，首先是因为它把消息当成追加写的日志，而不是在磁盘上随机改来改去。顺序写磁盘接近内存的量级，比随机写高效得多。写的时候还会先落在操作系统页缓存里，读的时候也经常直接命中缓存，减少真磁盘 I/O。

其次是批量和并行。生产者可以批量发送，消费者可以批量拉取，摊薄了网络和系统调用开销；Topic 拆成多个分区，多个生产者、消费者可以并行打不同分区，吞吐横向加。

再往下可以说零拷贝：消费时数据从页缓存经 sendfile 一类机制往网络发，少几次用户态和内核态之间的拷贝，发送路径更短。

面试里抓住三句话就够：日志型顺序写、页缓存加批量、分区并行；有余力再补零拷贝。它适合高吞吐的日志和流式场景，业务上要事务消息、丰富延时重试时，不一定比 RocketMQ 更合适。

**要点备忘：**

- 日志型存储 + 顺序 I/O  
- 页缓存、批量发送/拉取  
- 分区并行；零拷贝（sendfile）加分  
- 快 ≠ 所有业务场景都该选它



- 日志型存储+顺序IO，页缓存加批量发送拉取，分区并行，零拷贝
- 因为它是顺序写磁盘，把消息当追加写的日志，不是随机IO，效率高，而且走操作系统页缓存，读写经常不用每次打到真磁盘上
- 其次它的批量和并行，生产者可以批量发、消费者也可以批量拉，减少网络和系统调用开销。`Topic`拆分成多个区，多生产者、多消费者可以并行打不同分区，吞吐强
- 然后它发送给消费者的数据从磁盘/页缓存经`sendfile`类机制发送到网络再到消费者，其中，从磁盘到网络路径中少几次用户态和内核态的拷贝，路径变短了

### C3. Kafka 消费者 Rebalance 是什么？有什么影响？

**口述版：**

Rebalance 就是同一个消费组里，重新瓜分 Topic 分区的过程。比如组里新加了一个消费者实例、有实例挂了或扩缩容、订阅的 Topic 分区变了，Kafka 都要重新算：哪个实例负责哪些分区。

影响主要有三点。一是 Rebalance 期间，相关分区往往会暂停消费，消息会短暂积一下，表现为消费延迟。二是分区换手之后，新的消费者可能从上次提交的位点接着读，如果旧实例处理到一半还没提交 offset，就可能重复消费，所以业务还是要幂等。三是如果消费者频繁进出组，比如进程不稳、超时被踢，就会反复 Rebalance，吞吐抖、延迟抖，线上比较烦。

优化上可以说：尽量避免消费者频繁上下线；`max.poll.interval` 和一次拉取处理时间配合理，别处理太久被当成挂了；分配策略可以用 sticky / 协作式再均衡，减少分区不必要的大挪移。一句话：Rebalance 是组内重新分活，必要但有代价，要减少无意义的反复均衡。

**要点备忘：**

- 触发：加减实例、宕机、分区变化等  
- 影响：短暂停消费、可能重复、频繁则抖动  
- 优化：少折腾成员、合理 poll 超时、sticky/协作式分配



- `Rebalance`是同一个消费组里，重新瓜分Topic分区的过程。比如组里消费者实例变动、扩缩容，订阅的Topic分区变了，`Kafka`都要重算
- `Rebalance`的影响
  - 相关分区会暂停消费，消息短暂积压一下，可能会消费延迟
  - 新的消费者会从上次提交的位点接着读，如果旧消费者处理到一般还未提交`offset`，可能会重复消费，幂等解决
  - 如果消费者频繁进出组，比如进程不稳定、超时被踢，就会反复`Rebalance`，吞吐、延迟都会抖动
- 优化：
  - 尽量避免消费者频繁上下限
  - `mxa.poll.interval`和一次拉取处理事件配置合理，别处理太久超时被挂
  - 分配策略可以用`sticky`/协作式再均衡，减少分区不必要的大挪移。

## D. 架构概念

### D1. Topic 和 Queue/Partition 关系？

**口述版：**

Topic 是逻辑上的分类通道，比如「订单已支付」，生产者和消费者靠 Topic 名字对上号。真正存消息、真正能并行的，是 Topic 下面的 Queue 或 Partition——Kafka 叫分区，RocketMQ 叫队列，意思差不多。

可以想成：Topic 是一条业务主题，下面拆成多条管道。消息会落到其中某条管道里；同一消费组里的多个消费者实例，就是来瓜分这些管道的，一个分区同一时刻只分给组内一个实例。所以组内并行度上限大约等于分区数，消费者开得比分区还多，多出来的会闲着。不同消费组互不影响，可以各自再读同一批分区。

一句话：Topic 管「是什么消息」，Queue/Partition 管「怎么存、怎么并行」。

**要点备忘：**

- Topic = 逻辑分类；Queue/Partition = 存储与并行单元  
- 组内：一分区一人；并行度 ≤ 分区数  
- 组间：可各读同一分区  



- `Topic`是逻辑上的分类通道，生产者和消费者都靠`Topic`名字对号
- `Queue`/`Parttion`是`Topic`下存储与并行的单元
- `Topic`是一条业务主题，下面拆成多条管道`Queue/Partition`。消息会落到其中某条管道里；同一消费组中的多个消费者实例会瓜分这些管道进行订阅，一个分区同一时刻只分给组内一个实例。所以组内并行度上线大约等于分区数，消费者多于分区数就会出现空闲消费者。不同消费组互不影响，可以各自读同一批分区

### D2. 推拉模式？

**口述版：**

推模式是 Broker 主动把消息推给消费者，延迟可以很低，但消费者来不及处理时背压不好做。拉模式是消费者主动来取，节奏自己控，但可能空拉。实际很多 MQ 用长轮询：还是消费者发起拉，Broker 若暂时没消息就挂起一会儿，有消息再返回，这样既不太空转，延迟也还行。所以线上常见不是纯推或纯拉，而是可调节的拉取加长轮询。

**要点备忘：** Push / Pull / 长轮询兼顾节奏与延迟。



- 推模式是Broker主动将消息推送给消费者，延迟低，但是消费者可能来不及处理
- 拉模式是消费者主动拉取消息，节奏由消费者控制。
- 一般MQ用长轮询让消费者主动拉取消息，可以兼顾节奏和延迟。

### D3. 广播消费 vs 集群消费？

**口述版：**

集群消费是默认模型：同一个消费组里，一条消息只被组内一个实例处理，多个实例是分摊分区、一起扛量。广播消费则是组里每个实例都收到同一条，比如本地缓存都要刷新时会用。广播会把流量放大到实例数倍，也更难做位点管理，所以要慎用，多数业务异步都是集群消费。

**要点备忘：** 集群 = 组内一人处理；广播 = 组内每人一份，慎用。



- 集群是消费组一人处理，广播是消费组每人一份
- MQ一般默认集群消费，就是同一消费组里，一条消息只被组内一个实例处理，多实例是分摊分区的。
- 广播消费是组里每个实例都收到同一条，比如本地缓存都要刷新时用。

### D4. 死信队列是什么？

**口述版：**

死信队列就是专门收「怎么重试都处理不好」的消息的地方。消费失败后 MQ 一般会重试，重试次数打满还是失败，就把消息转到死信队列，比如 RocketMQ 里常见是 `%DLQ%消费组名`，避免一条坏消息无限重试，把后面的消息堵住。

它不是垃圾桶：死信一有增长就要告警，再人工看是数据问题还是下游故障，修好后重放或做补偿。如果业务上已经能判断是毒消息，也可以别空转重试十几次，记日志后写入业务死信或旁路，再 ACK 掉，效果类似，都是把坏消息隔离出去。

一句话：死信队列用来隔离反复失败的消息，必须配套监控和处置，不能当黑洞。

**要点备忘：**

- 多次失败 → 转入 DLQ，避免堵分区  
- 要告警、重放/补偿，不能当垃圾桶  
- 明确毒消息可快速隔离，不必空耗满重试



- 死信队列是用来隔离反复失败的消息的，比如RocketMQ中常见的`%DLQ%消费组名`。必须配套监控和处置

## E. 场景设计题

### E1. 设计一个秒杀/下单异步扣库存

要点：

- 下单/资格校验后发 MQ 削峰  
- 库存预扣可用 Redis 原子操作，异步落库  
- 超时未支付延迟消息关单  
- 全程幂等（订单号）  
- 堆积监控与降级  



- 首先秒杀/下单业务需要考虑流量大的问题，一般MQ用RocketMQ
- 先用Redis预热库存并用Lua脚本原子扣减，抗住尖峰，然后Redis扣减后通过MQ削峰，异步落库，同时考虑落库失败库存补偿
- 同时下单成功时，发送一条延迟消息，到点检查超时未支付的情况，未支付就关单并释放库存
- 全程用订单号幂等，防止重复消费、重复扣减\建单
- 同时需要监控消息MQ消息堆积与降级处理。

### E2. 缓存与 DB 一致性能不能靠 MQ？

**口述版：**

可以靠 MQ 做辅助，但 MQ 解决不了「强一致」，只能做成最终一致。常见做法是改完 DB 之后发一条变更消息，消费者去删缓存或更新搜索；比应用里同时写 DB 又写缓存更清晰，也少一点双写失败各写一半的问题。更稳的还可以写 Outbox，用 Canal 扫 binlog 再发 MQ，避免业务代码里双写。

但消息会重复、会乱序、会延迟，所以消费侧还要幂等，更新缓存最好带版本号或更新时间，乱序的旧消息不能覆盖新数据；很多时候「删缓存」比「更新缓存」更安全，下次读再回源 DB。另外还有 Cache Aside、延迟双删这些经典手法，和 MQ 可以配合，不是互斥。

一句话：能靠 MQ 做异步失效/同步到缓存，是最终一致；要接受短暂脏读，并把重复和乱序处理掉。

**要点备忘：**

- 可以：DB 变更 → MQ → 删/更新缓存（或 CDC）  
- 最终一致；处理重复、乱序、延迟  
- 删缓存往往优于直接更新；可配合 Cache Aside / 延迟双删



- MQ解决不了强一致，只能做到最终一致
- 常见做法是改完DB后发一条变更消息，消费者去更新缓存。比应用里同时写DB又写缓存更清晰，也少一点双写失败或各写一半的问题，还有就是可以写Outbox，用Canal扫binlog再发MQ，避免业务代码里双写。
- 但是消息会重复、乱序、延迟，所以消费侧要做好幂等，所以删缓存比更新缓存更安全，更新缓存容易脏数据，更新缓存的话最好带版本号或者更新时间，避免乱序的旧消息覆盖新消息。
- 另外还有`Cache Aside`旁路缓存、延迟双删这类经典手法
  - 旁路缓存：应用自己管缓存，缓存不写数据库
    - 读：先读缓存，命中直接返回，未命中读DB再写入缓存再返回
    - 写：先更新DB，再删除缓存
  - 延迟双删：为了补旁路缓存的并发下的一个问题，线程A删缓存、写DB中，此时线程B读缓存未命中，去读旧DB，写回旧值到缓存，然后线程A写DB完成，缓存里是脏数据
    - 延迟双删也就是先删一次缓存，跟新DB，然后过一段时间比如500毫秒，再删一次缓存。这样只能降低脏数据概率，延迟多久要结合业务读写耗时来估算。

### E3. 如何做消息的链路排查？

**口述版：**

用户说「操作了但没生效」，就按发送 → Broker → 消费 → 死信这条链查，关键是同一个业务键或 MsgId 串起来。

先看生产日志：有没有发送成功、返回的 MsgId 是什么、业务单号是什么。没有发送成功就是生产侧或网络问题。发送成功了，就到 Broker 控制台按 Topic、MsgId 或消息轨迹看消息在不在、有没有被哪个消费组拉走。然后再用同一个 MsgId 或订单号搜消费日志：是没收到、收到后业务失败、还是被幂等挡掉了。如果重试多次，还要看有没有进死信队列。

有 ARMS、SkyWalking 的话，把 MsgId、订单号打进 Trace，从一次用户请求就能点到后面的发消息和消费 span，会快很多。平时规范是：生产、消费日志都强制带 MsgId 加业务主键，环境、消费组别搞混。

**要点备忘：**

- 生产日志（MsgId/业务键）→ Broker 轨迹 → 消费日志 → 死信  
- Trace 串联更快；日志规范是前提



- 先摸清消息的链路顺序：发送 - Broker - 消费 - 死信
- 用户说操作了没生效，先看生产日志看是否发送成功，返回的MsgID是什么、业务单号是什么。
- 没有发送成功就是生产侧或网络问题
- 若发送成功了，就去Broker控制台按`Topic`、MsgID或消息轨迹看消息在不在，被哪个消费组拉走了。然后再用同一个MsgID或订单号搜消费日志，看是没收到、收到后业务失败还是被幂等挡掉了。
- 如果重试多次还要看有没有进死信队列
- 有`ARMS、SkyWalking`的话，把MsgID、订单号打进Trace，从一次用户请求就能点到后面的发消息和消费span。
- 平时规范要让生产、消费日志都带上MsgID+业务主键，同时环境、消费组别搞混

## F. 陷阱题（简答）

| 题 | 要点 |
|----|------|
| MQ 能保证Exactly once吗？ | 裸 MQ 几乎不；靠幂等或事务能力近似 |
| 消费者越多越快吗？ | 受分区数限制 |
| 堆积了会丢吗？ | 正常持久化不丢；磁盘满/过期删除策略会 |
| 顺序消息失败一条？ | 可能堵住后续，要快速失败或隔离 |
| 改 ConsumerGroup 名？ | 当新消费者，位点行为变化，可能漏或重放 |
