# 04 · 消息队列面试题精讲

> 答法结构：**结论 → 原理/对比 → 落地怎么做 → 踩过的坑（有则加分）**。  
> 下列按频次分组，可直接当口述提纲。

---

## A. 基础与场景

### A1. 为什么用消息队列？有什么缺点？

**答**：解耦、异步、削峰；缺点是架构变复杂、最终一致、重复/乱序要业务处理、运维与排查成本上升。  
不是所有地方都上 MQ——主链路强一致、极简系统可以不上。

### A2. 如何保证消息不丢失？

分三段讲：

1. **生产**：同步发送并判断结果；失败重试/落库补发  
2. **Broker**：持久化 + 合理刷盘；多副本；磁盘监控  
3. **消费**：处理成功再 ACK；失败重试；防先 ACK 后处理  

结合项目说你用的是同步发送还是事务消息/本地消息表。

### A3. 如何保证消息不被重复消费？

MQ 多为 **至少一次** → 必然可能重复。  
手段：业务唯一键、去重表、Redis SETNX、状态机、天然幂等写入。  
强调：**去重键用业务主键，不要只靠 MQ 的 MsgId（重发可能变）。**

### A4. 如何保证顺序？

- 全局有序代价大（单队列）  
- 业务上 **局部有序**：同一 key 进同一分区 + 顺序消费  
- 说明并发消费会破坏顺序，以及热点 key 的性能问题  

### A5. 消息积压怎么处理？

先讲清：**积压靠扩容/提速/止血，不是靠「补偿」**；补偿是业务不一致时的补单/对账。

再看是预期削峰还是故障：

1. 扩容消费者（到分区数上限）  
2. 优化消费/下游  
3. 修复毒消息/死信，避免重试风暴  
4. 紧急：临时 Topic 分流、丢弃非关键、修复后追赶  

细节见 [03-实操与生产经验 · 堆积](./03-实操与生产经验.md#五堆积怎么判断怎么处置)。

## B. 投递语义与事务

### B1. 三种投递语义？

At most once / At least once / Exactly once。  
生产常见：至少一次 + 幂等 ≈ 业务上的恰好一次。

### B2. 发消息和写库怎么保证一致？

说明两难（先发后写 / 先写后发都会出问题），然后答方案：

- 本地消息表  
- RocketMQ 事务消息（半消息 + 本地事务 + 回查）  
- Outbox + CDC  
- 最大努力通知 + 对账  

能画半消息时序图加分。

### B3. RocketMQ 事务消息原理？（深挖向）

1. 发半消息，Broker 对下游不可见  
2. 执行本地事务  
3. 提交/回滚半消息  
4. 若无最终结果，Broker 回查生产者  

注意：吞吐低于普通消息；回查必须实现。

## C. 对比选型

### C1. Kafka vs RocketMQ vs RabbitMQ？

| 问法 | 抓手 |
|------|------|
| 吞吐/日志 | Kafka |
| 事务/延时/业务重试 | RocketMQ |
| 路由灵活/多语言/中等流量 | RabbitMQ |

补一句：可并存（数据面 Kafka，业务面 RocketMQ）。

### C2. Kafka 为什么快？

顺序写磁盘、页缓存、批量发送/拉取、分区并行、零拷贝（sendfile）等。  
不必背细节，说出「日志型存储 + 顺序 I/O + 批量」即可。

### C3. Kafka 消费者 Rebalance 是什么？有什么影响？

组内成员变化时重新分配分区；期间可能停止消费、造成重复或短暂延迟。  
优化：减少频繁上下线、合理 `max.poll`、协作式 sticky 分配等（点到即可）。

## D. 架构概念

### D1. Topic 和 Queue/Partition 关系？

Topic 逻辑分类；Queue/Partition 是存储与并行单元。  
消费者并行度 ≤ 分区数。

### D2. 推拉模式？

结合长轮询：控制消费节奏又能降低延迟。

### D3. 广播消费 vs 集群消费？

集群：组内一人处理；广播：组内每人一份（慎用，注意放大流量）。

### D4. 死信队列是什么？

多次失败后转入；要监控和人工处理，不能当黑洞。

## E. 场景设计题

### E1. 设计一个秒杀/下单异步扣库存

要点：

- 下单/资格校验后发 MQ 削峰  
- 库存预扣可用 Redis 原子操作，异步落库  
- 超时未支付延迟消息关单  
- 全程幂等（订单号）  
- 堆积监控与降级  

### E2. 缓存与 DB 一致性能不能靠 MQ？

可以：改 DB 后发变更事件，消费者删缓存/更新搜索。  
仍要处理重复与乱序（版本号、删除缓存优于更新缓存等）。  
对比 Cache Aside、延迟双删、CDC。

### E3. 如何做消息的链路排查？

生产日志打 MsgId/业务键 → Broker 控制台查轨迹 → 消费日志同键检索 → 是否进死信。  
有分布式 Trace 则把 MsgId 放进 Trace baggage。

## F. 陷阱题（简答）

| 题 | 要点 |
|----|------|
| MQ 能保证Exactly once吗？ | 裸 MQ 几乎不；靠幂等或事务能力近似 |
| 消费者越多越快吗？ | 受分区数限制 |
| 堆积了会丢吗？ | 正常持久化不丢；磁盘满/过期删除策略会 |
| 顺序消息失败一条？ | 可能堵住后续，要快速失败或隔离 |
| 改 ConsumerGroup 名？ | 当新消费者，位点行为变化，可能漏或重放 |

## G. 口述模板（1 分钟版）

> 我们用 MQ 做下单后的异步解耦。发送侧检查结果，关键链路用了事务消息/本地消息表避免和写库不一致。消费侧按订单号幂等，失败重试，超限进死信并告警。线上重点盯堆积和消费延迟；大促提前加分区评估和消费者扩容。选型上业务用 RocketMQ（事务/延时），日志流水用 Kafka。

把其中名词换成你项目真实技术栈即可。
