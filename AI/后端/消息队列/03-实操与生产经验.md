# 03 · 实操与生产经验

> 偏「上线以后怎么稳」：接入约定、监控、堆积、重复、排障。具体命令以 RocketMQ 为例处可对照专文；思路通用。

---

## 一、接入前先定的约定

| 项 | 建议 |
|----|------|
| Topic / 队列命名 | 带业务域 + 环境：`order_paid_prod` |
| 消费组命名 | `业务-消费者职责-环境`，**禁止**多环境共用 group |
| 消息体 | JSON/统一 schema；带 `messageId` / 业务主键 / 发送时间 |
| 超时 | 发送超时、消费最大时间要显式配置 |
| 重试 | 可重试异常 vs 不可重试（直接进死信/告警） |

消息最好当 **不可变事件**：`OrderPaid`，而不是「调用库存接口的指令糊在一起说不清」。

---

## 二、生产端经验

1. **检查发送结果**：失败要重试或落本地补发，别 `send` 完当成功。  
2. **合理 key**：要顺序就用业务键；不需要顺序可打散，避免热点分区。  
3. **控制大小**：单条别太大（大报文上对象存储，MQ 传引用）。  
4. **批量与异步发送**：提吞吐，但要想清楚失败哪一条、如何回调。  
5. **事务场景**：写库+发消息用「事务消息 / 本地消息表 / Outbox」，不要裸双写碰运气。

---

## 三、消费端经验（重中之重）

### 3.1 幂等是标配

```text
收到消息 → 用业务键去重/状态机校验 → 处理业务 → ACK
```

- DB 唯一索引是最稳的底线  
- Redis 去重要注意 TTL 与缓存丢失  

### 3.2 ACK 时机

```text
❌ 先 ACK 再处理 → 进程挂了就丢
✅ 处理成功再 ACK；失败让消息重试
```

注意：部分框架「抛异常才重试，吞掉异常等于成功」。

### 3.3 并发与顺序

- 默认并发消费：吞吐高，可能乱序  
- 顺序消费：单队列单线程，慢消息会堵后面  

### 3.4 下游超时

消费里调 RPC/DB：

- 设超时，避免占满消费线程  
- 失败分类：可重试（网络抖）/ 不可重试（数据非法）→ 后者打日志 + 死信  

---

## 四、重试与死信

| 阶段 | 做什么 |
|------|--------|
| 短重视重试 | 立刻或短间隔重试，抗网络抖动 |
| 长间隔重试 | 避免打死下游（RocketMQ 多级延迟重试） |
| 死信队列（DLQ） | 超过次数；**必须告警 + 人工/工具重放** |

死信不是垃圾桶：要有责任人、重放流程、定期清零。

## 五、堆积：怎么判断、怎么处置

> **结论先记**：积压一般 **不是靠「补偿」清掉的**；优先 **扩容 + 修好消费/下游 + 止血**。  
> 补偿是业务失败后的补救（补单、对账、重放），和「把堆积量降下来」不是同一件事。

### 5.1 先看指标

- 堆积量（ready / lag / broker offset - consumer offset）  
- 消费 TPS vs 生产 TPS  
- 消费耗时、失败率、死信增速  

### 5.2 应急处置顺序

```text
1. 确认是否预期削峰（大促）→ 扩容消费者、观察是否下降
2. 消费变慢 → 查下游 DB/接口、线程是否打满
3. 失败重试风暴 → 隔离坏消息、修数据或进死信
4. 分区过少 → 评估加队列（有副作用，慎在高峰乱改）
5. 可降级业务 → 丢弃非关键、旁路写日志稍后补
```

| 手段 | 作用 |
|------|------|
| 扩容消费者 / 提并发 | 最常见，提到接近分区数即可 |
| 修慢 SQL、下游超时 | 治本 |
| 死信隔离毒消息 | 避免重试堵死 |
| 降级、丢弃非关键 | 救急 |
| 重置位点 | **慎用**（等于跳过/丢一批） |

### 5.3 积压 vs 补偿（别混）

| | 消息积压 | 补偿 |
|--|----------|------|
| 问题 | 消费跟不上，消息堆在 MQ | 某步失败导致数据不一致、状态空洞 |
| 做法 | 扩容、提速、止血、修下游 | 重放消息、对账补单、人工修数据 |
| 关系 | 先把积压消化掉 | 积压期间若已造成业务空洞，**再**做补偿/对账 |

### 5.4 和磁盘的关系

Broker 磁盘满 → 写入失败/阻塞 → 生产报错、消费异常。  
（经验：磁盘满拖垮 DB 连接，同理可拖垮 MQ。）

## 六、监控与告警（最低配）

| 指标 | 告警思路 |
|------|----------|
| 堆积量 / 消费延迟 | 超阈值持续 N 分钟 |
| 发送失败率 | > 基线 |
| 消费失败率 / 死信 | > 0 或突增 |
| Broker CPU、磁盘、FD | 常规主机告警 |
| 副本/ISR/主从不健康 | 立即级 |

有 Trace 时：消息 Key、MsgId 打进日志，和 ARMS/SkyWalking 串联。

## 七、排障清单（线上）

### 7.1 用户说「操作了但没生效」

```text
1. 生产日志：消息是否发送成功（MsgId）
2. Broker：Topic 是否有消息、是否进死信
3. 消费日志：是否收到、是否幂等挡掉、是否异常被吞
4. 是否订错 Topic / Tag / 环境 group 抢消息
```

### 7.2 发送超时 / 失败

- NameServer/Broker 地址、网络、权限  
- Broker 磁盘、页缓存、GC  
- 同步刷盘/同步副本导致的延迟  

### 7.3 重复消费

- 先认「至少一次」正常现象  
- 查幂等是否失效（去重 key 冲突、TTL、未落唯一索引）  
- 是否消费超时被重新投递  

### 7.4 乱序

- 是否开了并发消费  
- 是否同一 key 落到不同分区  
- 是否多修复并发重放  

### 7.5 工具入口（各产品名不同，事相同）

| 目的 | 通用动作 |
|------|----------|
| 看堆积 | 控制台 / `consumerProgress` / Kafka lag |
| 发测试消息 | 控制台或 admin 发一条 |
| 重置位点 | 慎用；会丢或重复，要审批 |
| 看死信 | DLQ Topic / 死信队列长度 |

RocketMQ 命令细节见专文「运维与监控」章节。

## 八、容量与扩容经验

- **分区/队列数**：决定消费并行度上限，创建时规划好，事后改动有成本  
- **消费者实例**：水平扩到接近分区数即可，再多也闲  
- **存储**：估算保留时长 × 日消息量 × 副本  
- **大促**：提前压测消费能力，设堆积告警，准备只读降级

## 九、反模式（尽量别犯）

| 反模式 | 后果 |
|--------|------|
| 消费里做超重逻辑且无超时 | 堆积、线程耗尽 |
| 多环境共用 ConsumerGroup | 消息被「偷」走 |
| 改 group 名当没事 | 位点丢失，从最新/最早再来一遍 |
| 用 MQ 当 RPC（同步强依赖返回值） | 复杂且脆弱 |
| 无限重试毒消息 | 堵死分区 |
| 不监控死信 | 静默丢业务 |

---

## 十、和「线上排查」模块的衔接

| 用户表象 | MQ 侧常见落点 |
|----------|----------------|
| 接口慢 / 超时 | 同步链路误等 MQ；或消费跟不上导致状态查不到 |
| 状态不对 / 偶发 | 延迟、乱序、重复、读到旧数据 |
| 大量失败 | 发送失败、消费异常、死信暴涨 |
| 某一时段 | 定时任务洪峰、大促削峰堆积 |
