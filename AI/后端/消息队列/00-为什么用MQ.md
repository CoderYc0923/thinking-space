# 00 · 为什么用消息队列

> 先想清楚：**MQ 解决什么、带来什么代价**。选型和原理都建立在这上面。

---

## 一、本质

消息队列 = **异步的、可持久化（通常）的中间缓冲区**。

```text
生产者 ──投递──▶ Broker（存 + 转发）──拉取/推送──▶ 消费者
```

调用方不必同步等待下游做完；下游按自己的节奏消费。

---

## 二、四大经典场景

| 场景 | 一句话 | 典型例子 |
|------|--------|----------|
| **解耦** | 上游只发事件，下游各自订阅 | 下单 → 库存 / 积分 / 物流 |
| **异步** | 主链路先返回，慢活往后放 | 注册成功 → 发邮件 / 建档 |
| **削峰** | 尖峰进队列，后端匀速消化 | 秒杀、大促下单 |
| **广播/多订阅** | 一事件多系统独立消费 | 实名通过 → 风控 + 额度 + 营销 |

---

## 三、不用 MQ 时常见痛点

- 同步 RPC 链路变长 → RT 差、任一下游挂全挂  
- 新下游要改上游代码 → 耦合重  
- 突发流量直打 DB → 雪崩  

MQ 用 **时间换空间/稳定性**：尖峰变成堆积，系统「慢一点」而不是「立刻崩」。

---

## 四、引入 MQ 的代价（面试常问「缺点」）

| 代价 | 说明 |
|------|------|
| **复杂度** | 多一个中间件要部署、监控、扩容 |
| **最终一致** | 不再强同步；业务要接受短暂不一致 |
| **重复与乱序** | 至少一次投递常见 → 必须幂等；全局有序很难 |
| **运维风险** | Broker 故障、磁盘满、堆积打满影响业务 |
| **排查变难** | 异步链路要靠消息 ID / Trace 串联 |

**原则**：主链路强一致、极低延迟、简单系统——未必上 MQ；异步、多下游、削峰——值得上。

---

## 五、核心问题空间（后面原理都围着转）

学任何一款 MQ，最终都要能回答：

1. **消息会丢吗？**（生产确认、持久化、刷盘、副本）  
2. **会重复吗？**（至少一次 → 消费幂等）  
3. **能保证顺序吗？**（分区/队列内有序，全局有序代价大）  
4. **堆积了怎么办？**（扩容消费者、降级、丢弃/旁路、清理）  
5. **和本地事务怎么一起保证？**（本地消息表 / 事务消息 / 最大努力通知）
