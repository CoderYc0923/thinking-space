# 01 · 消息队列通用原理

> 下列概念在 Kafka / RabbitMQ / RocketMQ 里名字不同，**语义高度共通**。先吃透这篇，再看单品实现。

---

## 一、基本角色与术语对照

| 通用概念 | RocketMQ | Kafka | RabbitMQ |
|----------|----------|-------|----------|
| 消息主题 | Topic | Topic | Exchange + RoutingKey → Queue |
| 队列/分区（并行单元） | Queue / MessageQueue | Partition | Queue |
| 消息服务端 | Broker | Broker | Node / Broker |
| 生产方 | Producer | Producer | Publisher |
| 消费方 | Consumer | Consumer | Consumer |
| 消费组（进度隔离） | ConsumerGroup | Consumer Group | 多个 Consumer 挂同一 Queue 等 |
| 位点/偏移（看消费组在这个分区上读到哪了，用来续读、算堆积，也能决定会不会丢消息或重复消费） | Offset / Consume Offset | Offset | 消费确认后出队（队列模型） |

**记住**：并行度通常受「分区/队列数」限制——消费者多于分区时，多出来的会空闲。

**注意：**

- 主题（`Topic`）是给消息分类的通道，用来决定**发哪种时间、谁可以订**
- 消费组（`Consumer group`）：一组消费者共用一个进度，用来决定**同一条消息在组内只被处理一次，不同组可以各消费一遍**

**发布订阅：**

```java
生产者：我往哪个 Topic 发（一般不配消费者、不配消费组）
              ↓
           Broker：存消息、按规则投递
              ↓
消费者：我订哪个 Topic、我属于哪个 ConsumerGroup
         （组名在消费侧配，建议全局唯一且带环境前缀）
```

- 生产者和消费者通过`Topic`约定；消费者组名写在消费者上；生产者将消息发送到`Borker`，再由消费者拉（或者长轮询）走。
- 消费者组名是一条**独立消费身份**（通常对应一个下游业务能力，比如订单支付后加积分），所以最好是唯一组名，方便区分，消费者组中的不同消费者，代表一个客户端实例，连接`Broker`去拉取消息、回调代码



`Broker`刷盘：

- 消息先写到操作系统的**页缓存（内存）**，再由`Broker`决定**何时真正写入磁盘**。刷盘策略决定**宕机时消息会不会丢**以及**写入的速度**
  - 同步刷盘，消息写入磁盘成功才给生产者返回成功，可靠性高，但是写入性能慢
  - 异步刷盘，消息写入页缓存时就返回成功，后台再写入磁盘，极端宕机可能会丢消息，写入快

## 二、推模式 vs 拉模式

| 模式 | 含义 | 特点 |
|------|------|------|
| **Push** | Broker 主动推给消费者 | 延迟低；消费者来不及会背压难 |
| **Pull** | 消费者主动拉 | 易控节奏；可能多一次空拉 |
| **长轮询** | 拉 + 服务端挂起等到有消息 | 兼顾延迟与节奏（RocketMQ/Kafka 常见） |

生产里很少纯 Push 不管背压；多数是 **可调节的拉取/长轮询**。

## 三、投递语义（必考）

| 语义 | 含义 | 实现成本 |
|------|------|----------|
| **At most once** | 最多一次，可能丢，不重复 | 最简单 |
| **At least once** | 至少一次，不丢，可能重复 | 主流默认 |
| **Exactly once** | 恰好一次 | 很难；多靠「至少一次 + 幂等」或事务/幂等生产者 |

实务结论：

```text
MQ 保证「别丢」→ 至少一次
业务保证「别做错两次」→ 消费幂等（或去重表 / 唯一键）
```

---

## 四、可靠性链路（发送侧 + 存储侧 + 消费侧）

```text
发送成功确认（ACK / SendResult）
    → Broker 持久化（刷盘策略：同步/异步）
    → 副本复制（主从 / ISR）
    → 消费成功 ACK（更新位点）
    → 失败重试 → 死信（DLQ）
```

| 环节 | 丢消息常见原因 |
|------|----------------|
| 发送 | 没检查发送结果、超时当成功 |
| Broker | 异步刷盘 + 宕机；单副本；磁盘满 |
| 消费 | 先 ACK 再处理业务，处理失败却已提交位点 |

---

## 五、顺序消息

```text
全局有序：整个 Topic 单队列 —— 吞吐差，少用
局部有序：同一业务键（如 orderId）进同一分区/队列 —— 常用
```

前提三件套：

1. 生产：按 key 哈希到同一 Queue/Partition  
2. 存储：单分区内 FIFO  
3. 消费：单线程/顺序消费模式（并发会打乱）

代价：热点 key、单分区阻塞会拖慢整条有序链路。

## 六、重复消费与幂等

**为什么必有重复**：超时重试、消费者重启、Rebalance、网络 ACK 丢失等。

幂等常用手段：

| 手段 | 适用 |
|------|------|
| 业务唯一键（订单号、消息 Key）+ DB 唯一约束 | 落库类 |
| 去重表 / Redis `SETNX`（带 TTL） | 通用 |
| 状态机（仅允许「待支付→已支付」） | 有明确状态流转 |
| 天然幂等（覆盖写、SET 终态） | 更新类 |

---

## 七、消息堆积（Backlog）

```text
生产 TPS > 消费 TPS 持续一段时间 → 堆积
```

| 原因 | 处理方向 |
|------|----------|
| 消费者慢 / 下游 DB 慢 | 扩容消费者、优化业务、降级 |
| 分区太少 | 增加 Queue/Partition（注意兼容） |
| 消费失败疯狂重试 | 快速失败进死信，避免堵死 |
| 突发流量（削峰预期内） | 接受短暂堆积 + 告警阈值 |

堆积本身不一定是事故；**堆积持续上升或延迟超 SLO** 才是事故。

---

## 八、延迟 / 定时消息

用途：超时关单、延迟重试、预约任务。

实现差异大：

- RocketMQ：延时级别 / 定时消息  
- RabbitMQ：死信 + TTL、延迟插件  
- Kafka：无原生延迟，多靠时间轮/外部调度  

---

## 九、事务与「发消息 + 写库」一致

经典两难：

```text
先写库再发消息：消息可能丢（发失败）
先发消息再写库：库失败但消息已发出（脏消息）
```

常见解法：

| 方案 | 思路 |
|------|------|
| **本地消息表** | 与业务同事务写「待发送」；异步投递并更新状态 |
| **事务消息**（RocketMQ） | 半消息 → 本地事务 → 提交/回滚；回查 |
| **Outbox + CDC** | 写 Outbox 表，Canal/Debezium 转成 MQ |
| **最大努力通知** | 多次回调 + 对账（支付常见） |

---

## 十、消费模型：集群 vs 广播

| 模型 | 行为 |
|------|------|
| **集群消费**（常见） | 同组内一条消息只被一个消费者处理 |
| **广播消费** | 组内每个实例都收到（配置、本地缓存刷新等） |

---

## 十一、过滤

- Tag / Header 过滤（Broker 或 Client）  
- SQL92 过滤（RocketMQ 等）  
- Kafka：多在消费端过滤，或用多 Topic  

过滤越靠 Broker，越省网络；规则太复杂会影响 Broker。

---

## 十二、和「双写 / 最终一致」的关系

MQ 经常是 **异步同步多存储** 的通道（DB → 搜索、缓存失效通知等）。

- 用 MQ 传递变更事件，比应用双写更清晰  
- 仍要处理：重复、乱序、延迟 → 消费幂等 + 版本号/更新时间
