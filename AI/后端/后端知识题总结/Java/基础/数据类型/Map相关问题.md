- **HashMap和HashTable、ConcurrentHashMap，对比**
  - HashMap：无锁，线程不安全，速度快，允许一个null key
  - HashTable: 整表锁，慢，不允许null key
  - ConcurrentHashMap：`jdk7`分段锁，`jdk8`空桶`CAS`，非空桶的桶头加`synchronized`占锁。

- **HashMap实现原理？**
  - **数组+（链表或红黑树）**
  - 对key算出一个hash值，然后通过**hash值确认桶位置**
  - 如果多个key算到同一个hash，也就是**哈希冲突**，就把这些**key串成链表**放进同一个桶
  - 从`JDK8`开始，某个桶**链表**太长了，默认是**长度到8**，**且整个数组的长度到了64**，就把这个桶的**链表改成红黑树**。若**数组长度小于64**，先不改红黑树，**先扩容**。当**节点变少**（**小于等于6**），树可能会**退化成链表**



- **为啥冲突严重时用红黑树，不用「严格平衡二叉树（AVL）」？**
  - **AVL**严格平衡树要求**左右高度差几乎随时为1**，这会让**插入/删除时频繁旋转调整**，**代价大**
  - **HashMap**里**链表变树**并非**不是常态**，**树**只是**冲突严重时的补救**。而**红黑树只保证“别歪的太厉害”，调整次数少，查找仍然快，增删也划算**。
  - 而且**HashMap查改是常态**，所以**综合用红黑树更合适**。



- **HashMap线程安全吗？**
  - **不安全**，**多个线程**同时**put/扩容**时，可能会出现**数据被覆盖、丢节点**的问题。
  - **`JDK7`中**，**扩容时**采用**头部插入**的方式，**并发下可能会把链表弄成环**，**`get`时死循环**
  - **`JDK8`改成尾部插入**，死循环解决了，但是丢数据、覆盖数据问题仍然在
  - 多线程要用**`ConcurrentHashMap`**或**整体加锁**



- **HashMap，`put`存大致怎么走？**
  - 用key算hash，找到数组下标桶
  - 桶是空的，直接放入
  - 桶有东西，先看是不是同一个key（先比hash，再比equals）。若是同一个，则修改value；若不是就顺着链表或者树找，找不到就新加入
  - 若该桶链表够长且数组够大，就变成红黑树
  - 若总元素个数超过「容量 × 负载因子」，就扩容（数组变大约2倍），元素重新分配到新桶。



- **HashMap，`get`取大致怎么走？**
  - 用key算出hash找到对应下标桶，先看第一个节点对不对，不对就顺着链表对比，或在红黑树中查找，找到返回value,找不到返回null



- **调用 get 就一定没问题吗？**
  - **不一定**
    - 如果连 HashMap 对象都还是 null（没 `new`），调任何方法都会空指针
    - 已经创建好的 HashMap，**用 `get(null)` 是允许的（它支持 null 作为 key）**
    - **多线程边读边改结构**，仍可能**读乱或出异常**



- **key 一般用什么？为啥 String 合适？**
  - **key 最好创建后别再改内容（不可变）**。
  - **String 不可变**，它的 `hashCode`、`equals` 稳定，**不会出现「存进去时算在 A 格，后来字段变了去 B 格找」的错乱**
  - **自己写的类当 key，通常要正确重写 `equals` 和 `hashCode`**，并且别在放进 Map 之后再改参与相等判断的字段



- **key 能为 null 吗？**
  - **HashMap：可以**。**null key 会固定放到某个位置（实现里相当于哈希当 0），而且只能有一个 null key**；value 为 null 可以有很多个。
  - **Hashtable、ConcurrentHashMap：不可以为 null**。



- **重写 equals / hashCode 要注意什么？**
  - HashMap **找位置靠 `hashCode`**，**确认是不是同一个 key 靠 `equals`**。
  - **`equals`为`true`，`hashCode`必须相等；`hashCode`不相等，`equals`必须为`false`**



- **HashMap扩容是怎么回事？负载因子是什么？**
  - 默认**数组长度**往往从 **16** 开始。
  - **负载因子默认 0.75**：意思是**元素个数超过「容量的 75%」就扩容**，**避免格子太挤、冲突太多**
  - **0.75 是空间浪费和查找变慢之间的折中**
  - **扩容**时**容量变成大约 2 倍**，**再把旧数据挪到新数组**，因**为容量一直是 2 的幂**（2、4、8、16…），**JDK 8 可以用很便宜的位运算判断**：这个元素是还留在原下标，还是挪到「原下标 + 旧容量」



- **为啥容量必须是 2 的幂？**

  - **定位下标**用的是类似「**哈希值和 (长度-1) 做按位与**」，在**长度为 2 的幂时**，这等价于「**对长度取余**」，**但比取余快**。同时也方便**扩容重分布**。
  - **若长度不是 2 的幂**，`(长度-1)` 的二进制不是低位全 1，有些下标几乎用不到，又浪费又更容易挤在一起冲突。

  

- **往里放 20 个元素，会扩容几次？（默认参数）**
  - **容量 16**，**阈值**大约是 16×0.75=**12**，放到第 13 个时**扩一次，变成 32**，20 还远小于 32×0.75，所以一共 扩容 1 次



- **Hashtable 怎么保证线程安全？为啥不香了？**
  - 几乎**每个对外方法都加了 synchronized**（同一时刻整张表往往只能一个线程在操作）
  - **安全，但锁太粗，并发一高就排队**，所以现在一般不用。也不允许 null



- **ConcurrentHashMap 怎么做到又能并发又相对安全？**
  - **JDK 7**：
    - **分段锁**，把整张大表切成好几段（Segment，分段），每段一把锁（线程 A 改第 1 段、线程 B 改第 2 段，可以同时进行，比锁整张表强）
  - **JDK 8**
    - **空桶偏乐观更新，有碰撞再锁这一桶**。锁比 Hashtable 细，也比 JDK7 分段更细一些
    - 数组 + 链表/红黑树，
      - **某个桶还是空的**：用 **CAS**的乐观写法，不一定先抢大锁）把新节点放进去
      - **桶里已经有链表/树**：对这一**桶的头节点加 synchronized**，只锁这一桶，别的桶别人还能动。
