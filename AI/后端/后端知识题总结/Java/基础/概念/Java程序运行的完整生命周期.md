整体链路：`.java` →（javac）→ `.class` →（启动 JVM）→ 类加载/验证/链接/初始化 → 解释/JIT 执行 → GC 等运行期机制

### 1. 编译期（运行前，用的是 JDK 工具）

- `javac` 将 `.java` 源码编译成平台无关的 `.class` 字节码
- 这一步**不依赖**目标机器上的操作系统指令集

### 2. 运行期（`java` 命令启动一个 JVM 进程）

JRE 提供「JVM + 类库」这套运行环境；**真正干活的是 JVM**。不要写成「先在 JRE 里加载类，再进入 JVM」——加载、验证、执行都在 JVM 内完成。

**（1）类加载子系统ClassLoader（JVM）**

- 类加载器按需读取 `.class`（以及类库中的标准类，如 `String`、`System`），并在堆中生成唯一java.lang.Class对象，作为反射入口
- **验证**（字节码安全、合法，防止恶意、畸形class文件损坏JVM）→ **准备**（为静态变量分配内存、赋默认零值）→ **解析**（将**常量池**中的**符号引用**替换为**直接引用**【直接内存地址】）
- **初始化**（执行**类静态逻辑**，按代码顺序执行：**静态变量显式赋值**，**静态代码块static{}** ）【父类优先初始化，子类初始化前必先完成父类初始化】
- 注意：类加载器的**双亲委派**：
  - JVM内置三层类加载器：`Bootstrap ClassLoader（启动类加载器）`,`Extension ClassLoader（扩展类加载器）`，`Application ClassLoader（应用程序类加载器、系统加载器）`，`自定义加载器`
  - 双亲委派的**工作机制**：加载一个类时，子加载器先委派给父加载器，逐层向上知道启动类加载器。当父加载器无法加载时才向下交给子加载器加载
  - 双亲委派的**核心作用**：
    - **安全防护**：防止开发者自定义java.lang.String这类核心类替换原生类，破坏JVM安全
    - **类全局唯一**：保证同一个全限定名的类，在JVM中只加载一次，避免多份Class对象造成类型转换异常

  - **破坏双亲委派的场景**：
    - 因为**上层加载器无法加载下层加载器加载的类**，而很多场景需要**父加载器依赖子加载器**
      - **SPI**：JDK提供的服务扩展机制，比如**JDBC**的SPI接口`java.sql.Driver`由`Bootstrap ClassLoader`启动类加载器加载，但是数据库驱动实现类`com.mysql.jdbc.Driver`由`Application ClassLoader`加载，需要父加载器依赖子加载器
        - 通过`TCCL（TgreadContextClassLoader）`线程上下文类加载器，让父加载器通过线程上下文拿到下层子加载器，绕过双亲委派

      - 热部署、热加载框架（**Spring DevTools、JRebel**）：开发时修改Java代码无需重启整个Spring容器，自动重新编译加载类。但是双亲委派同一个全限定名类只会加载一次，缓存永久生效，无法重新加载修改后的class文件。
        - 通过自定义加载器重写`loadClass()`方法，放弃向上委派父加载器，直接自己加载

    - 常见破坏方案：
      - TCCL，通过线程上下文类加载器绕过双亲委派
      - 自定义加载器重写`classLoader()`方法。


**（2）执行引擎（JVM）**

- 以**方法**为执行单位
- 若方法入口已指向 **Code Cache** 中的本地机器码 → 直接执行
- 否则 **解释器** 逐条解释字节码执行
- 用**方法调用计数器** / **回边计数器**统计热度；达阈值后 **JIT** 把该方法编译成本地机器码写入 Code Cache，并改入口，之后走机器码

**（3）其他运行期机制（JVM）**

- **GC**：回收堆中不可达对象
- **线程与同步**：管理并发
- 需要 OS 资源时：经 JNI/native → 系统调用 → 操作系统

### 3. 结束

- 主线程及非守护线程结束后，JVM 进程退出，操作系统回收其资源
