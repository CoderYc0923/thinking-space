  - 相关笔记：
    - [InnoDB的B+树](./InnoDB的B+树.md)

- **什么是索引？**
  - 类比书的目录：先查目录再翻到对应页，而不是一页页翻
  - 设计思想：**以空间换时间**
  - 定义：帮助存储引擎快速获取数据的一种数据结构；形象说就是**数据的目录**
  - 索引和数据都在存储引擎层；常见引擎 MyISAM、InnoDB、Memory；MySQL 5.5 后默认 InnoDB
  
- **索引的分类（四个角度）**

  - 按「数据结构」：B+tree 索引、Hash 索引、Full-text 索引
  - 按「物理存储」：聚簇索引（主键索引）、二级索引（辅助索引 / 非聚簇索引）
  - 按「字段特性」：主键索引、唯一索引、普通索引、前缀索引
  - 按「字段个数」：单列索引、联合索引

- **按数据结构分类**

  - 常见：B+Tree、HASH、Full-Text；不同引擎支持不完全相同
  - InnoDB 默认且最常用的是 **B+Tree 索引**；主键索引和二级索引默认都是 B+Tree

  - InnoDB 选聚簇索引键的规则

    - 有主键 → 用主键
    - 无主键 → 选第一个不包含 NULL 的唯一列
    - 上面都没有 → 自动生成隐式自增 id

  - B+Tree 形态要点

    - 多叉树；**只有叶子存数据**，非叶子只存索引（目录项）
    - **节点内按索引键有序**
    - 父节点索引值会出现在下层子节点中；叶子包含全部索引值信息
    - **叶子之间双向链表相连**（**便于范围扫描**）
    - 读一个节点 ≈ 一次磁盘 I/O；**千万级数据高度约 3~4 层** → **查一条大约 3~4 次 I/O**

  - 主键查询过程（例：`where id = 5`）

    - 自顶向下：根 → 中间层 → 叶子，**逐层比较定位**
    - 叶子里找到对应主键的整行数据

  - 二级索引查询过程

    - 主键索引叶子：**完整行数据**
    - 二级索引叶子：**主键值**（不是整行）
    - `select * where 二级索引列 = ?`：先走二级索引拿到主键，再走主键索引取整行 → **回表**（查两棵树）
    - 若查询列都能在二级索引叶子拿到（如 `select id where product_no = ?`）→ **覆盖索引**（只查一棵树）

  - 为什么 InnoDB 选 B+Tree

    - vs B 树
      - B+Tree **非叶子不存行数据**（B树**非叶子节点也存数据**），单节点更「瘦」，同一次 I/O 能装更多索引项 → 树更矮
      - **叶子双向链表**，适合范围 / 顺序扫描；B 树做不到同等方便的范围扫
    - vs 二叉树
      - B+Tree 复杂度约 `O(logd N)`，d（扇出）常常> 100，千万级仍约 3~4 层
      - 二叉树**扇出只有 2**，**层数更高** → 磁盘 I/O 更多
    - vs Hash
      - Hash **等值很快** O(1)，但**不擅长范围查询**
      - MySQL 场景里范围查询常见，B+Tree 适用面更广

- **按物理存储分类**
  - 聚簇索引（主键索引）：非叶子存主键值作为目录项，叶子存完整用户记录数据
  - 二级索引：非叶子存索引列，叶子存索引列+主键值
  - 二级索引能覆盖所需列 → **覆盖索引**，不回表；否则**回表**
  
- **按字段特性分类**

  - 主键索引
    - 建在主键上；一张表最多一个；不允许 NULL
    - `PRIMARY KEY (col) USING BTREE`

  - 唯一索引
    - 建在 UNIQUE 列上；一张表可多个；值唯一，允许 NULL
    - 建表：`UNIQUE KEY(...)`；建后：`CREATE UNIQUE INDEX ...`

  - 普通索引
    - 普通字段上的索引，不要求主键 / UNIQUE
    - 建表：`INDEX(...)`；建后：`CREATE INDEX ...`

  - 前缀索引
    - 对字符类型字段前若干字符建索引（char / varchar / binary / varbinary）
    - 目的：减小索引体积，一页多装些键值，提升查询效率
    - `INDEX(column_name(length))`

- **按字段个数分类**

  - 单列索引：建在一列上（如主键）
  - 联合索引（复合索引）：多列组成一个索引

  - 联合索引怎么排序

    - 例：`(product_no, name)` → 先按 product_no 排，相同再按 name 排
    - 非叶子的 key 是多字段组合值

  - 最左匹配原则

    - 按最左优先匹配；不遵循则联合索引用不上（或只能用到前缀部分）
    - 联合索引 `(a, b, c)` 能用上的例子：
      - `where a=1`
      - `where a=1 and b=2`
      - `where a=1 and b=2 and c=3`
      - where 里字段书写顺序不重要（有优化器）
    - 用不上的例子：
      - `where b=2` / `where c=3` / `where b=2 and c=3`
    - 原因：先按 a 全局有序；b、c 只在「前缀列相同」时局部有序；**用索引的前提是 key 有序**

  - 联合索引 + 范围查询（重点）

    - 不是「用了联合索引」就等于「索引里每个字段都参与了索引定位」
    - 口诀常说：最左匹配遇到范围查询会停止向后匹配 → **范围列本身能用索引，其后的列一般不能再用索引定位**
    - 但要分清哪些「范围」会停止匹配：

      - **会停止向后匹配**：`>`、`<` 这类
        - 例 Q1：`where a > 1 and b = 2`，联合索引 `(a,b)`
          - a 有序且命中区间相邻 → a 能走索引
          - `a > 1` 的区间里 b **全局无序** → b 不能用来缩小扫描区间
          - 执行计划里往往 `key` 仍是联合索引，但 `key_len` 只体现 a（如两 int 非空时 key_len=4）

      - **不会因此停止向后匹配**：`>=`、`<=`、`BETWEEN`、`like '前缀%'`
        - 例 Q2：`where a >= 1 and b = 2`
          - 可拆成：`a = 1 and b = 2`（ab 都能用）+ `a > 1 and b = 2`（后面这段 b 仍不能用索引定位）
          - 因存在 `a=1` 这一段局部有序，优化器可用 b 收紧起点 → **a、b 的 key_len 都能体现**（两 int 非空约 8）
        - 例 Q3：MySQL 的 `BETWEEN` 含两端，类似 `>=` 且 `<=` → a、b 都可能用上
        - 例 Q4：`where name like 'j%' and age = 22`，联合索引 `(name, age)`
          - `like 'j%'` 形成类似 `['j','k')` 的扫描区间，name 能走索引
          - 在 `name = 'j'` 的局部里 age 有序 → age 也能参与收紧
          - `like '%xx'` / `like '%xx%'` 另说，属于索引失效场景

    - 用 `key_len` 判断「到底用了联合索引的几列」来形成扫描边界（比只看 `key` 更细）
      - 注意：执行计划里变长列的 key_len，server 层对变长长度常按 **2 字节**估算，不一定等于 InnoDB 行格式里真实长度字节数；key_len 主要用来看「用了哪些列」

  - 索引下推（**ICP**，MySQL 5.6+）

    - 场景：联合索引 `(a,b)`，`where a > 1 and b = 2` → 只有 a 能索引定位，b 仍要过滤
    - 5.6 前：拿到主键后一个个回表，再在主键索引行上判断 b
    - 5.6 后：在二级索引遍历时，先用索引上已有的 b 做判断，过滤掉不满足的，**减少回表**
    - Extra 出现 `Using index condition` → 用了索引下推

  - 索引区分度

    - 区分度 ≈ 该列不同值个数 / 表总行数
    - 联合索引：区分度大的列尽量靠前（更常被用来过滤）
    - 区分度太低（如性别）：优化器可能发现某值占比很高（经验上常提 30%）而放弃索引、改全表扫描

  - 联合索引帮助排序

    - 例：`where status = 1 order by create_time`
    - 只建 status 索引 → 过滤后还可能 `Using filesort`
    - 更好：建 `(status, create_time)`，利用索引有序性，避免额外文件排序

- **什么时候需要 / 不需要创建索引？**

  - 索引的代价
    - 占磁盘空间，数量越大，占用空间越大
    - 创建 / 维护耗时，数据量越大越明显
    - **降低增删改效率**（每次对表数据做增删改，只要动到了索引相关的列（或整行插入/删除），对应 B+Tree 都要跟着维护，才能继续保持有序。）

  - 适合建索引
    - 有唯一性约束的字段（如商品编码）
    - 常出现在 WHERE 的字段；多条件可考虑联合索引
    - 常用于 GROUP BY / ORDER BY 的字段（利用有序，少一次排序）

  - 不适合 / 不需要建索引
    - WHERE / GROUP BY / ORDER BY 都用不到的字段
    - 大量重复值的字段（如性别）
    - 表数据量太小
    - 更新极其频繁的字段（如余额）：频繁维护 B+Tree 伤性能

- **有什么优化索引的方法？**
  - 前缀索引优化
    - 大字符串只取前缀建索引，减小索引项，提高页内装载量
    - 局限：ORDER BY 难以用前缀索引；也难以当覆盖索引用
  
  - 覆盖索引优化
    - SELECT 所需列都能在某个二级索引叶子拿到 → 不回表，少 I/O
    - 例：常查 name、price，可建包含这些列的联合索引（按查询与最左匹配设计）
  
  - 主键最好自增
    - 聚簇索引叶子按主键有序存放
    - 自增：新行多半追加到页尾，页满再开新页，插入高效
    - 随机主键：常插到页中间 → 移动记录甚至 **页分裂** → 碎片、空间利用率下降、影响性能
    - 主键尽量短：二级索引叶子存主键，主键越短二级索引越小
  
  - 索引列最好 NOT NULL
    - NULL 让优化器统计、比较更复杂（如 count 会跳过 NULL）
    - 允许 NULL 的列会在行格式里带来 NULL 值列表等额外空间
  
- **索引失效有哪些？（常见 6 类）**
  - 前提：建了索引 ≠ 这条 SQL 一定走索引；最终以 `EXPLAIN` 为准
  - 参考：[小林coding - 索引失效有哪些](https://xiaolincoding.com/mysql/index/index_lose.html)
  
  - **1）左模糊 / 左右模糊匹配**
    - 会失效：`like '%xx'`、`like '%xx%'`（执行计划常 `type=ALL`）
    - 能走索引：`like 'xx%'`（前缀匹配，常 `type=range`）
    - 原因：B+Tree 按索引值**有序**，只能按前缀定位起点；后缀 / 中间模糊不知道从哪开始比，只能全表扫
    
  - **2）对索引列使用函数**
    - 例：`where length(name) = 6` → 常全表扫描
    - 原因：索引里存的是列的**原始值**，不是函数计算后的值，无法用树去定位
    - 例外：MySQL 8.0+ 可建**函数索引**，对计算后的值建索引，例如：
      - `alter table t_user add key idx_name_length ((length(name)));`
      - 之后再按 `length(name)` 查就可以走该索引
    
  - **3）对索引列做表达式计算**
    - 例：`where id + 1 = 10` → 常失效
    - 改成：`where id = 10 - 1` → 计算落在常量侧，可走索引
    - 原因同函数：索引存原始值，不是 `id+1` 之后的值；MySQL 一般不会自动帮你把式子「搬到右边」
    
  - **4）隐式类型转换（特别容易踩坑）**
  
    - MySQL 比较「字符串 vs 数字」时，会把**字符串转成数字**再比（可用 `select '10' > 9`，结果为 1 来验证）
    - **索引列是字符串，条件给数字** → 失效
      - 例：`phone` 为 varchar 且有索引，`where phone = 1300000001`
      - 实际相当于：`where CAST(phone AS signed) = 1300000001`
      - CAST 作用在索引列上 ≈ 对索引用了函数 → 失效
    - **索引列是数字，条件给字符串** → 一般**不失效**
      - 例：`where id = '1'` → 相当于 `where id = CAST('1' AS signed)`，CAST 在常量上，索引列本身没被包函数
  
  - **5）联合索引不遵循最左匹配**
    - 联合索引 `(a, b, c)`：先按 a 排，a 同再按 b，b 同再按 c
    - 能用上（至少用到前缀）的例子：
      - `where a=1`
      - `where a=1 and b=2`
      - `where a=1 and b=2 and c=3`
      - where 里字段书写顺序不重要（有优化器）
    - 整段联合索引都用不上（从最左断掉）的例子：
      - `where b=2` / `where c=3` / `where b=2 and c=3`
    - 特殊：`where a=1 and c=2`
      - **不是完全失效**：a 仍可走索引定位；中间跳过 b，c **不能**参与缩小扫描区间（索引截断）
      - MySQL 5.5：常先靠 a 拿到主键再回表，在 Server 层再比 c
      - MySQL 5.6+：可能 **索引下推**，在二级索引上直接过滤 c，减少回表；Extra 常见 `Using index condition`
      - 记法：a 用上了，c 是过滤（可能 ICP），不是「c 也完整走了最左匹配」
    
  - **6）WHERE 里 OR 导致失效**
  
    - 若 OR 一侧是索引列、另一侧**不是**索引列 → 整句常全表扫描
      - 例：`where id = 1 or age = 18`（id 有索引、age 没有）→ 常 `type=ALL`
    - 原因：OR 表示两边满足其一即可；一边没法靠索引保证，优化器往往只能全表扫
    - 处理：给另一侧也建索引；可能变成 `type=index_merge`（两边分别扫索引再合并），避免全表扫

  - **和其他「看起来像失效」的区分（面试加分）**
    - **区分度太低** / **预计扫太多行**：优化器可能**主动不用索引**改全表扫（不一定是语法导致的「失效」，是成本选择）
    - **范围查询**后**联合索引后续列用不了**：索引仍可能在用，只是 `key_len` 只体现前面几列（见上文联合索引范围查询）
  
- **看执行计划（判断有没有用上索引）**
  - 常用字段
    - `possible_keys`：可能用到的索引
    - `key`：实际用的索引；为 NULL 往往表示没用索引
    - `key_len`：索引长度（联合索引可借此看用了几列）
    - `rows`：估算扫描行数
    - `type`：访问类型（重点）
    - `Extra`：额外信息
  
  - type 从差到好（常见）大致：
    - **ALL**（全表扫描）→ 尽量避免
    - **index**（全索引扫描）→ 对索引表进行全扫描，这样做的好处是不再需要对数据进行排序，但是开销依然很大
    - **range**（索引范围扫描：`<` `>` `in` `between` 等）→ **从这一级别开始，索引的作用会越来越明显**，尽量到这档及以上
    - **ref**（非唯一索引，或唯一索引的非唯一前缀）返回数据返回可能是多条（虽然使用了索引，但该索引列的值并不唯一，有重复）
    - **eq_ref**（主键 / 唯一索引，通常使用在多表联查中）
    - **const**（主键 / 唯一索引与常量比较：比如 select name from product where id=1，结果至多一行）
  
  - Extra 里常见要警惕 / 要争取的
    - `Using filesort`：当查询语句中包含 **group by** 操作，而且**无法利用索引完成排序**操作的时候，这时不得不选择相应的排序算法进行，甚至可能会通过文件排序，效率很低，尽量靠索引避免
    - `Using temporary`：使用**临时表**保存中间结果，常见于复杂 order by / group by，尽量避免
    - `Using index`：覆盖索引，较好
    - `Using index condition`：索引下推
  
- **总结**
  - 索引是数据目录，InnoDB 里主要是 B+Tree；聚簇叶子存行，二级叶子存索引列+主键，覆盖则免回表
  - 分类要按**数据结构** / **物理存储** / **字段特性** / **字段个数**四个角度记，面试才不乱
  - 联合索引核心是**最左匹配** + **有序性**；范围查询要分清 `>`/`<` 与 `>=`/`BETWEEN`/`like 'x%'` 对后续列的影响，并用 key_len、ICP（索引下推） 加深理解
  - 建不建、怎么优化，都是权衡：查得快 vs 空间 / 写入 / 维护成本；最终用 EXPLAIN 验证
  - 索引失效常记 6 类：**模糊匹配方向**、**函数**、**表达式**、**隐式类型转换**、**联合索引最左**、**OR**；`a=? and c=?` 属于截断而非整索引作废
