- 因为 MySQL 的索引数据结构，不仅仅考虑增删改查的时间复杂度，更重要的是磁盘 IO 次数。索引和记录都存放在硬盘中，硬盘相对内存非常慢，查询时应尽量在更少的磁盘 IO 内完成定位。
  - InnoDB 以页（默认 16KB）为单位读写：一次磁盘 IO 读一整页，页内再在内存里查找。树高大致决定最坏路径上要读多少页（实际还受 Buffer Pool 命中影响），所以「矮」比「单纯算法复杂度好看」更关键。

- 二分查找树（BST）虽能二分定位，但按有序/逆序插入时会退化成链表，查询从 O(logn) 退化到 O(n)。

- 自平衡二叉树（如 AVL、红黑树）能保证高度约 log₂(n)，查询稳定在 O(logn)。但它每个节点最多 2 个子节点，数据量大时树仍然很高；高度越高，最坏情况下要访问的页越多，磁盘 IO 越多，不适合海量磁盘数据检索。

- B 树和 B+ 树都是多路平衡查找树：一个节点可有很多个子节点（扇出大）→ 同样数据量下树更矮 → 更适合磁盘索引。
  - MySQL 默认的 InnoDB 选用 **B+ 树**，相对 B 树的主要原因：

    - **扇出更大，树更矮**：B+ 非叶子节点只存键和子节点指针，不存行数据；B 树非叶既存键又存记录。同一页里 B+ 能塞更多目录项 → 扇出（fan-out）更大 → 树更矮 → 等值查找路径上的页 IO 更少。「更矮胖」是结果，扇出更大才是原因。

    - **更适合范围 / 顺序访问**：B+ 叶子节点有序，且叶子之间用链表（InnoDB 中为双向链表）串联。范围查询定位到起点后，沿叶子链表顺序扫即可。B 树范围查询往往要在树内反复遍历，更容易带来更多页 IO。

    - **结构统一，利于维护与聚簇**：B+ 所有真实数据都在叶子；非叶只做路由（可存冗余键）。插入删除时分裂/合并语义更清晰。InnoDB 借此做聚簇索引：主键 B+ 的叶子存完整行；二级索引叶子存「索引列 + 主键」，需完整行时再回表。

    - **补充（易被追问）**：等值查询时，B 树可能在非叶就命中；B+ 必须走到叶子。InnoDB 仍选 B+，是因为「更矮 + 范围/顺序扫 + 叶子统一存数据（聚簇）」的整体收益更大，而不是单点查找一定比 B 树更快。插入删除也不是绝对比 B 树快，重点是整体读写模型和范围场景更划算。
