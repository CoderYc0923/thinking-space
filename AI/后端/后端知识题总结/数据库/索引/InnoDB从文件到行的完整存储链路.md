- **先把整条链路串起来（从上到下）**

  - `.ibd` 表空间
    - 段（segment）
      - 区（extent）
        - 页（page，默认 16KB，磁盘读写单位）
          - 页内的用户记录（User Records）
            - 一行记录按「行格式」排好的字节（Compact / Dynamic …）

  - 一句话记：
    - **页**决定「数据放在哪、怎么在页间/页内定位」
    - **行格式**决定「这一行的字节长什么样」
    - 两篇文档分别讲这两层，并不冲突：
      - [MySQL 一行记录的存储结构](./MySQL%20一行记录的存储结构.md)：文件 / 表空间 / 行格式
      - [InnoDB的B+树](./InnoDB的B+树.md)：数据页结构 / B+ 树 / 聚簇与二级索引

- **第 1 层：文件与表空间（宏观容器）**

  - MySQL 支持多种存储引擎，不同引擎落盘文件不同；这里只看 **InnoDB**

  - 每创建一个 database，会在数据目录下建一个同名目录，表结构和表数据都放在这个目录里

  - 一个 database 目录下常见文件

    - `db.opt`
      - 存放当前库的默认字符集和校验规则

    - `表名.frm`
      - 存放表结构（元数据、表定义等）

    - `表名.ibd`
      - 存放表数据
      - 表数据可以放在共享表空间（`ibdata1`），也可以放在独占表空间（`表名.ibd`）
        - 由 `innodb_file_per_table` 控制；为 1 时用独占表空间
        - MySQL 5.6.6 起默认就是 1，之后表数据默认单独一个 `.ibd`

  - 一个表空间文件（`.ibd`）的结构：由表空间 → 段 → 区 → 页 → 行 组成

    - 行（row）
      - 表中的记录按行存放
      - 每行根据不同的行格式，有不同的存储结构

    - 页（page）
      - 页中存放行数据
      - InnoDB 以**页**为单位读写，默认 16KB
      - 页类型很多：数据页、undo 日志页、溢出页等
      - 用户表里的行记录，由**数据页**管理；数据页再组成 B+ 树（见第 2、4 层）

    - 区（extent）
      - B+ 树每一层的页，通过双向链表逻辑相连
      - 若只按页分配，链表上相邻的两个页，物理位置可能并不连续 → 范围扫描容易变成大量随机 IO
      - 数据量大时，为索引分配空间不再按页，而按**区**
        - 每个区 1MB；16KB 页时，连续 64 个页划成一个区
        - 这样链表上相邻的页，物理上也尽量相邻，便于顺序 IO

    - 段（segment）
      - 表空间由各个段组成，段由多个区组成
      - 常见段：
        - **索引段**：B+ 树**非叶子节点**所在区的集合
        - **数据段**：B+ 树**叶子节点**所在区的集合
        - **回滚段**：回滚数据所在区的集合
      - 和后面「聚簇索引叶子存整行、非叶子只存目录项」是同一件事的两种说法

- **第 2 层：数据页 = B+ 树的一个节点（页怎么组织很多行）**

  - InnoDB 的数据按「数据页」为单位读取，一页默认 16KB

  - 数据页的七个部分

    - 文件头（File Header）38 字节：页的信息；其中有指针，把上下数据页串成**双向链表**（页与页逻辑连续）
    - 页头（Page Header）56 字节：页的状态信息
    - 最大、最小记录（Infimum、Supremum）26 字节：两个虚拟伪记录，标识页内最小、最大
    - 用户记录（User Records）：存放行记录内容（真正业务行 / 目录项都在这里）
    - 空闲空间（Free Space）：页里还没用的空间
    - 页目录（Page Directory）：存用户记录的相对位置，对页内记录起索引作用
    - 文件尾（File Trailer）8 字节：校验页是否完整

  - 页内记录怎么串、怎么查

    - 用户记录之间，用记录头里的 `next_record` 串成**单向链表**
      - 单向链表插删方便，但检索最差要扫整条链
    - 为了页内快速查找，有**页目录**
      - 页目录里是各个槽（分组），主键有序
      - 先对槽做二分，再落到槽内顺着链表找具体记录

  - 两套「链表」不要混：

    - **页 ↔ 页**：文件头指针，**双向**链表（方便范围扫相邻页）
    - **行 ↔ 行**：记录头 `next_record`，**单向**链表（方便页内插删）

- **第 3 层：行格式 = 一条记录在 User Records 里的字节布局**

  - 行格式就是「存储一条记录」的格式；它回答的是：在用户记录区里，**这一行**从左到右怎么排

  - InnoDB 提供 4 种行格式：Redundant、Compact、Dynamic、Compressed

    - Redundant：MySQL 5.0 之前，现在基本不用
    - Compact：紧凑行格式，让一页能多塞些行；MySQL 5.1 起一度默认 Compact
    - Dynamic、Compressed：在 Compact 基础上改进；MySQL 5.7 起默认 Dynamic
    - Dynamic / Compressed 与 Compact 的骨架相近，主要差别在大字段「行溢出」时页内留多少数据（详见同目录下「行溢出」相关笔记）

  - Compact 行格式：一条记录分「记录的额外信息」和「记录的真实数据」

    - 记录的额外信息

      - **变长字段长度列表**
        - 变长字段（varchar、TEXT、BLOB 等）实际长度不固定，要把占用大小记下来，读的时候才知道读多长
        - 只有表里有变长字段时才出现
        - 变长字段真实占用字节数**逆序**放进这个列表
          - 允许存储的最大字节 ≤ 255：用 1 字节表示长度；> 255：用 2 字节
        - 为什么逆序：
          - 记录头里「下一条记录」指针，指向下一条「头部信息」和「真实数据」之间的位置
          - 逆序后，真实数据和对应字段长度信息更容易落在同一 CPU Cache Line，提高命中率
          - NULL 值列表同理逆序

      - **NULL 值列表**（至少 1 字节）
        - 表中允许为 NULL 的列，每个对应一个 bit；1 表示该列是 NULL，0 表示不是
        - 必须按整数个字节对齐；不够的高位补 0；超过 8 个可空列就再加字节
        - 只有表里存在允许 NULL 的列时才出现
        - NULL 列在真实数据区**不占空间**

      - **记录头部信息**（5 字节）
        - `delete_mask`：是否删除（delete 往往先打标记，不立刻物理清掉）
        - `next_record`：下一条记录位置（页内单向链表）
        - `record_type`：
          - 0：普通记录
          - 1：B+ 树非叶子节点记录（目录项）
          - 2：最小记录
          - 3：最大记录
        - 说明：非叶子页上的目录项，也是「记录」，只是类型和内容不同，不是另一套完全无关的格式

    - 记录的真实数据

      - `row_id`（6 字节）
        - 建表时指定了主键或唯一约束列 → 没有 `row_id`
        - 都没指定 → InnoDB 自动加隐藏 `row_id`
      - `trx_id`（6 字节）：事务 ID，这条数据由哪个事务生成
      - `roll_pointer`（7 字节）：指向上一个版本（和 undo / MVCC 相关）
      - 各列真实数据（按列定义依次存放；NULL 列跳过）

  - 和「数据页七段结构」的关系：
    - 行格式描述的，是塞进 **User Records** 里的那一段字节
    - 页头、页目录、文件头等是页级外壳，不属于某一行的 Compact 布局

- **第 4 层：很多页组成 B+ 树（怎么跨页定位）**

  - 记录多了要多个数据页，就要靠索引定位「记录在哪一页」
  - 磁盘 IO 次数对效率很关键，所以用「矮胖」的 B+ 树：层数少 → IO 少，且利于范围查询

  - InnoDB 的 B+ 树

    - **每个节点都是一个数据页**
    - 只有叶子节点存放「真正要查的数据内容」；非叶子节点只放目录项当索引
    - 非叶子分层，降低每层搜索量
    - 同一层节点按索引键有序，并用双向链表串起来，方便范围查询

  - 聚簇索引

    - 叶子节点存的是**完整行**（按上面的行格式编码）
    - 一个表只有一个聚簇索引
    - 对应表空间里的「数据段」主要养的就是这棵树的叶子页

  - 二级索引

    - 叶子节点存的不是完整行，而是**索引列 + 主键值**
    - 一个表可以有多个二级索引
    - 查询列都能在二级索引叶子里拿到 → **索引覆盖**，不必回表
    - 还缺列 → 拿主键再走聚簇索引取完整行 → **回表**

  - 按主键查一条记录的路径（把页结构 + B+ 树 + 行格式串起来）

    1. 从根页开始，用目录项二分，定位下一层该去哪一页
    2. 一层层往下，直到叶子页
    3. 在叶子页的**页目录**里二分，落到某个槽
    4. 顺着槽内记录的 `next_record` 单向链表，找到目标行
    5. 按该表的**行格式**解析这一行的额外信息 + 真实数据，读出各列

- **容易混在一起的点（对照表）**

  - 「Compact 行布局」和「数据页七段结构」
    - 前者是一行怎么排字节；后者是一页怎么装很多行
    - 行格式 ⊂ User Records

  - 「页有很多类型」和「B+ 树节点都是数据页」
    - undo 页、溢出页等也是页
    - 组成用户表 B+ 树、装用户记录的，主要是**数据页**

  - 「双向链表」和「单向链表」
    - 页与页：双向
    - 页内行与行：单向

  - 「索引段 / 数据段」和「叶子存数据 / 非叶子存目录」
    - 同一分层的两种说法：非叶 ↔ 索引段；叶 ↔ 数据段

  - `record_type = 1`（非叶子记录）
    - 目录项也是记录，走同一套「记录」思想，内容是索引键 + 子页指针，不是完整业务行

- **收束成一句**

  - `.ibd` 里按段、区分配出许多 16KB 页；这些页组成 B+ 树；每个节点是一页；叶子页的 User Records 里按 Compact / Dynamic 等行格式存放字节；页内用单向链表 + 页目录找行，页间用双向链表 + 上层目录项找页；聚簇叶子是整行，二级叶子是键 + 主键。
