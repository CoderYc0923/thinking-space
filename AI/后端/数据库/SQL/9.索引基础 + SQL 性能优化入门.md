## 前置说明

1. 前置约定数据表：`student(id主键, name, phone, class_id, score)`
2. 主键 id：BIGINT PRIMARY KEY



## 一、索引基础原理

### 索引是什么

1. 索引是**有序的数据结构**，作用：避免全表扫描，快速定位行。
2. 类比：书本目录，根据标题快速找到页码，不需要逐页翻阅。
3. InnoDB 默认索引结构：**B + 树**
   - 区分：
     - B 树：节点同时存索引 + 数据
     - B + 树：只有**叶子节点存储完整数据**；**非叶子节点只存索引键**，多路分支，磁盘 IO 更少，范围查询极强
4. B + 树核心特性（必背）
   - 所有叶子节点通过双向链表相连，**范围查询友好**（`> < BETWEEN LIKE 前缀匹配`）
   - 非叶子节点只存索引 key，内存可以缓存更多索引，减少磁盘 IO
   - 数据全部在叶子节点；查询路径长度稳定



### InnoDB 两大索引类型

1. 聚集索引（主键索引）

   - 每张表**只能有一个聚集索引**
   - 叶子节点 = **完整一行数据**
   - 索引排序和物理数据存储顺序一致
   - 规则：
     - 表定义 PRIMARY KEY → 主键作为聚集索引
     - 无主键，选取第一个唯一非空索引作为聚集索引
     - 无主键、无唯一索引：InnoDB 自动生成隐藏 6 字节 `row_id` 作为聚集索引
     - 开发规范：**所有业务表必须设置主键，推荐 BIGINT 自增主键**

2.  二级索引（普通索引、联合索引、唯一索引）

   - 叶子节点**不存完整数据**，只存储：索引列值 + **主键 ID**

   - 重点概念：**回表查询**

     - 使用二级索引找到主键 ID，再拿着主键去聚集索引读取完整行数据，这个过程叫**回表**

   - 查询流程演示：

     - ```sql
       SELECT name,score FROM student WHERE phone='13800138000';
       -- 1.通过 phone 二级索引找到对应主键 id
       -- 2.根据 id 去聚集索引取出整行数据 → 回表
       ```

3. **覆盖索引（优化神器！高频面试）**

   - 查询需要的**所有字段全部包含在二级索引内**，不需要回表，直接从索引叶子拿到全部数据

   - ```sql
     -- 创建联合索引
     CREATE INDEX idx_phone_name ON student(phone, name);
     
     -- 覆盖索引，无需回表
     SELECT phone,name FROM student WHERE phone='13800138000';
     ```

   - 优化口诀：**尽量建立覆盖索引，消灭回表**



### 联合索引 & 最左匹配原则（重中之重）

1. 创建联合索引

   ```sql
   CREATE INDEX idx_class_score ON student(class_id, score);
   ```

   - 索引排序规则：先按`class_id`排序，class_id 相同再按`score`排序

2.  **最左前缀匹配原则**

   - 查询条件必须匹配索引最左侧起始字段，索引才能生效

   - 索引：`(a,b,c)`

     - 注意：MySQL 优化器会自动调整 WHERE 条件顺序，不用手动调换 a,b 顺序！

     - | SQL 条件                  | 索引是否生效                  | 生效部分 |
       | ------------------------- | ----------------------------- | -------- |
       | where a=?                 | ✅                             | a        |
       | where a=? AND b=?         | ✅                             | a,b      |
       | where a=? AND b=? AND c=? | ✅                             | a,b,c    |
       | where b=?                 | ❌ 失效                        | 无       |
       | where a=? AND c=?         | ✅ 仅 a 生效，c 无法走索引排序 | a        |



### 索引失效经典场景（日常踩坑大全）

1. **字段隐式类型转换**（最高频坑）

   - ```sql
     -- phone varchar类型
     WHERE phone = 13800138000; -- 字符串和数字对比，索引失效
     ```

   - 原理：`CAST(phone AS SIGNED)=138xxxx`，索引列被函数包裹

2. 索引列使用函数、运算

   - ```sql
     WHERE YEAR(create_time) = 2026; -- ❌失效
     WHERE create_time >= '2026' AND create_time < '2027'; ✅
     WHERE score + 10 > 90; -- ❌失效
     WHERE score > 80; ✅
     ```

   - 优化：等式变换，不要给索引列加计算

3. `LIKE '%关键词'` 后置通配符

   - ```sql
     WHERE name LIKE '%阳'; -- ❌失效
     WHERE name LIKE '程%'; -- ✅前缀匹配，可以走索引
     ```

4. 使用 `OR`，两侧字段不能同时命中索引

   - 解决方案：改用 UNION ALL 拆分 SQL
   
5. NOT、!=、<>、NOT IN

   - 优化器判定命中行数多，大概率放弃索引走全表扫描（不绝对，看数据分布）

6. 隔离级别 RC 下，普通索引等值查询无法降级，额外间隙锁；属于锁范畴，顺带了解

7. 区分度太低不建索引：比如 gender 性别只有 0/1，索引意义极小，优化器直接放弃



### 索引分类汇总

1. PRIMARY KEY 主键索引（聚集索引）
2. UNIQUE 唯一索引（二级索引，值不能重复）
3. INDEX 普通索引
4. FULLTEXT 全文索引（业务很少用，优先 ES）



## 二、Explain 执行计划 + 索引设计规范 + SQL 调优实战

### Explain 使用方式

1. ```sql
   EXPLAIN SELECT * FROM student WHERE class_id=1;
   ```

2. 核心字段详解（按优先级）

   - **type**： 访问类型（性能标尺，从优到差排序）
     - **system**：系统表，几乎见不到
     - **const**：主键 / 唯一索引等值匹配，最多 1 行，最优
     - **eq_ref**：关联查询主键匹配
     - **ref**：普通索引等值查询
     - **range**：范围查询 > < BETWEEN IN
     - **index**：扫描整个索引树（比全表扫描略好）
     - **ALL**：❌全表扫描，必须优化
     - 生产最低目标：尽量达到 range/ref，杜绝 ALL
   - **key**：实际使用的索引；NULL = 没有使用索引
   - **key_len**：索引使用长度，判断联合索引用到了几列
   - **rows**：扫描预估行数，数值越小越好
   - **Extra 额外信息（重点标记）**：
     - `Using filesort` ❌ 文件排序，**没有利用索引排序，需要优化**
       - 原因：ORDER BY 字段不在索引中；违背最左前缀
     - `Using temporary` ❌ 使用临时表，常见 GROUP BY 无索引
     - `Using index` ✅ 覆盖索引，无回表，理想状态
     - `Using where`：服务器层过滤数据



### 索引设计黄金规范（开发落地准则）

1. 优先建立联合索引，遵循**最左前缀**，区分度高字段放前面
2. 避免创建过多索引：索引会减慢 INSERT/UPDATE/DELETE（索引需要维护）
3. 不建立低区分度字段索引（性别、状态少量枚举）
4. 尽量使用覆盖索引，消除回表
5. 自增主键，避免随机主键（UUID 主键导致页分裂，性能暴跌）
6. 字符串索引合理前缀索引 `INDEX idx_name (name(10))`，减少索引占用空间
7. 禁止在频繁更新的字段建立索引，频繁维护索引成本高



### 常见 SQL 优化实战方案

1. 禁止 `SELECT *`，只查询需要字段，利于触发覆盖索引，减少网络传输

2. 分页深度优化

   - ```sql
     -- ❌低效 LIMIT 100000,10
     -- ✅优化：主键书签定位
     SELECT * FROM student WHERE id > 100000 LIMIT 10;
     ```

3. JOIN 优化

   - 小表驱动大表
   - 关联字段必须建立索引
   - 避免多表笛卡尔积，不要超过 3 表 JOIN

4. IN 集合过大 (上千条) 性能差，分批查询

5. 尽量避免 `SELECT COUNT(*)` 大表统计；可使用缓存计数



### 坑点补充

1. UUID 不适合做主键：无序，造成 B + 树频繁页分裂，碎片多
2. MyISAM 没有聚集索引，数据和索引分离，不支持事务，新项目禁用
3. 联合索引顺序：等值条件放前面，范围条件放最后
   - 例：`WHERE class_id=? AND score>80`
   - 索引设计 `(class_id,score)`，不要反过来





## 三、思考题自测

1. InnoDB 一条 SQL 查询，二级索引查找完整过程？
   - 二级索引找到主键 → 回表，聚集索引通过主键获取完整行
2. 联合索引，范围字段为什么后面的列无法使用索引？
   - 范围查询后索引有序性被打破，后续字段无法利用索引有序性过滤
3. 什么是索引页分裂？自增主键如何避免？
   - 叶子节点空间不足，需要拆分页面；自增主键持续尾部追加，很少触发分裂
4. 覆盖索引为什么可以避免回表？
   - 需要查询的全部字段都在二级索引叶子节点，不需要访问聚集索引
