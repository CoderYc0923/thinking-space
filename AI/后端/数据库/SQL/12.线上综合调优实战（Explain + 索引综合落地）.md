## 一、复习：Explain 核心字段快速回顾

| 字段      | 重点关注值                                   | 问题表现                                           |
| --------- | -------------------------------------------- | -------------------------------------------------- |
| `type`    | system>const>eq_ref>ref>range>index>ALL      | 出现 `index`/`ALL` 代表全索引扫描 / 全表扫描，危险 |
| `key`     | 实际使用的索引                               | NULL = 没用到索引                                  |
| `key_len` | 索引使用字节长度                             | 越小越好；联合索引判断命中几个字段                 |
| `rows`    | 预估扫描行数                                 | 数值越大性能越差                                   |
| `Extra`   | Using filesort、Using temporary、Using where | filesort 文件排序；temporary 临时表，严重性能损耗  |

> 线上调优固定流程：
>
> 1. 慢查询日志拿到慢 SQL
> 2. `explain sql;` 看执行计划
> 3. 判断：有没有走索引？扫描行数？是否文件排序 / 临时表？
> 4. 修改 SQL / 新增 / 调整索引
> 5. explain 复看执行计划 + 实际压测验证耗时

## 二、场景 1：全表扫描 ALL，完全没走索引

1. 原始 SQL（线上慢 SQL）

   ```sql
   SELECT * FROM t_order WHERE order_no = 'ORD20260806001';
   ```

   - explain 结果：`type:ALL`，`key:NULL`，rows 很大
   - **问题根因**：`order_no` 没有建立索引

2. ✅修复：建立单列索引

   ```sql
   CREATE INDEX idx_order_no ON t_order(order_no);
   ```

   - explain：`type:ref`，key 显示 idx_order_no，rows 降到 1

3. ⚠️坑：字段类型隐式转换，有索引也不走！

   ````sql
   -- order_no是varchar字符串，条件传数字，发生隐式转换，索引失效
   SELECT * FROM t_order WHERE order_no = 123456;
   ````

   - 原理：索引列做函数运算，索引失效

   - 修复：传入字符串常量

     ```sql
     SELECT * FROM t_order WHERE order_no = '123456';
     ```



## 三、场景 2：联合索引最左匹配失效

1. 表：t_order，联合索引 `idx_user_status (user_id, order_status)`

2. ❌坏 SQL：跳过最左前缀 user_id

   ```sq;
   SELECT * FROM t_order WHERE order_status = 1;
   ```

   - explain：key NULL，type ALL，全表扫描
   - 联合索引最左原则：必须从索引第一个字段开始，不能跳字段

3. ✅正确写法：带上 user_id

   ```sql
   SELECT * FROM t_order WHERE user_id=10086 AND order_status =1;
   ```

   - 思考题：`where user_id=10086` 只使用第一个条件，会不会走索引？
   - 答：会，只使用联合索引的第一列

4. 坑：范围条件后面索引失效

   ```sql
   WHERE a=? AND b>100 AND c=?
   ```

   - b 是范围条件 `> < between`，**b 之后的 c 字段索引失效**，c 无法使用索引
   - explain 的 key_len 可以观察，只能用到 a+b，c 不会计入 key_len

   

## 四、场景 3：Extra: Using filesort 文件排序（高频线上问题）

1. filesort：**没有利用索引排序，MySQL 内存 / 磁盘做文件排序，数据量大直接卡死**

2. 表 t_order，索引只有 idx_user_id (user_id)

3. ❌慢 SQL

   ```sql
   SELECT * FROM t_order WHERE user_id = 1001 ORDER BY create_time DESC;
   ```

   - explain Extra：`Using filesort`
   - 原因：where 条件使用 user_id 索引，但是`create_time`不在索引中，排序无法利用索引，触发文件排序

4. 两种修复方案

   - 方案 1：建立联合索引，where + order by 字段顺序匹配

     ```sql
     CREATE INDEX idx_user_createtime ON t_order(user_id,create_time);
     ```

     - where 条件字段在前，排序字段在后。此时排序直接走索引有序性，消除 filesort

   - 方案 2：业务妥协，应用层排序（极少用）

5. 重要面试点：

   - ✅联合索引：where 条件和 order by 字段顺序一致，升序降序保持统一，避免 filesort
   - ❌如果 where 用 a，order by b，a 和 b 不在同一个索引，大概率 filesort



## 五、场景 4：Extra: Using temporary 使用临时表

1. 出现 `Using temporary`：MySQL 创建临时表，一般发生在 **group by、distinct、多表 join**

2. 千万级大表出现临时表性能灾难。

3. 示例：无合适索引导致 group by 生成临时表

   ```sql
   SELECT order_status,count(*) FROM t_order GROUP BY order_status;
   ```

   - explain Extra：`Using temporary; Using filesort`

4. ✅修复：给 group by 字段建立索引

   ```sql
   CREATE INDEX idx_status ON t_order(order_status);
   ```

   - group by 尽量走索引，避免内存临时表溢出落到磁盘
   - 经验：如果 Extra 同时出现 `Using temporary + Using filesort`，属于严重慢 SQL



## 六、场景 5：join 关联查询调优（线上最常见）

1. 两张表：

   - t_order (千万)：order_id,user_id
   - t_user (十万)：user_id,username

2. join 优化黄金准则：**小表驱动大表**，`小表作为驱动表`

   - join 原理：Nested‑Loop Join，驱动表每一行，去被驱动表查询
   - **被驱动表 join 字段必须加索引！**

3. ❌错误写法：大表驱动小表

   ```sql
   SELECT * FROM t_order o LEFT JOIN t_user u ON o.user_id = u.user_id;
   ```

   - left join：左边 t_order 是驱动表（千万级），循环千万次去查 t_user
   - left join 注意：左表驱动右表，右表关联字段必须建索引

4. ✅修复：给被驱动表 t_user.user_id 建立索引

   ```sql
   CREATE INDEX idx_uid ON t_user(user_id);
   ```

   - explain 看 join：
     - 驱动表 type 尽量 range/ref
     - 被驱动表 type 最好 eq_ref/ref
   - 面试必背：left join 和 inner join 选择驱动表区别:
     - LEFT JOIN：左表一定驱动表，无法优化顺序，**右表关联字段务必建索引**
     - INNER JOIN：MySQL 优化器自动选择小表做驱动表



## 七、场景 6：select * 大坑，回表过多

1. 索引 `idx_user_id(user_id)`

   ```sql
   SELECT * FROM t_order WHERE user_id=1001;
   ```

   - `idx_user_id`是二级索引，只存 user_id + 主键 id；
   - 查询`*`需要拿着主键 id 回表读取完整行数据
   - 数据量大，大量回表 IO，性能下降

2. ✅覆盖索引：查询字段全部放进索引，**消除回表，Extra 出现 Using index**

   ```sql
   -- 只查需要字段，建立联合覆盖索引
   CREATE INDEX idx_user_cover ON t_order(user_id,order_no,create_time);
   SELECT user_id,order_no,create_time FROM t_order WHERE user_id=1001;
   ```

   - explain Extra：`Using index` → 覆盖索引，不需要回表，性能极高。
   - `Using index` = 好现象，覆盖索引；
   - `Using index condition` = 索引下推 ICP，MySQL5.6 + 特性，部分过滤，不是覆盖索引



## 八、场景 7：深度分页 limit offset 调优（复习巩固）

1. 千万表

   ```sql
   SELECT * FROM t_order ORDER BY id LIMIT 1000000,10;
   ```

   - offset=100 万，MySQL 扫描 1000010 行，丢弃前 100 万行

2. ✅方案 1：延迟关联

   ```sql
   SELECT o.* FROM t_order o INNER JOIN (SELECT id FROM t_order ORDER BY id LIMIT 1000000,10) t ON o.id = t.id;
   ```

3. ✅方案 2：书签分页（业务侧不允许跳页码，只允许上一页下一页，传上一页最大 id）

   ```sql
   SELECT * FROM t_order WHERE id > 1000000 ORDER BY id LIMIT 10;
   ```

   - 业务如果必须支持任意页码跳转，MySQL 本身很难，需要 ES 搜索引擎。



## 九、线上调优完整实操案例（模拟工作真实流程）

1. 收到告警：慢查询，SQL 如下

   ```sql
   SELECT * FROM t_order WHERE user_id = 23456 AND order_status IN(1,3) ORDER BY create_time DESC LIMIT 20;
   ```

   - `explain`执行输出：`type:ref`，key:idx_user_id，Extra：`Using filesort`

2. 分析：

   - 现有索引只有`idx_user_id(user_id)`
   - where 用到 user_id，order_status 没有进索引；排序 create_time 触发 filesort。

3. 设计联合索引：

   - where 条件：user_id，order_status；排序：create_time

   - 索引顺序：**等值条件放前面，排序字段放最后**

   - ```sql
     CREATE INDEX idx_user_status_ctime ON t_order(user_id,order_status,create_time);
     ```

4. 再次 explain 校验:

   - type:ref；Extra 不再出现 filesort；key_len 变长，索引全部命中

5. 执行 SQL 对比耗时，确认优化生效

   - 联合索引设计口诀：**等值优先，范围在后，排序放末尾**



## 十、索引设计避坑清单（工作写索引前自查）

1. 不要建立过多索引，写操作 (insert/update/delete) 会维护全部索引，索引越多写入越慢
2. 区分度极低字段不要建索引，例如性别 status (0/1)，区分度差，索引几乎无效
3. 避免索引列运算、函数、隐式转换，索引失效
4. 联合索引遵守最左匹配，范围条件后面字段失效
5. order by/group by 尽量利用索引有序性，消灭 filesort/temporary
6. 优先使用覆盖索引减少回表 IO
7. join 被驱动表关联字段必须建索引
