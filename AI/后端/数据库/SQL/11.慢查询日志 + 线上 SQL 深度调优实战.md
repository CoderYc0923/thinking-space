## 一、慢查询日志 + MySQL 性能诊断工具

### 慢查询日志 slow_query_log

1. 作用：自动记录**执行时间超过阈值**的 SQL，是排查慢 SQL 第一入口。

2. 核心配置参数（my.cnf/my.ini）

   ```ini
   # 开启慢查询日志
   slow_query_log = ON
   # 日志文件路径
   slow_query_log_file = /var/lib/mysql/slow.log
   # 执行超过该时间(秒)就记录，浮点支持小数，0.5代表500ms
   long_query_time = 1
   # 记录没有使用索引的SQL（开发环境建议开启，生产酌情）
   log_queries_not_using_indexes = ON
   # 不要记录管理语句（OPTIMIZE、ALTER等）
   log_slow_admin_statements = OFF
   ```

3. 在线动态效果（无需重启MySQL，临时调试）

   ```sql
   SET GLOBAL slow_query_log = 1;
   SET GLOBAL long_query_time = 0.5;
   ```

4. ⚠️注意：`GLOBAL`变量修改后，**新建立的数据库连接生效**，当前已存在会话不生效



### 慢日志分析工具

1. 自带工具 mysqldumpslow（简易分析）

   ```bash
   # 按总耗时降序，展示前10条慢SQL
   mysqldumpslow -s t -t 10 slow.log
   # 按执行次数排序
   mysqldumpslow -s c -t 10 slow.log
   ```

   - `-s t`：按执行时间排序
   - `-s c`：按执行次数排序
   - `-s l`：按单次耗时排序
   - `-t n`：展示 top n 条

   缺点：功能简陋，生产推荐 **pt-query-digest**

2. pt-query-digest（Percona Toolkit，生产标准工具）

   - 业界主流，统计吞吐量、平均耗时、95% 耗时、锁等待时间

   - ```bash
     pt-query-digest slow.log > slow_report.txt
     ```



### 实时诊断工具

1. SHOW FULL PROCESSLIST

   - 查看当前所有数据库连接、正在执行 SQL、阻塞状态

   - ```sql
     SHOW FULL PROCESSLIST;
     ```

   - 重点观察 `State` 字段高频状态：

     - `Waiting for table metadata lock` → **MDL 锁阻塞（重大线上坑）**
     - `Waiting for row lock` → 等待行锁，事务争抢
     - `Creating sort index` → 需要排序，大概率 Using filesort
     - `Sending data` → SQL 大量扫描数据

2. SHOW PROFILE（SQL 耗时精细拆解）

   - 用来定位一条 SQL 时间消耗在：磁盘 IO、排序、锁、网络传输

   - ```sql
     SET profiling = 1;
     -- 执行目标SQL
     SELECT * FROM student WHERE class_id = 1;
     -- 查看概要
     SHOW PROFILE;
     -- 查看详细IO\CPU
     SHOW PROFILE CPU,BLOCK IO FOR QUERY 1;
     ```

3. Performance Schema（MySQL 内置监控框架）

   - 长期监控、等待事件、锁等待溯源，适合持续观测，入门先了解即可





## 二、线上综合调优实战 + MDL 锁、大事务、经典踩坑

### MDL 元数据锁 Metadata Lock【线上最高频事故源头】

1. 核心规则（必背）

   - MySQL 5.7/8.0，**只要访问表（SELECT / DML）都会申请 MDL 读锁**
   - DDL 语句（ALTER、DROP、RENAME）申请**MDL 写锁**
   - MDL 锁：**事务结束后才释放，不是语句执行完释放！**
   - MDL 读写锁互斥：读锁与读锁兼容；写锁和所有锁互斥

2. 经典雪崩场景（真实线上事故）

   - 会话 A：

   - ```sql
     BEGIN;
     SELECT * FROM student WHERE id = 1;
     # 持有sutdent表MDL读锁，事务没有提交
     ```

   - 会话 B（执行 DDL）：

   - ```sql
     ALTER TABLE student ADD COLUMN age INT;
     # 尝试获取MDL写锁 -> 阻塞
     ```

   - 会话 C、D、E…… 任何查询 student 表的 SQL：

   - ```sql
     SELECT name FROM student;
     # 需要申请MDL读锁，被会话B阻塞，全部排队
     # 连接池迅速打满 -> 服务雪崩
     ```

3. ✅规避方案

   - 业务低峰执行 DDL
   - 禁止长事务运行期间执行表结构变更
   - 使用**在线无锁改表工具**：pt-online-schema-change` / `gh-ost
     - 原理：新建临时表，增量同步数据，避免长时间持有 MDL 写锁



### 大事务危害与优化准则

1. 什么是大事务：
   - 单次事务更新大量数据
   - 事务执行时间很长（中间包含网络等待、业务逻辑）
2. 危害：
   - 持有行锁时间变长，引发大量阻塞、死锁
   - Undo 日志持续膨胀，磁盘占用上涨
   - Binlog 体积巨大，**主从复制延迟飙升**
   - 崩溃恢复耗时增加
3. 优化准则：
   - 事务尽量短小，快速提交
   - 大批量更新拆分成分批小事务
   - 不要在事务中调用外部接口、sleep、复杂业务逻辑



### 批量 SQL 优化

❌反模式：应用循环逐条 Insert

```java
// java循环单次插入1000次，频繁网络往返
for() {
    insert into student values(...)
}
```

✅优化 1：批量插入

```sql
INSERT INTO student(name,class_id)
VALUES ("张三",1),("李四",1),("王五",2);
```

✅优化 2：超大量数据导入使用 `LOAD DATA INFILE`



### IN 查询、NOT IN 避坑

1. IN 集合元素数量 > 1000，性能显著下降，建议拆分多次查询\

2. NOT IN 子查询存在 NULL 值时，查询结果为空！

3. ```sql
   WHERE id NOT IN (SELECT student_id FROM score);
   -- 如果student_id存在NULL，整条查询返回空
   ```

4. ✅替代方案：优先使用 `NOT EXISTS`



### SELECT * 为什么不推荐（面试常问）

1. 读取不必要字段，增加磁盘 IO、网络传输
2. 无法触发**覆盖索引**，被迫回表查询
3. 表新增字段后，程序接收字段异常，兼容性风险



### 分页深度优化

1. ❌低效写法：

   ```sql
   SELECT * FROM student LIMIT 100000, 10;
   ```

   原理：数据库扫描前 10 万行，丢弃，再取 10 行，扫描行数巨大。

2. ✅书签分页优化（主键有序场景）

   ```sql
   SELECT * FROM student WHERE id > 100000 LIMIT 10;
   ```

   局限：不能支持随意跳页，适合滚动分页；后台跳转页码场景需要其他方案

3. 后台支持【任意页码跳转】解决方案

   - **管理后台：支持直接跳第 10000 页** → 书签分页失效！因为不知道上一页最大 ID。

   - 原始低效 SQL：

     ```sql
     SELECT name,score FROM student ORDER BY score DESC LIMIT 99990,10;
     ```

     底层：扫描前 99990 行，丢弃，取出后 10 行，偏移量越大越慢。

   - 方案 1：延迟关联（MySQL 最优原生方案，无需中间件）

     - 核心思路：先通过覆盖索引只分页查出主键 ID（不需要回表，速度极快），再用 ID 关联查询完整数据

     - ```sql
       SELECT s.*
       FROM student s
       INNER JOIN (
           SELECT id FROM student ORDER BY score DESC LIMIT 100000,10
       ) t ON s.id = t.id
       ORDER BY s.score DESC;
       ```

     - 原理

       - 子查询仅访问索引，没有回表，大量减少 IO；
       - 只拿到 10 条目标主键，再一次性查询完整数据。

     - ⚠️局限：

       - 依然需要扫描偏移行，只是开销大幅降低；偏移量几十万以上，依然会变慢。适合**几万以内偏移量**。

   - 方案 2：主键范围分页 + 页面缓存（业务改造，最推荐落地）

     - 业务限制改造（产品层面配合）
     - 不允许用户直接跳转到超大页码，例如：最多允许跳转至 5000 页
     - 超过 5000 页，提示「请筛选条件缩小范围」
     - 配套：查询时**强制增加筛选条件**（时间范围、状态）缩小数据集。

   - 方案 3：预计算分片 / 索引书签（适合超大表）

     - 如果必须支持百万级偏移跳转：
     - 根据排序字段，定期预生成分段节点；例如按 score 分段，记录 `score=90` 大概是第 30000 条；
     - 用户跳页时，先定位分段起点，再用 `score < ? LIMIT ...` 缩小偏移。
     - 缺点：维护成本高，排序条件变更需要重新维护节点。

   - 方案 4：脱离 MySQL，使用 Elasticsearch

     - ES 天然深度分页优化方案：
       - `from/size` 同样有深度分页问题
       - ES 推荐方案：**Search After**（等价书签分页）
       - 如果需要任意跳页：使用 `Composite 聚合分页` 或者开启游标
     - 适用场景：大数据量报表、商品后台、海量日志检索。

   - 方案 5：禁止 COUNT (*) 总条数（配套优化！很多人忽略）

     - 后台分页一般同时执行两条 SQL：

     - ```sql
       -- 1. 获取数据 LIMIT offset,size
       -- 2. SELECT COUNT(*) FROM student 计算总条数，渲染页码
       ```

     - 大表 COUNT (*) 非常慢！

     - 优化手段：

       - 缓存总数量，不必实时
       - 不展示精确总数，显示「>10000 条」
       - 用户翻页时动态加载，不一次性算出总记录
