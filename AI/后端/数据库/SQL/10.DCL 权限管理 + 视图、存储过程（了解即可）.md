## 说明

1. DCL：Data Control Language 数据控制语言，用户、权限、运维管理语法
2. 视图 (View)：虚拟表，日常开发少量使用；了解优缺点
3. 存储过程 / 自定义函数：**互联网后端开发极少推荐使用**，做到看得懂、会调用，不建议大量编写



## 一、DCL 权限管理

`CREATE USER` 创建用户、`GRANT` 授权、`REVOKE` 回收权限、`DROP USER` 删除用户、`ALTER USER` 修改密码

### 创建数据库用户

1. ```sql
   CREATE USER '用户名'@'访问主机' IDENTIFIED BY '密码';
   ```

2. 主机说明

   - `'root'@'localhost'`：仅本机登录
   - `'user'@'192.168.1.%'`：192.168.1 网段所有机器
   - `'user'@'%'`：**任意远程地址（生产谨慎使用，安全性低）**

3. 示例

   ```sql
   -- 创建账号，只能本机访问
   CREATE USER 'dev'@'localhost' IDENTIFIED BY 'Dev@123456';
   -- 允许任意地址访问
   CREATE USER 'dev'@'%' IDENTIFIED BY 'Dev@123456';
   ```



### GRANT 授予权限

常用权限清单：

1. `SELECT,INSERT,UPDATE,DELETE` 增删查改
2. `CREATE,ALTER,DROP` 建表、改表、删表
3. `ALL PRIVILEGES` 所有权限（除授权权限）

语法模板

```sql
GRANT 权限列表 ON 数据库.表 TO '账号'@'主机';
```

示例

```sql
-- 给dev账号，test库所有表 查询、新增、修改、删除权限
GRANT SELECT,INSERT,UPDATE,DELETE ON test.* TO 'dev'@'%';
-- 授予全部权限
GRANT ALL PRIVILEGES ON test.* TO 'dev'@'%';
-- *.* 代表所有数据库所有表
GRANT SELECT ON *.* TO 'read_user'@'%';
```

⚠️ MySQL8.0 不再支持`GRANT ... CREATE USER`隐式创建用户，必须先`CREATE USER`再授权！



### 刷新权限（重要）

修改权限后生效

```sql
FLUSH PRIVILEGES;
```



### REVOKE 回收权限

```sql
REVOKE INSERT,UPDATE,DELETE ON test.* FROM 'dev'@'%';
```



### 修改密码、删除用户

```sql
-- 修改密码
ALTER USER 'dev'@'localhost' IDENTIFIED BY 'NewPass@789';
-- 删除用户
DROP USER IF EXISTS 'dev'@'%';
```



### 查看权限

```sql
SHOW GRANTS FOR 'dev'@'%';
```



### 生产权限规范（面试 & 工作重点）

1. 禁止应用账号使用 `ALL PRIVILEGES`
2. 区分环境：开发账号、测试账号、生产只读账号、生产读写账号
3. 最小权限原则：程序只分配需要的权限，不需要 DROP、ALTER
4. 禁止生产使用 `root` 账号连接业务程序
5. 尽量限制访问 IP，杜绝 `user@%` 大范围开放





## 二、视图 VIEW、存储过程 PROCEDURE、函数 FUNCTION、触发器 TRIGGER

### 视图 VIEW

1. 什么是视图

   - 视图是**保存好的 SELECT 查询语句**，一张虚拟表；本身不存储数据，每次查询视图都会执行底层 SQL

   - ```sql
     CREATE VIEW viewname AS queryviewname;
     ```

   - ```sql
     -- 创建视图：查询各班学生成绩
     CREATE VIEW v_class_student AS
     SELECT s.id,s.name,s.score,c.class_name
     FROM student s
     LEFT JOIN class c ON s.class_id = c.id;
     
     -- 使用视图，像查表一样
     SELECT * FROM v_class_student WHERE class_name='一班';
     ```

2. 修改 / 删除视图

   - ```sql
     ALTER VIEW v_class_student AS SELECT ...;
     DROP VIEW IF EXISTS v_class_student;
     ```

3. 视图优点

   - 简化复杂多表查询，对外屏蔽多表 JOIN 细节
   - 权限控制：只开放视图，不开放原始表，隐藏敏感字段（手机号、身份证）

4. 视图巨大缺点（互联网项目很少用）

   - **无法优化底层 SQL**；视图嵌套多层极易性能爆炸
   - Explain 很难追踪视图内部执行计划
   - MySQL 视图不支持索引，底层查询无法缓存优化
   - 业务变更，视图很难维护
   - 行业共识：新项目尽量**不用视图**，应用层编写 SQL 替代



### 存储过程 PROCEDURE

存储过程：数据库内部预先编写好的一段 SQL 逻辑，支持变量、判断、循环，一次编译多次调用。

简易示例

```sql
DELIMITER // -- 修改语句结束符，避免;提前终止
CREATE PROCEDURE GetStudentByClass(IN cid INT)
BEGIN
	 SELECT * FROM student WHERE class_id = cid;
END //
DELIMITER ;

-- 调用存储过程
CALL GetStudentByClass(1);
```

互联网公司为什么不推荐存储过程（面试高频）

1. **业务逻辑耦合在数据库**，难以调试、版本管理、灰度发布
2. 数据库压力上升，数据库是集群瓶颈，算力应该交给应用服务器
3. 无法做分布式、分库分表场景适配
4. 难以迁移数据库（MySQL 迁移 PostgreSQL 存储过程全部重写）
5. 排障困难，日志、监控不好处理

适用场景：传统政企项目、数据定期统计报表；**互联网后端尽量避免**



### 自定义函数 FUNCTION

1. 和存储过程区别：

   - 函数必须有返回值，可以写在 SELECT 后面；

   - 存储过程使用 CALL 调用，支持多个出入参。

   - ```sql
     DELIMITER //
     CREATE FUNCTION CalcAvgScore(cid INT) RETURNS DECIMAL(5,2)
     BEGIN
     	DECLARE avg_s DECIMAL(5,2);
         SELECT AVG(score) INTO avg_s FROM student WHERE class_id=cid;
         RETURN avg_s;
     END //
     DELIMITER ;
     
     -- 使用
     SELECT CalcAvgScore(1);
     ```

   - ⚠️风险：WHERE 条件调用自定义函数极易造成索引失效



### 触发器 TRIGGER（了解）

1. 在表发生 INSERT/UPDATE/DELETE 时，自动执行一段 SQL

2. 典型场景：数据变更自动记录日志、数据备份。

3. 缺点：隐形逻辑，开发很难感知，故障排查地狱，**生产尽量禁用**。

4. ```sql
   -- 简单示例（了解即可，不建议实战使用）
   CREATE TRIGGER tri_student_update
   BEFORE UPDATE ON student
   FOR EACH ROW
   BEGIN
       -- 自动写入操作日志
   END;
   ```



### 思考

1. 简答：视图本质是什么？互联网项目为什么尽量避免使用视图？
   - 视图本质是一条持久化的 SELECT 语句，虚拟表，不存储数据；
   - 弊端：多层嵌套性能差、难以调优、业务耦合在数据库，难以维
2. 简答：存储过程优缺点，互联网项目为什么不推荐大量使用？
   - 优点：SQL 预编译，减少网络传输；适合大批量统计任务
   - 缺点：业务逻辑下沉数据库，数据库压力大，难以版本控制、不方便迁移、调试困难
3. 视图可以建立索引吗？MySQL 视图底层能否优化？
   - MySQL 普通视图不能建立索引；查询视图等价直接执行原始 SQL，优化器能力有限。
4. IN 和 OUT 参数分别在存储过程代表什么？
   - IN：传入参数；OUT：向外输出结果。
5. 触发器有什么隐藏风险？
   - 触发器逻辑隐式触发，开发无感知，出现数据异常很难定位根源。
