## 说明

1. TCL：Transaction Control Language 事务控制语言
2. 仅 **InnoDB 引擎支持事务**；MyISAM 不支持事务，这也是生产环境默认选用 InnoDB 的核心原因
3. 复用 student、score 测试表；所有案例均可直接执行测试



## 一、什么是事务

事务是一组**不可分割的SQL操作**，这一组SQL要么**全部执行成功**，要么**全部失败回滚**，不会出现中间状态。

典型场景：

- 转账：A扣钱，B加钱；不能出现A扣款成功，B收款失败。

### TCL核心指令

```sql
START TRANSACTION; -- 开启事务（推荐，等价于BEGIN）
BEGIN;

COMMIT; -- 提交事务，永久生效，数据落地
ROLLBACK; -- 回滚事务，撤销本次事务内所有修改

-- 可选：保存点（局部回滚）
SAVEPOINT point1;
ROLLBACK TO point1;
```

### 基础演示示例

```sql
-- 开启事务
START TRANSACTION;
UPDATE student SET score=90 WHERE id=1;
UPDATE student SET score=85 WHERE id=2;

-- 此时打开另一个数据库窗口查询：看不到修改的数据！

-- 二选一执行
COMMIT; -- 提交：所有人可见修改
-- ROLLBACK；-- 回滚：两条UPDATE全部作废

```

- 触发**自动提交**，事务会直接结束，无法回滚；
- 默认MySQL的autocommit=ON，每条SQL自动单独事务
- DDL语句（CREATE/ALTER/DROP）执行时**会自动CIMMIT事务**，事务中不要执行建表改表语句





## 二、事务四大特性ACID（必背面试题）

1. **原子性Atomicity**
   - 事务内所有操作都是原子整体，全部成功/全部失败，不存在部分执行。
   - 由**undo log（回滚日志）**实现
2. **一致性Consistency**
   - 事务执行前后，数据完整性约束不会被破坏
   - 例：转账前后总金额不变；主键唯一、外键约束生效；
   - **原子性、隔离性、持久性共同保障一致性**
3. **隔离性Isolation**
   - 多个事务并发执行时，事务之间相互隔离，互不干扰
   - 由**MVCC + 锁**实现；**隔离级别就是用来控制隔离程度**
4. **持久性Durability**
   - 事务提交成功后，修改永久保存到磁盘，数据库宕机数据也不会丢失
   - 由**redo log（重做日志）**实现



## 三、并发事务带来的三大问题（由隔离不足导致）

假设有事务A、事务B并发运行

### 脏读  Dirty Read

- 一个事务读到了**另一个事务未提交的数据**
- 如果另一个事务最终回滚，独到的数据就是无效“脏数据”

### 不可重复度 Non-Repeatble Read

- 同一个事务内，**先后两次读取同一行数据**
- 中间被其他事务提交修改，两次查询结果不一致
- 重点：**同一行数据被UPDATE修改**

### **幻读  Phantom Read**

- 同一个事务内，先后执行相同条件范围查询
- 其他事务插入 / 删除满足条件的数据，导致前后查询行数不一样。
- 重点：**范围查询，新增/删除数据（INSERT/DELETE）**

简单区分：

- 不可重复读：行数据内容变了（update）
- 幻读：查询出来的条目数量变了(insert/delete)



## 四、MySQL InnoDB四种事务隔离级别（由低到高）

| 隔离级别                                      | 脏读  | 不可重复读 | 幻读        | 详解                                                         |
| --------------------------------------------- | ----- | ---------- | ----------- | ------------------------------------------------------------ |
| 1.READ UNCOMMITTED 读未提交                   | ✅允许 | ✅允许      | ✅允许       | 几乎不会使用，可以读到其他事务未提交数据，**存在脏读**       |
| 2.READ COMMITED 读已提交（RC）                | ❌禁止 | ✅允许      | ✅允许       | 只能**读取别人已经提交的数据**，**解决脏读**。同一事务内，两次查询，别的事务提交更新，数据会变化：**存在不可重复读** |
| 3.REPEATABLE READ 可重复读（RR）【MySQL默认】 | ❌禁止 | ❌禁止      | ✅* 特殊处理 | 事务开启后，多次读取到同一数据，结果保持一致。**依靠MVCC生成数据快照**。日常开发绝大数场景使用。 |
| 4.SERIALIZABLE 串行化                         | ❌禁止 | ❌禁止      | ❌禁止       | 最高隔离级别。事务串行执行，完全杜绝三类问题。性能很差，并发低，几乎业务不用 |

### 重点补充：

- MySQL InnoDB 默认隔离级别REPEATABLE READ(RR)
- 在RR级别，通过MVCC机制避免了幻读现象（快照读）；当前读下依然存在幻视风险
- Oracle默认隔离级别：READ COMMITED

### 实操命令

```sql
-- 查看当前会话隔离级别
SELECT @@transaction_isolation;
-- 设置当前会话隔离级别
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
-- 设置全局隔离级别（需要重启数据库生效）
SET GLOBAL TRANSACTION ISOLATION LEVEL REPEATABLE READ;
```



## 五、快照读 vs 当前读（理解 RR 隔离、MVCC 关键）

### 快照读（普通 SELECT）

- 不加锁，读取MVCC历史快照
- 普通SELECT * FROM student;
- RR级别下实现可重复读，规避幻读

### 当前读（加锁读取，读取最新数据）

- ```sql
  SELECT ... FOR UPDATE;
  SELECT ... LOCK IN SHARE MODE;
  UPDATE / DELETE
  ```

- 读取数据库最新已提交数据，会加行锁；RR级别下当前读仍会出现幻读



## 六、演示：保存点 SAVEPOINT（局部回滚）

```sql
START TRANSACTION;
UPDATE student SET score=60 WHERE id=1;
SAVEPOINT sp1; -- 创建保存点

UPDATE student SET score=60 WHERE id=2;

ROLLBACK TO sp1; -- 回滚到保存点，id=2的修改撤销，id=1保留

COMMIT;
```

保存点只在当前事务有效，commit/rollback 后全部消失



## 七、事务开发规范（生产避免）

- 事务尽量短小，不要在事务中执行网络请求、大量耗时逻辑；长事务占用锁，引发阻塞死锁
- 事务内禁止执行 DDL（ALTER/CREATE/DROP），会隐式提交
- 查询优先快照读；需要强一致性才使用 `FOR UPDATE` 行锁
- 避免大事务批量更新，防止锁范围过大
- 业务捕获异常必须手动 ROLLBACK；框架 (Spring) 依靠异常自动回滚



## 七、开发生产避坑清单（工作直接使用）

- 更新条件字段务必建立索引，防止行锁升级表锁
- 事务尽可能短小，禁止在事务中调用第三方 http 接口
- 统一多条 SQL 操作资源顺序，预防死锁
- 高并发扣库存优先使用原子 UPDATE，不要先查询后更新
- 不要滥用 `SELECT ... FOR UPDATE`，降低并发吞吐量
- 资金业务强一致性：悲观锁；商品秒杀：乐观锁



## 八、InnoDB锁体系分类

### 按锁粒度划分

1. #### 表级锁：锁住整张数据表

   - **表共享读锁（S 锁）** LOCK TABLES … READ
     - 多个事务可以同时加 S 锁，互相兼容
     - 持有 S 锁的事务，**禁止其他事务写操作**
   - **表排他写锁（X 锁）** LOCK TABLES … WRITE
     - 和所有锁互斥；只有持有锁的事务可读可写，其他事务阻塞
     - 注意：`LOCK TABLES` 是 MySQL 上层锁，**不推荐在 InnoDB 使用**，破坏 MVCC 事务机制

2. #### 行级锁（InnoDB 核心，粒度最小，并发最高）

   **行锁是加在索引上！重点！**如果更新条件没有命中索引 → InnoDB**行锁升级为表锁**（超级高频面试坑）

   - **共享行锁（S 锁 / 读锁）**
     - 语法：`SELECT * FROM student WHERE id=1 LOCK IN SHARE MODE;`
     - 规则：
       - 事务 A 加 S 锁，其他事务**可读（快照读），不能当前读更新**
       - S 锁与 S 锁兼容；S 锁和 X 锁互斥
   - **排他行锁（X 锁 / 写锁）**
     - 语法：`UPDATE / DELETE / SELECT ... FOR UPDATE`
     - 规则：
       - 持有 X 锁的事务：可读可写
       - 其他事务：**任何当前读操作全部阻塞**
       - X 锁与 S、X 锁全部互斥

3. #### 间隙锁 Gap Lock（RR 隔离级别特有）

   - 锁定**索引区间间隙**，锁住 “还不存在的数据”，防止其他事务插入数据，**解决幻读（当前读场景）**
   - 间隙内不存在真实记录。
     - 例：索引存在 id=1、id=5
     - 间隙区间：(-∞,1)、(1,5)、(5,+∞)
     - 事务锁住 (1,5)，其他事务不能插入 id=2、3、4

4. #### 临键锁 Next-Key Lock = 行锁 + 间隙锁

   - InnoDB RR 隔离级别下**默认行锁算法**
   - 锁定区间：左开右闭 (1,5]
   - 作用：同时锁住已有记录 + 两侧间隙，彻底阻止 INSERT 产生幻读

5. #### 意向锁 Intention Lock（意向共享 IS / 意向排他 IX）

   - **意向锁是表锁，是一种标记，不阻塞读写！**

   - 作用：快速判断表上是否存在行锁，避免逐个遍历行锁，提升效率

   - 规则：

     - 事务要加行 S 锁 → 先给表加 IS 意向共享锁
     - 事务要加行 X 锁 → 先给表加 IX 意向排他锁

   - 

   - |      | 表 S 锁 | 表 X 锁 | IS   | IX   |
     | ---- | ------- | ------- | ---- | ---- |
     | IS   | ✅兼容   | ❌互斥   | ✅    | ✅    |
     | IX   | ❌互斥   | ❌互斥   | ✅    | ✅    |



### 按照锁的实现方式区分

1. #### 悲观锁

   - 认为并发一定会冲突，操作前上锁
   - 对应：`FOR UPDATE、LOCK IN SHARE MODE、UPDATE、DELETE`（当前读）

2. #### 乐观锁

   - 认为冲突概率低，不加数据库锁；依靠版本号控制

   - 实现方案：增加 `version` 字段

   - ```sql
     UPDATE goods SET stock=stock-1,version=version+1
     WHERE id=1 AND version=1;
     ```

   - 更新前后版本不一致，说明已经被别人修改，更新失败

   - **乐观锁没有数据库锁开销，高并发抢购场景常用**





## 九、快照读 VS 当前读

### 快照读（不加锁）

1. 普通 `SELECT * FROM student;`
2. 读取 undo log 生成的历史快照，不加任何行锁，并发性能高
3. RR 级别：事务启动后第一次查询建立快照，全程快照不变 → 可重复读
4. RC 级别：每次 SELECT 都生成最新快照 → 不可重复读

### 当前读（加锁）

1. UPDATE / DELETE / SELECT ... FOR UPDATE / LOCK IN SHARE MODE
2. 读取磁盘最新数据，加行锁 / 临键锁。





## 十、MVCC 核心（多版本并发控制）

### 三大组件

1. **undo log：数据修改前的旧版本数据**
2. **read view：判断数据版本对当前事务是否可见**
3. **roll_pointer：每条记录指向旧版本的链表指针**

### 作用

1. 实现**不加锁的读**，读写不阻塞（快照读与写互不阻塞）
2. **写操作依然会加行锁**，写与写之间互相阻塞！





## 十一、死锁

###  死锁四大必要条件（全部满足才会死锁）

1. 互斥条件：锁互斥，资源不能共享
2. 请求保持：持有锁，同时申请新锁
3. 不可剥夺：锁不能被强行抢占
4. 循环等待：事务互相持有多方需要的锁，形成环路

### 死锁示例

1. 事务1

   - ```sql
     START TRANSACTION;
     UPDATE student SET score=90 WHERE id=1; -- 持有id1行X锁
     UPDATE student SET score=80 WHERE id=2; -- 持有id2锁（被事务2占用）
     ```

   - 

2. 事务2

   - ```sql
     START TRANSACTION;
     UPDATE student SET score=80 WHERE id=2; -- 持有id2行X锁
     UPDATE student SET score=90 WHERE id=1; -- 请求id1锁（被事务1占用）
     ```

   - 

3. 形成循环等待 → 死锁。

4. InnoDB 会自动检测，主动回滚代价较小的事务

### 死锁解决方案

1. **统一 SQL 资源访问顺序（最优方案）**，所有人先操作 id 小的数据
2. 缩小事务范围，事务尽量简短
3. 避免长事务
4. 必要时设置超时 `innodb_lock_wait_timeout`



## 十二、场景题

### REPEATABLE READ 下，快照读解决幻读，那当前读为什么还存在幻读？

RR 隔离级别下，**快照读读取历史快照，看不到其他事务新插入的数据，感受不到幻读**；但当前读读取最新数据，普通行锁只能锁住已存在记录，无法阻止间隙插入；依靠**临键锁 Next-Key Lock**锁住间隙，才能阻止插入，规避当前读幻读。

### 行锁什么时候会退化成表锁？

更新条件**没有索引 / 索引失效**（隐式类型转换、模糊查询 % 前缀、函数操作索引列）InnoDB 无法定位具体行，只能锁住整张表。

### SELECT * FROM t WHERE id=1 是否加锁？

普通 SELECT 快照读 **不加任何锁**；`SELECT ... FOR UPDATE` 当前读，加排他行锁；`LOCK IN SHARE MODE` 当前读，加共享行锁。

### 商品库存扣减有哪些方案？各自优缺点？

方案 1：`UPDATE goods SET stock = stock -1 WHERE id=? AND stock>0;` SQL 原子性，InnoDB 行锁保证并发安全

方案 2：Java 代码查询库存，判断后再更新。存在超卖！查询和更新中间存在时间窗口，并发出现超卖。解决方案：要么把查询 + 更新放进事务加 FOR UPDATE 悲观锁；要么乐观锁 version 版本号

### 悲观锁和乐观锁适用场景？

悲观锁：并发冲突高、数据一致性要求极高（资金交易），缺点并发性能差

乐观锁：冲突较少、高并发场景（商品秒杀），大量冲突时频繁重试，CPU 消耗高

### RC 和 RR 除了不可重复读，锁机制有什么区别？

RC 隔离级别**没有间隙锁，只有行锁**，无法阻止幻读

RR 默认使用 Next-Key 临键锁（行锁 + 间隙锁）防止幻读

RC 每次快照读都生成新 ReadView；RR 一个事务只生成一次 ReadView

### 线上频繁发生死锁，排查思路？

开启死锁日志 `innodb_print_all_deadlocks`，抓取死锁 SQL

检查 SQL 操作资源顺序是否不统一

检查是否存在大事务，事务执行时间过长

确认索引是否有效，防止行锁升级大范围锁

拆分大事务，减少锁持有时间

### 意向锁作用是什么，意向锁之间会互相阻塞吗？

意向锁只是标记，**意向锁之间不会互相阻塞**；

作用：快速判断表上是否存在行锁。

举例：想要加表 X 锁，先检查表有没有 IS/IX 意向锁；如果存在，说明表上存在行锁，直接阻塞，不需要遍历每一行

### DELETE 没有 WHERE 条件，加什么锁？

全表扫描，没有索引，行锁升级为**表排他锁**，整张表锁住

### Gap 间隙锁什么时候出现？

仅在 **REPEATABLE READ 隔离级别** 的当前读下存在；

RC 隔离级别不存在间隙锁。

### 同一个事务先后执行多条 `FOR UPDATE`，锁什么时候释放？

`SELECT ... FOR UPDATE` 属于**当前读**，执行语句时**立即申请锁**

所有行锁、临键锁、间隙锁，直到事务执行 **`COMMIT` 或者 `ROLLBACK`** 才统一释放！**同一条事务内部，语句执行完毕不会释放锁，锁持有周期 = 整个事务生命周期**

### 临键锁、间隙锁、行锁三者关系？

行锁 Record Lock：锁住**一条真实存在的数据行**

间隙锁 Gap Lock：锁住索引两条记录之间的**空隙区间**，区间内禁止插入新数据；

临键锁 Next-Key Lock：

- 临键锁 = 行锁 + 间隙锁，
- 间隙锁 **只在 RR 隔离级别存在，RC 级别没有间隙锁**，
- 左开右闭区间 `(上一条索引, 当前索引]`区间包含：间隙 + 当前真实行，也就是「间隙锁 + 行锁」组合

**优化降级规则（必考）**

- 当**唯一索引精准等值匹配（= 查询，命中唯一一条记录）**
- 临键锁会**降级**：临键锁 → 单纯**行锁**，间隙锁消失
- 范围查询（> < >= <=）不会降级，依旧使用临键锁

### 为什么 MySQL 默认 RR 隔离级别，而 Oracle 默认 RC？

MySQL InnoDB 在 RR 隔离级别通过临键锁消除了当前读的幻读，因此选用 RR 作为默认；

Oracle 没有间隙锁机制，RR 无法解决幻读，并且 RC 性能更好，所以默认 RC。

**补充拓展（面试官深挖加分项）**

RC 相比 RR：快照每次重建，锁粒度更小、冲突更少，并发性能更高；

MySQL 很多互联网公司线上主动调为 RC，换取更高并发，代价是需要业务层面处理幻读问题

**附带高频衍生思考题（自测）**

**RC 隔离级别有没有间隙锁？**

没有，RR才有

**普通 select 快照读加不加任何锁？**

不加，依靠mvcc；for update才是当前读加锁

**唯一索引等值查询和普通索引等值查询，锁降级逻辑一样吗？**

不一样，普通索引等值查询临键锁不会直接降级，会附带后端间隙锁
