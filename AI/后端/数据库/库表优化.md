## 面试版：大库、大表业务场景化优化（MySQL）

> 面试答题思路：先定义问题现象→分析产生的业务痛点→给出优化方案，按**成本由低到高**给出解决方案，说明选型取舍，讲清楚什么场景该用、什么场景不建议用。
>
> 经验阈值：大表一般千万行以上 /ibd 文件 10GB+；大库单实例总数据 100GB 以上。





## 一、场景 1：订单流水表，千万级大表，按时间持续增长，绝大多数查询只查近 3 个月数据，历史数据需要留存不能删除

1. 业务现象
   - 每日大量订单写入；线上业务几乎只访问近 3 个月热数据，半年以上历史数据极少查询；随着数据持续上涨，表体积越来越大。
2. 数据库痛点
   - DDL 加字段、加索引耗时很长，容易引发**主从延迟**
   - 不带时间条件统计查询性能差
   - 全量备份时间变长，binlog 量增大，加重主从复制压力
3. 优化方案（按优先级）
   - SQL 层：
     - 所有业务查询强制携带时间范围条件，杜绝无过滤条件全表扫描；
     - 精简索引，只保留业务查询必须的索引，减少写入开销
   - 架构层：
     - 采用 RANGE 按时间按月 / 日做分区。历史过期分区直接`drop partition`，秒级回收数据，不会产生大量 binlog 与 undo 日志，避免 delete 大批量删除带来的复制延迟问题
     - **分区表**本质还是单表，解决快速删除历史数据的问题，**不能解决单表超高并发写入瓶颈**，并发写压力上来后就要考虑分表
   - 业务层：
     - 把超过 6 个月的历史订单迁移至独立归档库；
     - 业务区分热/历史查询场景，历史订单查询入口做降级走归档库，不允许无时间条件导出全量历史
   - 运维层：
     - 大表DDL使用**gh‑ost/pt‑osc**，禁止线上直接alter table



## 二、场景 2：核心订单主表，亿级大表，新老数据都有读写，冷热数据混杂，无法简单按时间归档

1. 业务现象：
   - 订单主表，既有新下单，也会查询、更新很久之前的老订单，无法直接归档历史数据；
   - 读写 QPS 都很高，每秒大量请求，既有大量新增写入，同时又有大量查询、更新老数据
2. 数据库痛点：
   - 单表数据量过大，B + 树索引层级变深，查询、更新性能下降
   - DDL 风险极高，大事务容易造成主从延迟
   - 单表成为性能瓶颈，无法继续承接业务流量增长
3. 优化方案：
   - SQL层：
     - 拆分为大事务，大批量 update、delete 拆成分批小事务，降低主从延迟风险

   - 架构层：
     - 垂直拆分：
       - 大文本、备注、扩展这类低频访问大字段拆到附属子表，主表只保留高频核心字段减少行存储大小

     - 读写分离：
       - 查询流量下沉从库，热点更新继续走主库

     - 水平分表（压力持续上涨的话）：
       - 以订单 ID / 用户 ID 做分片键，使用 Sharding‑Sphere 做水平分片，打散单表数据压力
       - 水平分表会引入分布式事务、跨分片 join、跨分片分页排序等问题，业务要改造适配，不是银弹，数据量没到一定程度不优先上




## 三、场景 3：大表频繁删除更新，磁盘文件只涨不缩，大量碎片

1. 业务现象：

   - 业务大量逻辑删除、物理 delete，业务数据量下降，但 ibd 磁盘文件不会自动回收，磁盘占用居高不下，查询性能逐步变差

2. 痛点：

   - InnoDB delete 只打标记，空间内部复用，不会归还操作系统
   - 大量碎片会降低索引扫描效率

3. 优化方案：

   - SQL层：

     - 禁止一次性大批量delete；删除逻辑改为循环小批次删除提交。

   - 架构层：

     - 历史冷数据优先归档迁移，而不是直接 delete，减少本地表数据量，避免直接物理删除

   - 业务层：

     - 优先逻辑删除替代物理delete
     - 业务侧尽量避免高频大批量物理删除

   - 运维层：

     - 业务低峰执行`optimize table`重建表回收碎片，高峰期不要执行，会带来大量 IO 压力

     

## 四、场景 4：报表统计任务，大表 join，跑在线业务库，拖垮整个实例

1. 业务现象：

   - 后台运营报表，直接在线库做大表 join、group by、count 聚合，SQL 执行时间长，消耗大量 CPU、IO，影响线上业务

2. 优化方案：

   - SQL层：

     - 遵循小表驱动大表原则
     - 关联条件建立索引
     - 禁止select *****，裁剪返回字段**

   - 架构层：

     - 统计查询路由至从库
     - 超大规模统计，数据同步到数仓做离线分析，业务库只承担线上业务读写
     - **预计算**结果存入统计表，业务直接查询统计表
       - 预计算方案：通过定时任务把统计结果计算完成存入统计表，业务直接查询统计表，放弃实时聚合；
     - 不要为了报表去优化业务主库，统计类业务应该做业务隔离

   - 运维层：

     - 通过SQL限流，限制报表类SQL最大执行时间，防止打满实例

     

## 五、场景 5：大库问题：多个业务模块全部部署在同一个 MySQL 实例，单实例几百 GB，多张大表叠加

1. 业务现象：
   - 订单、用户、流水、配置全部放在同一实例；
   - 实例体量巨大
   - 一旦故障全部业务受影响，备份恢复耗时久
2. 痛点：
   - 业务之间资源互相抢占；单条慢SQL影响整个实例；备份恢复RTO高，主从复制压力大
3. 优化方案：
   - SQL层：
     - 各业务模块慢SQL专项治理，上线增加SQL审核，杜绝高危SQL
   - 架构层：
     - 大表归档、分区：
       - 大表优先做冷热归档
       - 分区，降低整体实例数据体量；
     - 读写分离：
       - 查询流量下沉从库，热点更新继续走主库
     - 业务分库分实例：
       - 按业务域拆分实例，订单实例、用户实例、配置实例物理隔离，业务之间资源互不影响
       - 分实例会增加运维成本，优先归档、优化SQL，资源冲突严重再拆分实例
   - 业务层：
     - 业务按领域做边界划分，不同业务流量做资源隔离规划
   - 运维层：
     - 使用xtrabackup物理备份，替代mysqldump逻辑备份；定期做备份恢复演练



## 六、场景 6：大库，写入量大，频繁出现主从延迟

1. 业务现象：
   - 多张流水大表，写入量大，binlog输出量大，主从延迟频发，写完读从库查询不到数据
2. 痛点：
   - 主库生成大量binlog，从库重放跟不上，数据同步延迟，业务读从库出现数据不一致
3. 优化方案：
   - SQL层：
     - 拆分大事务，避免一次性生成巨量binlog
     - 精简索引，减少写入产生binlog量
   - 架构层：
     - 大流水表做冷热归档，减少 binlog 产生
     - 写入压力过高，拆分业务到独立实例，降低单实例写入压力
   - 业务层：
     - 业务关键强一致性读请求强制走主库
     - 业务避免超大事务
   - 运维层：
     - MySQL 开启从库并行复制
     - 优化从库机器 CPU、IO 配置
     - 监控主从延迟告警



## 七、面试高频反问点（面试官常追问）

1. 什么时候不要做分库分表？
   - 单表只是几百万行，慢 SQL 根源是索引差、SQL 写烂，分库分表带来分布式事务、跨分片 join、分布式 ID 等大量复杂度，收益不高反而增加开发运维成本
     - 优先优化 SQL、索引、归档
   - 字典表、配置小表绝对不要拆分
2. 优化整体执行优先级（答题可以直接背）
   - SQL索引优化
   - 冷热归档/分区表
   - 垂直字段拆分
   - 读写分离
   - 水平分表/业务分库
   - 分库分表中间件
3. 开发约束（面试加分项）
   - 大表禁止不带索引条件查询
   - 禁止高峰期DDL，大表变更使用gh-ost/pt-osc
   - 禁止大事务，大批量DML拆小批次
   - 流水类业务前期就要设计时间分区，不要等数据爆炸了再改造
   - 报表统计不占用线上主库资源
