# 一、SQL Dump 核心定义

**SQL Dump** 是数据库的**逻辑备份文件**，本质是将数据库的表结构、数据、索引、约束、视图等所有内容，导出为可直接执行的 SQL 文本脚本。

通俗理解：将数据库完整“复刻成 SQL 代码”，执行该脚本即可1:1还原数据库所有内容。

主流工具：

- MySQL：`mysqldump`（后端最常说的 SQL Dump 特指该工具）
- PostgreSQL：`pg_dump`
- Oracle：`expdp`

# 二、常用实操命令（生产常用）

## 1. MySQL 导出 Dump（核心）

```Plain
# 导出单库（InnoDB 生产热备、无锁、一致性备份）
mysqldump -u root -p --single-transaction --databases 业务库名 > db_backup.sql

# 导出指定表
mysqldump -u root -p 库名 表名1 表名2 > table_backup.sql

# 只导出表结构、不导出数据
mysqldump -u root -p -d 库名 > table_struct.sql
```

## 2. MySQL 导入 Dump 恢复数据

```Plain
# 命令行导入
mysql -u root -p 库名 < db_backup.sql

# 数据库内导入
source /xxx/db_backup.sql;
```

# 三、核心对比：逻辑备份（Dump）VS 物理备份

面试高频考点，生产选型核心依据

| 对比维度      | SQL Dump（逻辑备份）                         | 物理备份（xtrabackup、文件拷贝）   |
| :------------ | :------------------------------------------- | :--------------------------------- |
| 备份内容      | 可执行 SQL 语句（建表、插入数据等）          | 数据库原始磁盘数据文件             |
| 跨版本兼容性  | 极强，全版本通用                             | 极差，大版本不兼容                 |
| 文件体积      | 文本格式，体积偏大                           | 可压缩，体积更小                   |
| 备份/恢复速度 | 慢，逐条执行 SQL                             | 极快，直接拷贝文件                 |
| 锁表情况      | InnoDB 加参数无锁；MyISAM 全局锁表           | 热备工具无锁，冷备需停库           |
| 适用场景      | 环境迁移、小库备份、初始化脚本、数据脱敏导出 | 生产大库定时全量备份、故障快速恢复 |

# 四、真实业务落地场景

## 1. 环境复刻与 Bug 复现

线上数据库导出 Dump，导入测试/开发环境，复刻线上真实数据，精准复现偶现 Bug，避免线上调试风险。

## 2. 数据库迁移、版本升级

跨服务器、跨 MySQL 版本迁移时，使用 Dump 逻辑备份，规避物理文件不兼容问题，迁移稳定性最高。

## 3. 数据备份与应急回滚

作为**全量时间点快照备份**，配合 binlog 增量日志，实现「全量备份+增量回放」，恢复到故障前任意时间点数据。

## 4. 离线数据分析

导出 Dump 给数据分析、算法团队离线使用，杜绝大批量查询直接压垮线上数据库。

## 5. 项目初始化部署

项目内置的 `init.sql` 初始化脚本，本质就是精简版数据库 Dump，用于新环境快速建库建表。

# 五、生产踩坑总结

- **无参数备份锁表**：mysqldump 不加 `--single-transaction`，InnoDB 会锁表，导致业务读写阻塞
- **数据泄露风险**：线上 Dump 包含手机号、身份证等敏感数据，导出后必须脱敏，禁止直接外传
- **大库不适用**：几十G以上超大库，Dump 导出、恢复耗时极长，优先使用物理备份
- **无法实时恢复**：Dump 仅为时间点快照，无法恢复备份后新增数据，必须搭配 binlog 使用

# 六、面试专属速记版（高频必背）

## 1. 什么是 SQL Dump？

SQL Dump 是数据库**逻辑备份方式**，将库表结构、数据、索引等导出为标准 SQL 脚本，可跨版本、跨环境还原数据库，核心工具为 mysqldump。

## 2. mysqldump --single-transaction 原理？

仅针对 InnoDB 引擎生效，基于 **MVCC 多版本并发控制**，开启全局一致性事务快照，在无锁、不阻塞业务读写的前提下，导出同一时间点的完整数据，实现热备。

## 3. Dump 恢复速度慢的原因？

Dump 是文本 SQL 脚本，恢复时需要逐条执行建表、插入数据、创建索引、刷写事务日志，IO 开销大，相比物理文件拷贝速度极慢。

## 4. Dump 和 binlog 的区别与配合？

- **SQL Dump**：全量快照，记录某一个时间点的完整数据库数据
- **binlog**：增量日志，记录备份后所有的增删改 SQL 操作
- **生产标准方案**：定时 Dump 全量备份 + 持续保留 binlog，故障后先恢复全量快照，再重放 binlog，实现任意时间点数据恢复

## 5. mysqldump 核心优缺点？

**优点**：跨版本兼容、操作简单、无需停机、适合迁移和小库备份、可读性强。

**缺点**：大库备份恢复慢、仅时间点快照、MyISAM 引擎会锁表、文本文件体积大。

## 6. 物理备份和逻辑备份选型？

- 小库、迁移、环境复刻、初始化：优先 SQL Dump（逻辑备份）
- 线上超大库、高频备份、快速故障恢复：优先物理备份
