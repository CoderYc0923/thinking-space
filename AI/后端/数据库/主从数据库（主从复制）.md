# 主从数据库（主从复制）

> 核心思想：**一台主库写，多台从库读**，数据从主库同步复制到从库，实现读写分离、高可用、数据备份。以 MySQL 最典型。

## 一、核心角色

1. **主库 Master**

- 负责接收**写请求**（insert/update/delete）
- 把数据变更记录到二进制日志 `binlog`

1. **从库 Slave（Replica）**

- 拉取主库 binlog，重放日志，复现数据变更
- 承担**读请求**，分担主库压力
- 可以有 1~N 个从库

## 二、MySQL 主从复制原理

1. Master 执行写操作，变更写入 `binlog`（二进制日志）
2. Slave IO 线程：连接主库，拉取 binlog，存入本地 `relay‑log`（中继日志）
3. Slave SQL 线程：读取中继日志，执行里面的 SQL，完成数据同步

> 三个线程：主库 binlog dump 线程；从库 IO 线程、SQL 线程

### 复制模式

|       模式       |                   说明                   |                延迟                |
| :--------------: | :--------------------------------------: | :--------------------------------: |
| 异步复制（默认） | 主库写完直接返回客户端，不等从库同步完成 |          存在延迟，性能高          |
|    半同步复制    |   主库至少等待一个从库接收完日志再返回   | 延迟较小，保证至少一台从库拿到日志 |
|    组复制 MGR    |    多节点互相通信，多数派确认，强一致    |       强一致，适合高可用集群       |

## 三、常见架构

1. **一主一从**：简单，备份 + 读分流
2. **一主多从**：多个从库分担大量读流量，互联网最常用
3. **主从链式（级联复制）**：A 主→B 从，B 再作为主给 C 同步。减轻主库压力，但延迟会叠加
4. **双主互主**：两台库互为主从，双写，业务要规避主键冲突，一般配合 MGR / 中间件使用

## 四、主要用途

1. **读写分离**：业务写走主库，查询走从库，扛住更大 QPS
2. **数据备份**：从库做备份，不影响主库业务
3. **高可用故障切换**：主库宕机，把其中一台从库提升为新主库，继续对外服务
4. **数据分析**：大报表、统计任务跑从库，避免影响线上业务

## 五、问题与痛点

1. **主从延迟**

- 网络慢、从库机器性能差、大事务、大量 SQL 导致从库追不上主库
- 现象：写完立刻查，从库查不到刚写入的数据
- 解决方案：关键读请求强制走主库；优化大事务；并行复制；半同步

1. **数据不一致**

- 人为在从库执行写操作；binlog 格式问题；复制异常中断

1. 主库单点故障

   

   原生主从只是复制，

   不能自动故障转移

   。要自动切换需要中间件：MHA、Orchestrator、ProxySQL、MGR。

## 六、binlog 三种格式

1. **STATEMENT**：记录 SQL 语句，日志小，部分函数会造成主从数据不一致
2. **ROW（行模式，推荐）**：记录行数据变更，日志量大，数据一致性最好
3. **MIXED**：混合模式，自动选择 statement/row

## 七、读写分离实现方式

1. 代码层：业务代码手动判断，写→主库，读→从库
2. 中间件层：MyCat、Sharding‑Sphere、ProxySQL，代理层自动路由读写

## 八、和分库分表区别

- **主从复制**：**数据全量复制**，库表结构完全一样，解决读压力、高可用
- **分库分表**：**数据拆分**，每个库只有一部分数据，解决单库数据量过大写压力
