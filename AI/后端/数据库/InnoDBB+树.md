## InnoDB B + 树最优层数

> InnoDB 一页默认 **16KB**，主键索引 B + 树，**3 层是工程上最优、最常用层数**，2 层性能更好但内存成本高，4 层会多一次磁盘 IO 尽量避免。

### 核心计算

1. B + 树非叶子节点（页）存：`主键值 + 子页号`，作用是导航，相当于目录
2. 叶子节点（页）存完整表行数据，用双向链表串起来，范围查询、order by不用回表，直接顺着链表扫叶子页。
   - 二级索引的叶子页存的不是整行，存的是主键值，拿到主键之后再去聚簇索引叶子页回表拿完整数据。

- 页大小固定：`16KB = 16384 byte`

- 非叶子节点一条记录：主键 8字节 + 页号 6字节 = **14B（字节）**，一页大约放1170个索引条目（扇出）

- 树高度

  ```sql
  # 里面的 Index_length不能直接看高度
  SHOW TABLE status like 'xxx'\G 
  
  # 真正看索引树高度命令
  # INDEX_LEVEL就是树高度，根节点 level 最大，叶子页 level=0
  SHOW NAME,INDEX_NAME,INDEX_LEVEL FROM INFORMATION_SCHEMA.INNODB_BUFFER_PAGE
  WHERE TABLE_NAME='`库名`.`表名`' AND PAGE_TYPE='INDEX_PAGE';
  ```

  



### 各层能承载的数据量

1. **1 层**：只有叶子页，数据很少
2. **2 层（根 + 叶子）**：根节点 1 页，指向约 1170 个叶子页。
   - 假设一行数据 1KB，一页存 16 行。总记录 ≈ `1170 * 16 = 18720`
   - 适合小表，只 1 次磁盘 IO，性能最高。
3. **3 层（根→分支→叶子）【生产最理想】**：根 (1) → 1170 分支页 → 每个分支页再 1170 叶子页
   - 叶子总页数 ≈ `1170 * 1170 ≈ 137万`
   - 如果一行比较宽，一行 1KB（业务表平均行宽（几百～1KB））：一页只能存 16 行，那总记录 ≈ `1370000 * 16 ≈ 2200万`
   - 查询需要 **2 次磁盘 IO**（根常驻内存，实际磁盘 IO 是 2 次）（InnoDB 根节点永远缓存在内存，不用读盘）
4. **4 层**：`1170^3`，亿级别数据，查询需要**3 次磁盘 IO**，性能明显下降



| 层数     | 最大量级（行数） | 磁盘 IO 次数 (根在内存) | 适用场景                         |
| -------- | ---------------- | ----------------------- | -------------------------------- |
| 2 层     | 几万～十几万     | 1 次                    | 小表，性能最好                   |
| **3 层** | **千万级**       | **2 次**                | **生产最优，绝大多数业务表目标** |
| 4 层     | 亿级别           | 3 次                    | 大表，尽量避免，建议分库分表     |



### 重点

1. InnoDB 根节点永远在内存，不计入磁盘 IO。
2. 设计表尽量让 B + 树维持 **3 层以内**，千万以内单表最合适
3. 页大小会影响扇出：8KB 页扇出减半，能存的数据量变小，更容易涨到 4 层
4. 主键越大，非叶子节点单条占用越大，扇出降低，树更容易变高，**所以建议自增整型主键**
5. 很多人会记口诀：**千万级 3 层，亿级 4 层，尽量控制在 3 层**



单表千万行 B + 树一定是 3 层吗？

- 不一定，**树高度不只看行数，还看每行记录的宽度**
- 行越宽，一个叶子页放下的行数越少，同样行数需要更多叶子页，中间索引层就更容易膨胀，树就变高
- 主键字段越大，非叶子页能放的索引条目变少（扇出下降），同样行数，树也更容易长高

为什么不用 B 树？

- B + 树数据全部放叶子，非叶子只存索引，扇出更大，树更矮；叶子链表支持范围查询

页越大，扇出越高，层数越少，但缓冲区内存压力上升



### 口述

1. InnoDB 默认数据页是 16KB，它的索引是 B + 树结构，**工程上最优是 3 层**
2. B + 树非叶子节点只存主键和子页号，不存行数据。按 bigint 主键来算，一条索引项大概 14 字节，算下来一个非叶子页大概能存 1170 个索引条目，这个就是扇出。
3. 根节点是常驻内存的，不需要磁盘 IO
4. 如果是两层 B + 树，根直接指向叶子页，只需要一次磁盘 IO，性能最好，但承载数据量有限，适合小表，大概几万十几万数据
5. 三层 B + 树，根、分支层、叶子层，实际两次磁盘 IO，可以支撑千万级别的数据，这也是生产环境最理想的层数
6. 如果涨到四层，就要三次磁盘 IO，性能会明显下降，一般到亿级才会出现四层，这种情况就要考虑分库分表了
7. 主键不要用大字段，主键越大，非叶子节点一条记录占用空间就越大，扇出就变小，树就更容易长高；所以推荐自增整形主键。
8. 页大小也会影响扇出，页越小，扇出越低，树层数更容易变高
9. 所以我们设计 MySQL 表的时候，尽量把单表数据控制在千万以内，让 B + 树维持在 3 层，查询性能最好
